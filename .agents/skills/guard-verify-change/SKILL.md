# Проверка изменения Guard

Сначала прочитай применимые AGENTS.md и AGENTS.override.md. Установи текущую ветку, состав diff и принадлежность незакоммиченных изменений. Не изменяй чужую работу и не создавай новую ветку при продолжении задачи.

Определи проверяемое поведение и риск: доступ, транзакции, дерево, конкуренция, UI либо только документация. Прочитай `scripts/Test-Guard.ps1` и нужный раздел `docs/testing.md`; пути отсчитываются от корня репозитория. Не считай исторические числа успешных проверок результатом текущего запуска.

- Для C#/Razor выполни `dotnet build Guard.slnx --no-restore`. Restore нужен при изменении пакетов или отсутствии восстановленных зависимостей.
- После сборки запускай `./scripts/Test-Guard.ps1`: это последовательный запуск двух исполняемых проектов Guard.UnitTests и Guard.IntegrationTests. Они используют собственный Check; не заменяй их `dotnet test`, xUnit, NUnit или Microsoft.Testing.Platform ради применения внешнего Skill.
- Для изменения доступа, транзакций, дерева и конкуренции нужны соответствующие содержательные сценарии. `-Mode Postgres` допустим только после проверки изоляции тестовой БД и доступности предназначенной среды без вывода подключения или секретов.
- Для браузерной проверки используй предусмотренный стенд и `-Mode Browser`, проверь среду и порт 5079. Не запускай обычный Guard host ради сборки: Program может создавать БД и выполнять seeding.
- Для простого обратимого UI-изменения следуй исключению корневого AGENTS.md: сборка и затронутый сценарий, без тестов, повторяющих реализацию. Для документации и конфигурации Codex достаточно проверки синтаксиса, ссылок и diff; сборка Guard не нужна.

Не выполняй конфликтующие сборки и тестовые среды параллельно. Сначала целевые проверки, расширение — по риску. При отказе среды или разрешений сообщи конкретный блокер; не обходи запрет другой командой. После двух неудачных попыток одной причины пересмотри подход.

Верни: изменённое поведение, точные выполненные команды и результаты, непроверенные сценарии и причины, `git diff --check`, ветку для проверки пользователя. Предложенный тест не называй выполненным. Успешные проверки не разрешают merge, commit или публикацию сами по себе.
