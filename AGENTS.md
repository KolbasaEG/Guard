# Правила работы с Guard

## Область действия

Этот файл действует для всего репозитория. Перед изменением вложенной области проверь наличие более конкретного `AGENTS.md`. Общайся с пользователем на русском языке, если он не попросил иначе.

Выполняй изменения в рамках задачи. Не превращай исправление в переработку всей архитектуры. Проверяй `git status` перед работой и сохраняй существующие изменения пользователя. Не меняй настройки подключения, секреты и данные ради локальной проверки.

## Порядок работы над задачами и Git

- Перед началом каждой новой задачи проверь текущую ветку и `git status`, затем создай отдельную ветку `codex/<краткое-название-задачи>`. Изменения выполняй в этой ветке, а не в `main`. Продолжение той же задачи выполняй в уже созданной для неё ветке.
- Обычно создавай ветку от актуальной локальной `main`. Если задача продолжает работу другой ветки или рабочее дерево содержит незавершённые изменения, сначала оцени их принадлежность. Не сбрасывай, не прячь в stash и не включай чужие изменения в коммит автоматически. При неоднозначности уточни у пользователя, от какой базы продолжать и как сохранить незавершённую работу.
- По ходу задачи задавай пользователю вопросы, когда возникают неясности в требованиях, ожидаемом поведении, ограничениях или значимых вариантах реализации. Задавай их до зависимых изменений; при возможности продолжай независимую часть работы. Не принимай отсутствие ответа за подтверждение.
- После выполнения представь результат для проверки: название ветки, описание изменений и их назначение, затронутые файлы, результаты проверок и существенные ограничения. Укажи, что ветка ожидает проверки пользователя.
- Сливай ветку в `main` только после того, как пользователь проверит результат и явно подтвердит слияние. Завершение реализации, успешная сборка или отсутствие замечаний сами по себе не разрешают merge. До подтверждения оставляй изменения в ветке задачи.
- Если после проверки пользователь просит доработки, выполняй их в той же ветке, повторяй необходимые проверки и представляй обновлённый результат. Подтверждение должно относиться к актуальному результату; не распространяй прежнее согласие на существенные последующие изменения.
- Перед подтверждённым слиянием проверь состояние рабочего дерева и совместимость с `main`. Не включай несвязанные изменения. После слияния сообщи результат и проведённые проверки. Push, публикацию и удаление ветки выполняй только в рамках отдельного разрешения пользователя.

## Проект и архитектура

- `Guard.slnx` содержит один веб-проект `Guard/Guard.csproj`, целевая платформа — .NET 10.
- Приложение использует Blazor с интерактивным серверным режимом, Radzen, ASP.NET Core Identity, EF Core и PostgreSQL.
- Это слоистый монолит. Папки слоёв находятся в одной сборке; границы зависимостей не обеспечиваются отдельными проектами.
- Основной поток записи: компонент → сервис → `IUnitOfWork` → репозиторий → `ApplicationDbContext`.
- Основной поток чтения: компонент → сервис → `IReadRepository<T>` → `IDbContextFactory<ApplicationDbContext>`.
- `LogsDbContext` обслуживает отдельную БД логов. Serilog и Identity-аудит выполняют разные задачи.

Карта кода:

| `Guard/Core/1-Entities` | Сущности и общие поля |

| `Guard/Core/7-Interceptors` | Заполнение полей аудита при сохранении |
| `Guard/Core/8-Extensions` | Общие преобразования и фильтры запросов |

## Границы и прикладные операции

- UI отвечает за отображение, ввод, состояние загрузки, диалоги и уведомления. Новые бизнес-правила размещай в сервисах или специализированных доменных методах.
- Для новых сценариев предпочитай явные параметры поиска и DTO результата. Не расширяй зависимость UI от `IQueryable`, `Include` и EF-операторов без необходимости. Существующие query-делегаты поддерживай совместимыми в рамках задачи.
- Материализуй результат `IReadRepository.QueryAsync` внутри делегата: контекст освобождается сразу после выполнения. Не возвращай из него запрос или отложенное перечисление, требующее живого контекста.
- Проверяй входные данные в прикладной операции. Валидация формы не заменяет серверную проверку.
- MediatR и FluentValidation присутствуют среди пакетов, но не являются установленной архитектурной конвенцией. Не вводи обработчики, pipeline или новые зависимости только из-за наличия пакета.

## Данные, контексты и транзакции

- Не выполняй параллельные операции на одном `DbContext`. Scoped-контекст в интерактивном Blazor может жить весь circuit; не считай его автоматически контекстом одной операции.
- Для новых независимых операций записи предпочитай контекст на операцию с единым временем жизни репозиториев и транзакции. При изменении текущей схемы согласованно сохраняй аудит и интеграцию Identity.
- Составные изменения выполняй атомарно. Используй существующие транзакционные обёртки там, где они подходят; учитывай, что `CommitTransactionAsync` сам вызывает `SaveChangesAsync`.
- Не вызывай сохранение после каждой записи в цикле без необходимости. Передавай `CancellationToken` до EF и HTTP-операций; не подменяй его `CancellationToken.None`, кроме необходимого завершения отката или очистки.
- Проверяй каждый `IdentityResult`. Не возвращай успех, если назначение ролей, удаление claims или другой обязательный шаг завершился ошибкой. Предусматривай транзакцию или явную обработку частичного результата.
- Конфигурацию схемы размещай в `IEntityTypeConfiguration`. Изменения модели сопровождай миграцией и проверкой индексов, внешних ключей и поведения удаления.
- Не редактируй применённые миграции без явной задачи. Не запускай `database update`, сброс, очистку или seeding против неизвестной БД.
- Время сохраняй в UTC. `DateTime.SpecifyKind` меняет метку, а не переводит часовой пояс: используй его только для данных, уже представляющих UTC.

## Доступ и жизненный цикл

- `[Authorize]` проверяет вход пользователя; он не заменяет проверку permissions, роли и доступа к конкретной записи.
- Для новых или изменяемых защищённых операций проверяй полномочия и доступное подразделение на уровне сервиса. Не доверяй ID, пути подразделения, выбранному фильтру или флагу редактора, полученным из UI.
- Пустой путь в `FilterBySubdivision` сейчас снимает фильтр. Не используй это поведение как правило доступа. Доступ Root ко всем подразделениям должен быть явным.
- Не добавляй операции редактирования заблокированных записей или произвольные переходы статусов. Учитывай `Blocked`, `Archived`, `ArchivedBlocked` и `Deleted`; определяй допустимые переходы явно.
- Значения `Status` сохраняются в БД: не меняй их числовые значения. Не полагайся на сравнение enum через `<` или `<=` для новых правил активности; перечисляй допустимые состояния либо используй общий проверенный фильтр.
- Полномочия берутся только из permissions назначенных ролей. Индивидуальные permission claims сохраняются, но не учитываются. Не используй имя «Администратор» или claims cookie как самостоятельное основание доступа; применяй IPermissionService и серверную область IDataAccessScopeService. Root имеет полный доступ и единственный управляет ролями.
- Список сотрудников получает PersonalListItemDto через SearchAsync; полная сущность требует Personals.ReadDetails. Экспорт и архив проверяются отдельно. Обычная область — подразделение сотрудника и потомки; отсутствующий или некорректный путь означает пустую область.
- Изменение ролей и их permissions выполняй через IRoleAccessService с проверкой версии и транзакцией. Правила перехода существующих данных и проверки описаны в docs/role-permissions.md.
- IP-допуск проверяется перед выдачей cookie и при новом HTTP/Blazor-подключении: только активные IP сотрудника, пустой список запрещает доступ, Root освобождён от IP-проверки. Периодического отзыва уже открытого соединения нет. Не отключай эти проверки и не подменяй их фильтром UI.

## Иерархия подразделений

- Дерево представлено одновременно связью `ParentId` и materialized path `Path` вида `/1/4/12/`.
- При создании и перемещении сохраняй согласованность родителя и пути. Перемещение ветви должно атомарно менять пути всех потомков.
- Запрещай перенос узла в самого себя и в своего потомка. Не выполняй массовую выборку потомков по пустому префиксу.
- Сохраняй разделители пути и учитывай конкурентное редактирование дерева. При изменении запросов проверяй применимость индекса `Path` с `varchar_pattern_ops`.

## DI, интеграции и аудит

- Проверяй не только явные регистрации в `Program.cs`, но и Scrutor-сканирование по суффиксам `Service` и `Repository`.
- Не допускай повторной регистрации typed HTTP client обычным сервисом: это может обойти настройки `AddHttpClient`. При добавлении такого клиента исключай его из общего сканирования или делай регистрацию однозначной.
- Адреса внешних сервисов и credentials получай из конфигурации или хранилища секретов. Не добавляй секреты в код, `appsettings`, логи или вывод команд.
- Не отключай проверку TLS-сертификатов. Существующее принятие ошибок сертификата SIEM — технический долг, а не образец для новых интеграций.
- `AuditSaveChangesInterceptor` заполняет метаданные `BaseEntity`, но не хранит полную историю изменений. Контексты фабрики сейчас создаются без этого интерцептора: учитывай это, если добавляешь запись через фабрику.
- Для событий безопасности используй `IAuditService`; для технической диагностики — структурированный `ILogger<T>`. Не логируй пароли, токены и избыточные персональные данные.
- При изменении динамического логирования проверяй освобождение старых логгеров, доставку накопленных событий и потокобезопасность смены конфигурации.

## UI и стиль

- Используй существующие компоненты Radzen и обёртки `Components/Library`, прежде чем создавать аналогичные элементы.
- Перед созданием или изменением форм добавления, редактирования и чтения (просмотра) изучи `Guard/Components/Library/README.md` и содержимое подходящих компонентов библиотеки, включая их параметры, события и стили. Используй `Forms/CreateEntity`, `Forms/EditEntity` и `Views/ViewEntity`, а для дополнительной информации — `Views/EntityInfo`; учитывай общий каркас `Forms/EntityForm`, компоненты `Cards` и `Loading`. Не дублируй существующие оболочки и поведение: если возможностей недостаточно, сначала оцени совместимое расширение компонента. Логику конкретной сущности оставляй в компоненте соответствующей области и прикладных сервисах.
- Сохраняй разделение `.razor` и `.razor.cs` в областях, где оно принято. При изменении маршрута проверяй страницу `Workspaces`, вложенный CRUD-компонент и layout.
- Пользовательские надписи и сообщения — на русском. Ошибки интерфейса должны объяснять действие пользователю; внутренние исключения и детали БД отправляй в лог.
- Сохраняй принятый стиль C# и nullable-аннотации. Не выполняй массовое форматирование и переименование в несвязанной задаче.
- Не оставляй публичные методы-заглушки, возвращающие успех без выполнения операции.

## Проверка изменений

Команды из корня репозитория:

```powershell
dotnet restore Guard.slnx
dotnet build Guard.slnx --no-restore
dotnet run --project Guard/Guard.csproj
```

- Для изменений C#/Razor выполняй сборку. Restore нужен при отсутствии восстановленных зависимостей или изменении пакетов.
- Не запускай приложение только ради проверки сборки: запуск вызывает создание БД, а в Development — seeding. Перед запуском проверь, что подключения ведут к предназначенной для проверки среде, не выводя секреты.
- Проверки IP-доступа находятся в `Guard.IpRules.Tests`: запускай через `dotnet run --project Guard.IpRules.Tests/Guard.IpRules.Tests.csproj`. Режим интеграционных проверок PostgreSQL описан в `docs/ip-access.md`. Не заявляй, что тесты прошли, если выполнялась только сборка.
- Для изменений доступа, транзакций, дерева и конкуренции добавляй содержательные тесты при наличии подходящей среды; интеграционные проверки PostgreSQL выполняй на изолированной тестовой БД.
- Для простых обратимых UI-изменений достаточно сборки и проверки затронутого сценария. Не добавляй тесты, повторяющие реализацию.
- Перед завершением проверь diff на случайные изменения. В ответе укажи результат, проведённые проверки и существенные непроверенные сценарии. Если проверка недоступна, сообщи причину прямо.

## Направление развития

Улучшай архитектуру постепенно: серверные правила доступа → согласованное время жизни контекстов и атомарность операций → DTO и параметры поиска вместо запросов из UI → единые правила статусов → защита от конкурирующих изменений. Разделение на сборки или введение новых архитектурных паттернов выполняй в отдельной задаче с конкретной пользой.
