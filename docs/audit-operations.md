# Обязательный аудит Guard: реализация и эксплуатация

Изменения подготовлены в `codex/logging-reliability` по [согласованному плану](audit-compliance-plan.md). Эта инструкция описывает текущий код; [первоначальный разбор логирования](logging-reliability.md) сохранён как история.

## Режимы и первый запуск

| Условие | Локальный режим | Режим RuSIEM |
| --- | --- | --- |
| Обязательная запись в PostgreSQL приложения | Да | Да |
| Новые события требуют отправки | Нет | Да |
| Старая обязательная очередь | Сохраняется, отправка приостановлена | Отправляется с исходным временем постановки |
| Запрет по возрасту/объёму очереди | Нет | Да |
| Запрет при отказе локальной записи | Да | Да |

После миграции режим ещё не подтверждён (`Configured=false`). Обычная работа закрыта до сохранения настроек действительным Root. Начальное хранение — один календарный год. Численные ограничения SIEM не подбираются автоматически: Root должен задать их перед включением режима.

При первом запуске войдите под Root: система выдаст ограниченную сессию и направит в диагностику. Откройте `/audit/settings`, выберите локальный режим либо RuSIEM с обязательными пределами очереди и сохраните. После этого выйдите и войдите заново для обычной работы. Фоновая проверка показывает `NotConfigured` как состояние без исключения; очередь экспорта ожидает готовности аудита. Запрет рабочих операций до настройки сохраняется.

Настройки доступны в `/audit/settings`; подробный диагностический журнал — `/audit/diagnostics`. Обычный журнал `/audit` также требует серверного допуска. Право `Audit.Read` помечено как Root-only. Все диагностические операции дополнительно проверяют актуальную роль Root, security stamp и блокировку аккаунта в Identity-БД.

Страницы восстановления используют оформление основного приложения: логотип, боковую навигацию, верхнюю панель с темой и выходом, стандартные карточки библиотеки. Меню содержит только состояние/настройки, диагностический журнал и обычный вход. На широком экране состояние и настройки расположены в двух колонках; на узком — последовательно. Временные метки показываются в UTC в формате `дд.ММ.гггг ЧЧ:мм:сс`.

Диапазоны: хранение 1–30 лет; возраст SIEM 1–525600 минут; объём от 1024 байт; дополнительный предел количества от 0, где 0 отключает только этот дополнительный предел. Объём — сумма UTF-8 сериализованных данных обязательных неотправленных событий, **не физический размер БД, индексов или истории попыток**. Ёмкость диска требует отдельного эксплуатационного контроля.

## Переключение и доставка

События Local не отправляются задним числом. Переход Local → SIEM возобновляет прежнюю обязательную очередь, включая её первоначальный возраст; поэтому работа может сразу оказаться заблокированной. SIEM → Local сохраняет очередь и останавливает отправитель. Изменение host, port или доверенного CA при наличии pending требует отдельного подтверждения Root; без него настройки не меняются.

Смена режима или назначения не подтверждается при действующей аренде отправки. После штатного завершения попытки можно повторить сохранение. После падения процесса аренда истекает через две минуты. Это исключает начало отправки арендованного события после подтверждения локального режима.

Отправитель выбирает до 25 событий за цикл, работает отдельно от транзакций изменения данных, записывает каждую попытку и использует задержку повторов до часа. Интервал циклов — две секунды. Сетевой таймаут — 15 секунд. После потери подтверждения возможен повтор того же `EventId`: получатель должен учитывать дубликаты.

Транспорт — Syslog RFC5424 с UTF-8 CEF и byte-count framing RFC6587 поверх TLS. Проверяются доверие, имя и срок сертификата; отключения проверки нет. Можно задать публичный PEM CA либо использовать системное доверие. Приватный ключ форма не принимает. CEF передаёт `externalId`, `rt`, `suser`, исходный IP, результат, correlation, тип/ID объекта, вид инициатора, код причины и введённое имя аккаунта. Строки экранируются, размер ограничивается с признаком усечения.

**«Отправлено по TLS» означает завершённую запись транспортом. Это не подтверждение сохранения или нормализации события в RuSIEM.** Для проверки соединения Root получает EventId тестового события и должен найти его в своей SIEM. Поддержку парсеров CEF/syslog и Syslog TLS описывает [каталог RuSIEM](https://rusiem.com/ru/products/parsers); используемые ключи и экранирование сверены с [CEF Implementation Standard](https://docs.microfocus.com/doc/2097/25.4/siemcefimplementationstandard) и [словарём CEF](https://docs.microfocus.com/doc/2097/26.1/ab6eeee4916c_arcsight_extensions). Приёмку конкретной установки эти источники не заменяют.

## Состав событий и целостность

| Область | Что сохраняется |
| --- | --- |
| Вход | Один итог попытки: успех, неверные данные, неизвестный аккаунт, IP/политика/блокировка, некорректная форма, rate limit. Отдельно — изменение счётчика и наступившая блокировка |
| Сессия | Выход, отзыв при HTTP-проверке stamp/политики, обновление сессии; обновление после смены пароля не выдаётся за новый вход |
| Аккаунт | Создание, изменение, блокировка и разблокировка; безопасные изменённые поля Identity, ошибки и отказы прикладных операций |
| Пароль | Смена/сброс и отклонение, требование смены; только имена чувствительных полей, без значения хеша, пароля или токена |
| Роли | Создание/изменение/удаление, безопасный diff permissions, назначение/снятие, отказы и ошибки |
| IP | Изменения адресов и назначений, отказ до cookie и при новом соединении |
| Политики | Безопасный diff параметров; автоматическая блокировка с системным инициатором |
| Экспорт | Запрос, обработка, архив с количеством строк/байтов/SHA256, начало и результат передачи, отказ/отмена, восстановление после перезапуска, истечение срока, изменение хранения |
| Аудит | Изменение режима/назначения/ограничений/срока, тест соединения, переходы доступности, очистка |

Инициатор и затронутый аккаунт/объект — разные поля. Анонимно введённое имя не становится UserId. Фоновые операции указывают системного инициатора. HTTP и Blazor задают отдельные контексты IP и correlation. Обычные просмотры, поиск и предварительный просмотр архива самостоятельных событий не создают.

Основная запись и обязательные события сохраняются одной транзакцией основной БД. Это действует для фабричных контекстов, scoped Identity stores и составных операций. Сетевой вызов SIEM в эту транзакцию не входит. Полная история персональных значений и построчная история импорта не добавлены; импорт имеет итоговый аудит.

При потере подтверждения commit возвращается отдельный неподтверждённый исход: сначала нужно перечитать состояние, затем решать о повторении. При восстановлении скачивания после перезапуска результат попытки остаётся nullable/unknown; сервер не утверждает, что клиент получил файл. Ссылка остаётся использованной.

Изменение файла настроек технического логирования имеет иной предел атомарности: сначала долговечное намерение, затем применение файла и подтверждение результата. Если подтверждение потеряно, требуется проверить фактические настройки; общей транзакции файла и PostgreSQL нет. Ошибка записи намерения запрещает изменение.

Новые прямые `ExecuteUpdate`/SQL-пути требуют явного события и транзакции: EF SaveChanges не перехватывает произвольный SQL. Служебное обновление времени активности проверяет доступность внутри транзакции, но не создаёт событие просмотра.

## Запрет работы и восстановление

Проверка доступности выполняет пробную вставку и удаление в одной транзакции с подтверждённым commit. Так проверяется и завершение транзакции, а события просмотров не остаются в журнале. Для SIEM проверяются доверенное время постановки, байты и количество. Равенство пределу допустимо, превышение запрещает работу; записи проверяются с учётом добавляемого события. Сериализация проверки и вставки защищает от конкурентного переполнения.

При запрете закрыты обычные HTTP-запросы, серверные операции чтения/записи, экспорт, действия уже открытого circuit и новые фоновые рабочие задания. Чтение проверяется повторно перед возвратом; длительные операции — в контрольных точках, поток файла — при чтении. Уже показанные пользователю данные нельзя отозвать из памяти браузера. Уже переданные байты нельзя вернуть обратно.

Доступными остаются выход, отправитель, безопасное обслуживание и ограниченная диагностика Root. Служебные события имеют конечный резерв очереди: до дополнительных 1% объёма или 1 МиБ (большее значение), а при пределе количества — до 1000 дополнительных событий. Изменение настроек восстановления и пакетный итог очистки не блокируются этим резервом, но требуют исправной локальной записи. Физический отказ хранилища не позволяет гарантировать запись события даже о самом отказе; независимая диагностика пишет stderr и резервный файл.

При доступной Identity-БД Root может получить отдельную непостоянную cookie на 15 минут только для восстановления. Она не даёт обычных permissions и не превращается в рабочую после ремонта: нужен новый обычный вход. Вход ограничен по доверенному IP, а настройки всё равно требуют аудита. Обычная сессия возобновляет работу автоматически после успешной проверки и возвращения очереди в допустимые пределы.

При отказе Identity-БД Root не может подтвердить полномочия. Если сбой произошёл при проверке cookie, текущий запрос помечается как недопущенный; доступны только точные пути публичного отказа и выхода. Решение о sliding renewal откладывается до успешной проверки Identity. Приложение не продлевает сессию на отказавшей проверке. Восстановление БД и инфраструктуры выполняется обслуживанием сервера.

Root видит режим, текущий код и время проверки, возраст показателей, последние успех/сбой локального хранения, безопасный SQLSTATE, текущую очередь и пределы, версию настроек, время отправителя, наблюдаемый срок сертификата, очистку и историю попыток каждого события. При недостоверном состоянии очереди показывается «неизвестно». Счётчики ошибок, очистка и наблюдение сертификата относятся к данному процессу и сбрасываются при перезапуске; сами события, настройки и попытки долговечны.

## Хранение и выпуск

Очистка работает каждые пять минут независимыми этапами: аудит, техническая БД, известные файлы приложения. Каждый цикл ограничен десятью пакетами по 1000 записей аудита и 10000 технических записей. Сбой одного этапа не мешает следующим. Предел — `UtcNow.AddYears(-RetentionYears)`. Удаляются старые Local и доставленные события; обязательные pending сохраняются до доставки, даже при остановленной очереди. Поздно доставленное старое событие попадает в штатную очистку. История попыток удаляется каскадно с событием.

В подготовленной схеме участвуют миграции `20261020120000_AddAuditJournal` и `20261020150000_EnforceMandatoryAudit`, а для существующей технической таблицы — [Upgrade-Logs.sql](../scripts/Upgrade-Logs.sql). Последняя миграция также делает результат попытки выдачи файла nullable. Миграции проверяются только на изолированной БД. Рабочая среда в этой задаче не обновляется.

Перед выпуском нужны резервная копия, проверка подготовленного SQL на копии фактической схемы и согласованное окно обслуживания. Старые события сохраняются; legacy pending получают обязательство доставки и исходный возраст. Уменьшение срока Root разрешает штатной очистке удалить старые Local/доставленные записи. Старт обычного приложения создаёт БД при её отсутствии, а Development также выполняет миграции/seeding — использовать его как проверку сборки нельзя. Отказ соединения с БД при холодном старте обрабатывается с сохранением публичной страницы отказа; доступа к диагностике без подтверждённого Identity он не даёт.

Реальная RuSIEM, её парсер/корреляции, доверие и отзыв сертификатов в целевой сети, нагрузочная ёмкость, резервное копирование и восстановление рабочей инфраструктуры требуют отдельной эксплуатационной приёмки. PostgreSQL-журнал не является криптографическим WORM-хранилищем и не защищён от администратора самой БД.

## Проверки

Используются сборка решения и `scripts/Test-Guard.ps1`. PostgreSQL/Browser runner создаёт локальную БД `guard_ip_test_*` и удаляет её после завершения; браузерный host использует временные ключи и каталог экспорта.

Проверки охватывают конкуренцию очереди, режимы и перенос назначения, отказ локального журнала, атомарность Identity/ролей/IP/экспорта/импорта, потерянное подтверждение commit, отзыв Root во время ожидания, отказ аудита во время чтения, неизвестный исход выдачи, TLS trust/SAN/expiry/framing, очистку при отказе технической БД и ограниченные HTTP recovery-сессии. Отдельный тест настоящего CookieAuthenticationHandler сравнивает отказавшее и успешное продление старой cookie.

Браузером проверены автоматическая загрузка журнала, выбор Local, пагинация, сортировка, применение/очистка фильтра, открытие и закрытие карточки, поля режима RuSIEM и сохранение срока с новой версией.

Заключительная сборка `dotnet build Guard.slnx --no-restore -v quiet` — без ошибок; полная перекомпиляция сохраняет 25 прежних предупреждений, заключительная инкрементальная сборка — без предупреждений. Заключительный `./scripts/Test-Guard.ps1 -Mode Postgres` от 20.10.2026: **4711 unit checks и 21319 integration checks**, включая настоящий cookie handler, отказ при commit и доверенного автора Identity вне HTTP. Отдельно на изолированном браузерном host прошли **20 own-password/logout HTTP**, **70 local-account HTTP** и **20 audit outage/recovery HTTP** проверок. Временные host остановлены, runner завершился штатно с удалением временной БД. Проверка холодного старта использует loopback TCP-порт, принадлежащий самому тесту; на нём нет PostgreSQL.

После уточнения изоляции TCP-стенда повторён `./scripts/Test-Guard.ps1 -Mode Basic`: **4711 unit checks и 19941 integration checks**, успешно. `git diff --check` и проверка новых файлов замечаний не выявили. Целевое независимое security-ревью завершено, подтверждённые находки исправлены; его исполнитель проверки не запускал.

После исправления остановки отладчика при первом запуске: сборка в `Guard/obj/audit-startup-build` с `UseAppHost=false` — 0 ошибок, 25 прежних предупреждений.
