# Готовность технического логирования

Дата: 21.10.2026. Ветка: `codex/technical-logging`. Статус: программные доработки и локальная проверка завершены; пользовательская и эксплуатационная приёмка, слияние и выпуск отдельно. Процент не заменяет критерии ниже.

## Согласованные требования

Технический fail-open; отдельный обязательный аудит с прежними ограничениями. Root включает диагностику вручную на ограниченное время; автоматический рост уровня запрещён. Хранение технических данных независимо от аудита. Доставка локального буфера после восстановления БД с защитой от дубликатов и учётом известных потерь. Ориентир: около 1 000 пользователей и 12 часов недоступности БД логов. После замера пользователь согласовал 3072 МиБ для новых установок; сохранённые политики, включая 512 МиБ, остаются прежними. Остальные начальные значения: 30 суток, резерв 1024 МиБ, 15–60 минут, 20 ошибок за 5 минут.

## Владельцы регистрации ошибок

| Граница | Штатное / ожидаемое | Технический сбой |
|---|---|---|
| Startup / shutdown | Безопасный bootstrap-канал | Fatal и безопасный граф до завершения host |
| HTTP | Serilog request logging + correlation; обработанные отказы отдельно | Необработанный request Error; обработанные ошибки передачи регистрирует endpoint |
| Blazor / CRUD | Отмена загрузки отдельно; правила/доступ/конкуренция Warning | UI вызывает LogOperationFailure с контекстом операции |
| ReadRepository | Debug этапы/длительность/отмена | Итог принадлежит вызывающей операции; компонент сотрудников теперь пишет Error |
| UoW | Debug отмена, ожидаемые конфликты отдельно | Первый зарегистрировавший исключение владеет Error; следующий инструментированный этап Debug. Ошибка rollback — отдельное исключение/Error |
| Directory API | Warning промежуточные повторы; correlation/run | Финальный сбой runner; ручной ping — UI с exception и техническим кодом |
| Synchronization | Подтверждённая отмена Information; состояние и этап | Исходная ошибка до повторного обращения к БД, служебный сбой доходит до worker |
| Export | Подтверждённая отмена/отзыв доступа Information | Ошибка формирования/таймаут Error; сбой worker отдельно; очистка Warning |
| Logging worker | Независимые probes и health | Без рекурсии в собственный sink; безопасная внутренняя диагностика и причины состояния |

Одинаковый объект исключения подавляется через ConditionalWeakTable только в согласованных вызовах LogOperationFailure. Новое исключение, другая подсистема или отдельное событие EF может создать новый Error. Предупреждение Root считает события, а не расследованные инциденты. Произвольный cancelled token внутри HttpRequestException/OperationCanceledException не доказывает отмену пользователя: учитывается именно токен операции или подтверждённая причина.

## Проверки текущего изменения

### Замер подсистемы

Итоговый Technical-Benchmark завершился успешно на текущем коде: .NET 10.0.12, 12 логических CPU, 1000 параллельных производителей по три операции. Нормальный профиль — 3000 событий, диагностический — 15000. Все принятые события доставлены, число строк точно совпало; временные файлы и БД удалены. После успешного функционального прогона добавлялись только измерительные показатели benchmark, производственный код не менялся.

| Показатель | Штатный | Диагностический |
|---|---:|---:|
| Запись событий/с | 473,5 | 477,2 |
| Средний JSON-конверт, байт | 871,2 | 787,4 |
| Добавленная длительность операции p50 / p95 / p99, мс | 26,1 / 42,3 / 49,2 | 224,1 / 243,8 / 266,0 |
| Доставка без пауз, событий/с | 1526,9 | 1167,8 |
| Расчёт доставки с паузами worker, событий/с | 214,8 | 205,9 |
| Покрытие 512 МиБ при расчётном входящем потоке, часов | 5,14 | 1,14 |
| CPU процесса на запись, секунд / доля всей 12-CPU машины | 4,88 / 6,41% | 19,73 / 5,23% |
| Working set после записи / managed memory, МиБ | 115,0 / 17,8 | 122,1 / 23,7 |
| Логическая скорость записи JSON, МиБ/с | 0,39 | 0,36 |
| Чтение локального пакета 1000 событий, мс | 290,3 | 267,5 |

Операции benchmark содержат одно штатное или пять диагностических событий; для ёмкости принят консервативный пример два/десять событий на пользовательскую операцию. Это отдельные синтетические профили, не замер времени CRUD/HTTP/Blazor. Параллельные производители выполняются через пул потоков, а не через 1000 выделенных потоков/браузеров. p95 под одновременным насыщением не является SLA обычной пользовательской операции. Порог пригодности подсистемы: поток записи/доставки выше плановых 33,3 штатных и 166,7 диагностических событий/с, нулевые потери в проверенном наборе. Он выполнен на локальном стенде.

Для 12 штатных часов нужно около 1556 МиБ логической квоты с 30% запасом; для 11 штатных и часа диагностических — 2012 МиБ и 1,92 млн файлов. Согласованные 3072 МиБ/3 млн файлов покрывают этот расчётный пример. Исходные 100000 файлов не покрывали его независимо от байтовой квоты. При продолжающемся штатном потоке расчётное опорожнение backlog 1,44 млн занимает около 2,2 часа; это оценка по короткому замеру, не выдержанный двенадцатичасовой опыт.

Итоговая сборка `Guard.slnx --no-restore` в `Guard/obj/technical-readiness-build`: 0 ошибок, 0 предупреждений в последнем инкрементальном запуске. Полная перекомпиляция затрагиваемых проектов ранее выводила существующие предупреждения проекта; новых предупреждений не добавлено.

`./scripts/Test-Guard.ps1 -Mode Postgres -BinaryDirectory Guard/obj/technical-readiness-build`: **4711 unit + 22827 integration**, код 0. Проверены безопасные nested/aggregate/длинные исключения, numeric-secret, сохранение прежних 512 МиБ, Root/аудит/отзыв прав в обеих финальных точках, CSRF/Range, локальная выгрузка при недостижимой logs DB, cursor и отсутствие ACK, второй владелец, stale probes, восстановление отдельно от исторических потерь, сохранение/commit/rollback/отмена без повторных Error. На временной PostgreSQL-БД проверены несовместимая схема, ошибка второй строки и отмена задержанного INSERT с откатом всего пакета, replay, коррумпированные файлы, экспорт/ограничения, безопасный historical jsonb и retention.

Тест реального завершения процесса запускает только собственный дочерний runner, дожидается подтверждения двух durable-событий, принудительно завершает его и сверяет UUID после восстановления. Непринятый частичный .tmp исключается; отдельно проверена файловая копия backup с исходным сроком диагностики. Это процессный crash, не отключение питания.

`-Mode Browser` на тех же бинарниках повторно прошёл 4711/22827; дочерний host дополнительно выполнил **20** HTTP-проверок собственного пароля/выхода, **70** Account и **23** отказа/восстановления аудита. В браузере проверены первая загрузка `/Logs`, свежие причины/пробы, 3072 МиБ в форме, выбор локального источника и поле продолжения, аудируемый preview, включение с основанием/абсолютным сроком и ручное завершение. Реальная HTML-форма скачала JSONL: manifest Count=199, фактически 199 уникальных UUID, 172967 байт, Truncated=false. После проверки host остановлен, временная БД удалена, порт 5079 освобождён.

Независимое security-ревью подтвердило устранение двух P2: numeric-sensitive properties и окно выдачи при отзыве Root во время последнего audit await. Повторное ревью нового постоянного SQL и итоговых проверок не выявило новых существенных замечаний в назначенной области. Это целевая проверка, не полный аудит всей системы.

Доказательства локального запуска (игнорируемые артефакты): `Guard/obj/technical-readiness-build.log`, `technical-readiness-postgres.log`, `technical-readiness-benchmark-final.log`, `technical-readiness-browser-export.jsonl`, `technical-readiness-status.png`. `git diff --check` — без замечаний. Воспроизведение:


## Граница готовности

Нельзя заявлять «100%» или гарантию 12 часов для любого количества событий. Требуется приёмка на целевой инфраструктуре: реальный поток/объём/физическое место, полный retention-набор и индексирование БД, 1000 пользовательских сессий, длительный outage и replay при продолжающейся работе, реальное дисковое переполнение/отзыв INSERT, эксплуатационное восстановление независимым администратором. Локальные тесты не эмулируют физическое отключение питания и не доказывают гарантии контроллера диска. Внешние уведомления требуют отдельно выбранного канала и получателей.
