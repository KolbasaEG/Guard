# IP-доступ

## Политика

- Для обычного пользователя используются только адреса, назначенные его сотруднику в `PersonalIpAddresses`. Принадлежность адреса подразделению не даёт разрешения на вход.
- Пустой список назначений, отсутствующий сотрудник, неактивный сотрудник, неизвестный пользователь или неопределённый IP запрещают доступ.
- Для допуска используются IP со статусом `Inserted` или `Modified`. Архивные, заблокированные и удалённые IP не разрешают вход.
- Роль `Root` освобождает от IP-проверки. Это исключение не отменяет проверки Identity и блокировки учётной записи при входе.
- Проверка выполняется перед выдачей authentication cookie и для авторизованных HTTP-запросов, включая новое соединение Blazor. Периодической проверки уже открытого соединения нет. Изменение назначений действует на следующем входе, запросе или переподключении.
- Выход доступен даже после отзыва IP. При отказе нового подключения возвращается HTTP 403.

## Каталог и назначения

Поддерживаются IPv4, IPv6 и CIDR. Например, `192.168.1.99/24` сохраняется как `192.168.1.0/24`. Подсети `/32` и `/128` приводятся к отдельному адресу. IPv4-mapped IPv6 приводится к IPv4; для mapped CIDR разрешены префиксы `/96`–`/128`, которые преобразуются в IPv4 `/0`–`/32`.

Повторные адреса запрещены, включая эквивалентные варианты старых строк. Архивные и удалённые строки также сохраняют уникальность: для повторного использования восстановите запись. Невалидные старые строки не дают доступа; исправляйте их через каталог. Автоматической массовой перезаписи старых данных нет.

В списке сотрудников кнопка с иконкой сети открывает назначения IP. Разрешённые адреса можно выбрать или очистить. Список содержит активные адреса из области доступа оператора. Root может назначать и общие адреса без подразделения. Недоступные оператору старые связи сохраняются; удалить их может Root или оператор с доступом к соответствующему подразделению.

Управление доступно Root, роли `Администратор` или обладателю соответствующих `Permissions.Users.*` / `Permissions.Personals.*`. Сервисы проверяют актуальные роли и claims в БД и область подразделений. Для записи требуются `Manage` или `Write`, для чтения — `Read`. Администратор ограничен своим подразделением и потомками. Общими адресами управляет Root.

Записи каталога и назначений выполняются в отдельных контекстах с транзакциями. Заполнение автора и времени задаётся явно, поскольку фабрика контекстов не подключает scoped-интерцептор. Advisory lock сериализует запись IP-каталога и назначений. Индекс уникальности остаётся последней защитой от одинаковых строк.

## Прокси

Адрес берётся только из `HttpContext.Connection.RemoteIpAddress` после `UseForwardedHeaders`. Код не доверяет сырому `X-Forwarded-For`. Для удалённого reverse proxy настройте список его адресов через конфигурацию окружения, например `ReverseProxy__KnownProxies__0`. По умолчанию сохраняются доверенные loopback-прокси ASP.NET Core и ограничение на один переход. Прокси должен перезаписывать заголовки клиента; не добавляйте произвольные адреса в список доверенных.

## Проверки

```powershell
dotnet build Guard.slnx
dotnet run --project Guard.IpRules.Tests/Guard.IpRules.Tests.csproj --no-build
dotnet run --project Guard.IpRules.Tests/Guard.IpRules.Tests.csproj --no-build -- --postgres Guard/appsettings.json
```

Тестовый проект — исполняемый набор проверок без отдельного test framework; запускайте его через `dotnet run`, а не `dotnet test`. Ошибка проверки завершает процесс с ненулевым кодом.

Режим `--postgres` читает строку подключения из указанного файла без вывода секретов. Он допускает только localhost, создаёт отдельную БД `guard_ip_test_<uuid>`, применяет модель через `EnsureCreated` и удаляет только эту БД в `finally`. Учётной записи нужны права создания БД. Рабочие базы и их данные не изменяются. Проверяются серверная валидация, права, назначения, статусы, IPv6/CIDR, конкурентные дубликаты и отказ выдачи cookie.

Перед развёртыванием назначьте IP всем обычным пользователям, которым нужен доступ. Проверьте вход Root и корректность определения IP за фактическим прокси. Изменение схемы БД для этой доработки не требуется.
