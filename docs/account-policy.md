# Политика паролей и учётных записей

## Управление

Root открывает `/account-policy` через меню «Политика паролей и аккаунтов».
Только Root сохраняет настройки; сервер повторно проверяет его доступ.
Версия настроек предотвращает перезапись изменений другой сессии.

Настройки общие для приложения: смена пароля через N дней, блокировка за
неактивность через M дней (кроме Root), минимальная длина, число различных
символов, требования цифр, обоих регистров латинских букв и специальных символов.
Периоды — от 1 до 3650 дней, длина — от 6 до 100 символов.
По умолчанию периоды выключены, N/M — 90 дней, начальная сложность соответствует
прежним требованиям Identity. Политика проверяется при создании, смене, задании
и сбросе пароля. Текущий пароль повторно использовать нельзя; история не хранится.

В `/users` право `Users.Manage` позволяет блокировать, разблокировать и сбрасывать
пароли доступных пользователей собственного подразделения и потомков. Root
имеет полную область. Администратор не изменяет Root, вручную блокировать Root нельзя.
Сброс заблокированного аккаунта запрещён до разблокировки.

Администратор задаёт временный пароль с подтверждением. Старые сессии отзываются;
при следующем входе обязательна самостоятельная смена временного пароля, даже
если период выключен. Обязательная смена после входа открывается на
`/Account/Manage/ChangePassword` с `AccountLayout`. Без локального пароля
используется `/Account/Manage/SetPassword` с тем же layout.
Добровольная смена через меню «Сменить пароль» открывается в диалоге кабинета.
Ошибки остаются в диалоге. HTTP-обработчик проверяет текущий пароль,
подтверждение, политику и antiforgery-токен; после успеха обновляет cookie,
а браузер перезагружает текущую страницу для обновления Blazor-сессии.

## Неверные попытки входа

Root на `/account-policy` задаёт Z неверных попыток (1–100) и длительность
временной блокировки (1–10080 минут). Начальные значения — **5 попыток и 15 минут**.
Ограничение применяется к входу с паролем всех пользователей, включая Root;
отдельного исключения для Root здесь нет.

Счётчик и срок хранятся в стандартных полях Identity `AccessFailedCount` и
`LockoutEnd`. Любая парольная точка входа учитывает ошибки, даже если прежний
вызывающий код передаёт `lockoutOnFailure: false`. Для старых аккаунтов с
отключённым LockoutEnabled менеджер включает учёт перед проверкой пароля.
Неизвестный адрес аккаунта и отказ IP-доступа не увеличивают счётчик другой записи.

На Z-й ошибке Identity устанавливает срок блокировки в UTC и сбрасывает счётчик.
До окончания срока парольный вход запрещён, повторные попытки срок не продлевают.
По истечении срока вход разрешается автоматически; успешный вход сбрасывает
предыдущие ошибки. При включённой двухфакторной проверке сброс выполняется
по стандартным правилам Identity при завершении входа.

Изменение Z и длительности применяется при следующей неверной попытке,
не пересчитывая уже установленный LockoutEnd. Постоянные блокировки с причиной
Administrator/Inactivity не снимаются по таймеру. Разблокировка через существующий
экран пользователей по-прежнему сбрасывает счётчик и требует серверных полномочий.
Событие достижения порога записывается через `IAuditService` без пароля.

## Сроки и активность

Даты хранятся в UTC. N отсчитывается от последней успешной смены пароля.
Без этой даты — от более позднего из создания аккаунта и включения политики.
Изменение N пересчитывает срок; усиление сложности не инвалидирует старый пароль.

Активность — успешный вход, авторизованная HTTP-навигация и действия в видимой
вкладке (нажатия указателя/клавиатуры). Соединение, переподключение, таймеры,
фоновые обновления и ответы JS сами по себе срок не продлевают. Браузер сообщает
о действиях не чаще раза в минуту, дата в БД обновляется не чаще раза за пять
минут; её точность — до пяти минут. Отказ JS не продлевает срок.

M отсчитывается от последней записанной активности, при её отсутствии — от
создания аккаунта. Более поздние включение политики и разблокировка начинают
новый период. Повторное включение предоставляет новый период M. Выключение
политики не снимает уже установленную блокировку.

Фоновая проверка выполняется раз в минуту. Вход, HTTP-запросы и действия Blazor
проверяются дополнительно. После истечения N доступны только смена/задание
пароля и выход. Cookie и прикладные операции проверяют актуальный SecurityStamp;
блокировка и административный сброс изменяют его. Уведомления обслуживают
сессии одного процесса; в других экземплярах работают серверные проверки и
периодическая перепроверка сессии раз в минуту.

События блокировки, разблокировки, изменения политики и пароля проходят через
`IAuditService`. Пароли в аудит не передаются.

## Миграция и проверки

Миграция `20261008100218_AddAccountPolicy` добавляет таблицу политики, поля
аккаунта и индекс активности. Дата создания существующих аккаунтов заполняется
моментом миграции, неизвестная дата пароля остаётся пустой. Обновление рабочей
БД выполняется отдельно в предназначенной для развёртывания среде.

Миграция `20261009090000_AddLoginFailurePolicy` добавляет в существующую политику
Z=5, длительность=15 минут и ограничение диапазонов. Остальные настройки политики
сохраняются. Новая миграция в рамках этой задачи не применялась; при обычном запуске
приложения DatabaseInitializer выполняет MigrateAsync, поэтому перед запуском
нужно проверить предназначенную для развёртывания БД.

Для блокировки входа добавлены проверки с памятью вместо БД: граница Z, срок,
повторный вход, сброс счётчика, сохранение ручной блокировки, неизвестный аккаунт,
IP-допуск, ошибка IdentityResult, отсутствие cookie при отказе, запрет изменения
политики обычным пользователем, неизменность общих IdentityOptions и SQL миграции.
PostgreSQL-набор дополнен сохранением параметров Root, применением миграции к
существующей политике и проверкой сохранённого LockoutEnd. Эти интеграционные
проверки и браузерная проверка новых полей не запускались: изолированной БД нет.

```powershell
dotnet build Guard.slnx --no-restore
dotnet run --project Guard.IpRules.Tests/Guard.IpRules.Tests.csproj --no-build
dotnet run --project Guard.IpRules.Tests/Guard.IpRules.Tests.csproj --no-build -- --postgres Guard/appsettings.json
dotnet run --project Guard.IpRules.Tests/Guard.IpRules.Tests.csproj --no-build -- --browser Guard/appsettings.json
```

Режимы PostgreSQL и браузера допускают только localhost и создают собственную
временную БД. Проверка миграции воссоздаёт предыдущую схему только в этой БД и
применяет новую миграцию. Браузерный режим запускает приложение на `127.0.0.1:5079`
в Development: обе строки подключения ведут в временную БД, аудит — на loopback.
Учётные данные синтетического Root печатаются при готовности сервера. Enter
останавливает процесс и удаляет только созданную временную БД. Диагностика:
`Guard/obj/account-policy-browser.log`.

Перед ручной проверкой браузерный режим автоматически выполняет 15 HTTP-проверок
самостоятельной смены: валидация и защита от CSRF, обновление cookie и отзыв
предыдущей сессии, выход при обязательной смене пароля. Эти проверки используют только синтетический аккаунт.

В браузере проверять открытие и сохранение политики, блокировку/разблокировку,
отмену/успех сброса, обязательную смену, фильтры, сортировку и несколько сессий.
При ручной проверке ввод новых паролей выполняет пользователь; серверные
сценарии автоматизированы интеграционными проверками.
