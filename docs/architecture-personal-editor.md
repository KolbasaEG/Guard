# DTO редактора сотрудников

Формы `Personals/Add`, `Edit` и `Components/PersonalFields` используют `PersonalEditorDto` и `PersonalSubdivisionOptionDto` через узкий `IPersonalEditorService`. Они больше не получают `Personal`, `Subdivision` и граф связей. Каскадный `UserContext` пока остаётся переходной зависимостью; его замена — отдельная поставка.

`GetEditorAsync` материализует SQL-проекцию скалярных редактируемых полей, Id, Version и Status через `IReadRepository<Personal>`. IP, пользователи, значения справочников и поля аудита не загружаются. Требуются Personals.Write и Personals.ReadDetails; репозиторий сохраняет проверку области и архива. Сервер отказывает для неактивной записи. После чтения повторно проверяются permissions, исполнитель и доступ к подразделению. Эти повторные проверки не являются атомарным снимком прав и данных; согласование доверенного исполнителя остаётся задачей этапа 2.

Варианты подразделений проецируются в Id/Name, ограничиваются серверной областью и статусами Inserted/Modified. Сортировка — Name, Id. После материализации проверяются permissions и доступность возвращённых подразделений. Root получает все активные подразделения. Зависимость Personals.Write → Personals.ReadDetails → Personals.Read сохраняется.

Запись остаётся через CreatePersonalDto/EditPersonalDto и существующие операции с проверкой версии, области, ссылок, статусов и локального режима управления. Старые методы IPersonalService сохранены совместимыми. Scrutor регистрирует PersonalService через AsImplementedInterfaces, включая новый интерфейс; отдельная дублирующая регистрация не нужна.

После сохранения назначений IP редактор заново получает DTO и сравнивает исходный снимок PersonalFieldsDto с серверными полями. Только при совпадении принимает новую Version и Status, сохраняя незаписанный ввод. Чужая правка полей вызывает конфликт; сведения полной карточки не используются для обхода ReadDetails.

Проверки: сборка Guard.slnx; runner с `--postgres Guard/appsettings.json` — 1502 проверки на отдельной автоматически создаваемой и удаляемой БД. Включены серверное чтение DTO, область, отсутствие прав и их зависимостей, запрет редактирования заблокированного сотрудника, Root, отзыв доступа при чтении, отмена, сохранение введённых полей и конфликт после IP. Обе формы также проверены через HtmlRenderer с настоящими компонентами Library/Radzen. Интерактивный браузерный сценарий этой поставки отдельно не выполнялся. Подключения, схема и рабочие данные не изменены.

## Контракты списка и просмотра

Список использует IPersonalSearchService (PersonalSearchRequest → PersonalSearchResult) и IPersonalStatusService (существующие команды с Id/Version). Карточка использует только IPersonalDetailsService (Id → PersonalDetailsDto). IPersonalService наследует эти контракты, сохраняя прежние вызовы для существующих потребителей. Scrutor AsImplementedInterfaces регистрирует и унаследованные интерфейсы; это проверяется runner. Число проектов и реализация операций не изменены.

PersonalFilterValidation проверяет независимое дерево без IQueryable, сущностей, EF и Radzen. CaptureFilter сначала копирует условия, затем вызывает эту проверку; неверный фильтр не заменяет применённый. Серверный PersonalQueryFilter.Apply повторяет проверку перед построением выражения, поэтому поиск и экспорт используют те же правила: пять разрешённых текстовых полей, десять операций, глубина до 16 и не более 100 узлов с учётом корня. Пустая группа и поведение отсутствующего подразделения сохранены. Проверки включают граничные размеры дерева, запрещённые поля/операции, null-узлы и все операции по Subdivision.Name.

Эта поставка не меняет права, серверную область, SQL-проекции, пагинацию, команды статусов или формат экспортного запроса. Повторная проверка полномочий и единый доверенный исполнитель для всех операций остаются работой этапа 2. Интерактивный браузерный сценарий списка отдельно не выполнялся; жизненный цикл загрузки и рендер карточки проверяются runner.

Следующий шаг — модель отображения пользователя и доверенный исполнитель операции по плану перехода.

Проверки этой поставки: сборка — 0 ошибок, 36 существующих предупреждений; полный runner с PostgreSQL — 1525 проверок, временная БД удалена штатным завершением. Также выполнен git diff --check.
