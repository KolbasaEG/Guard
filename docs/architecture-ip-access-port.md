# IP-допуск: правило и порт чтения

Дата: 17 октября 2026 года. База: `a3bcfb8`, ветка `codex/architecture-ip-search`.

IpAccessService больше не зависит от EF и ApplicationDbContext. Прикладная последовательность получает минимальные данные через IIpAccessReader и сопоставляет адрес через независимый IpAddressRule. Последний сохраняет исторический namespace Guard.Core.Identity, но использует только BCL; при разделении его нельзя переносить вместе с ASP.NET Identity по одному имени каталога.

## Разделение ответственности

- `IIpAccessReader.FindSubjectAsync` возвращает null для неизвестного пользователя либо IpAccessSubject: признак роли Root, ID сотрудника и его статус. Признак Root вычисляется по назначенной роли с NormalizedName ROOT, а не по cookie или permission claims.
- `GetActiveRulesAsync` получает только строки активных IP, назначенных конкретному сотруднику. IP подразделения без назначения сотруднику не дают доступ. Это внутренний порт хранения для проверки допуска до входа, а не API страницы; он не требует уже существующей текущей сессии.
- `IpAccessReader` реализует эти возможности через EF. Каждый вызов создаёт и освобождает собственный контекст; чтение материализуется до его освобождения. Контекст circuit и отложенные запросы не передаются в Application.
- `IpAccessService` сохраняет порядок отказов и решений: неизвестный пользователь запрещён; Root освобождён от проверки IP; остальные требуют сотрудника в Inserted/Modified, корректного адреса клиента и совпадающего активного назначения. Пустой список запрещает доступ. До проверки статуса/адреса и для Root список IP не загружается.

IIpAccessReader регистрируется явно как scoped в общем производственном AddGuardServices; suffix-сканирование Service его не регистрирует. IpAccessService продолжает регистрироваться прежним способом. Состав Account, middleware, SignInManager и проверка при переподключении не менялись.

В инвентаре теперь 33 независимых интерфейса: прежние 32 сервисных контракта и новый порт чтения. Семь legacy-интерфейсов остаются инфраструктурными. Общая проверка публичных типов включает порт и его DTO.

## Проверки и ограничения

Независимые проверки с подставным портом подтверждают неизвестного пользователя, отсутствие сотрудника/статуса, все статусы и неизвестное значение enum, Root без сотрудника/адреса, пустые/повреждённые правила, mapped IPv4, IPv6 и CIDR. Проверяются отсутствие лишнего чтения IP, передача ID и CancellationToken обоим вызовам, распространение ошибки чтения и отмены обоих этапов.

В PostgreSQL добавлена проверка всех шести статусов сотрудника с повторным вызовом того же сервиса после изменения статуса. Прежние интеграционные сценарии используют новый reader: отсутствие назначения, IP подразделения, активность IP, изменение назначений, Root, вход и серверная авторизация. DI в Development/Production проверяет единственную scoped-регистрацию reader и разрешение обновлённого графа.

Добавлено **46 проверок**. Полный runner с PostgreSQL: **20 364**, код завершения 0; изолированная временная БД удалена. Сборка: 0 ошибок, 25 прежних предупреждений. Рабочие данные/подключения, схема, UI и публичный IIpAccessService не менялись. Приложение и браузер не запускались.

Чтение пользователя, роли и IP, как и прежде, не является атомарным снимком одной транзакции. Между вызовами порт создаёт разные контексты; SQL-проекции и порядок чтений сохранены. Эта поставка не добавляет отзыв уже открытого соединения и не измеряет производительность на полном объёме данных.
