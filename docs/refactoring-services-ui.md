## Новая миграция

`20261008160000_AddEntityVersions` добавляет uuid `Version` сотрудникам, подразделениям, классификаторам и типам органов. Начальное значение существующих записей — Guid.Empty; первая запись через контекст присваивает новую версию. EF использует её как concurrency token.

По отдельному подтверждению пользователя миграция также включает генерацию `OrganTypes.Id` через PostgreSQL identity by default. Существующие Id сохраняются, последовательность устанавливается выше максимального. Начальный seeding использует фиксированные Id 1–3 и после вставки выравнивает последовательность. Новая команда создания типа органа не принимает Id.

Миграция **не применялась**. Перед её применением нужны резервная копия, проверка SQL и прогон на изолированной PostgreSQL-БД. Внешние импорты с явно заданными Id должны поддерживать последовательность; внешние изменения версионируемых строк должны менять Version.

## Что проверить перед слиянием

1. На предназначенной для проверки среде применить миграцию и выполнить интеграционный набор. Существующий harness создаёт собственную временную БД только на localhost; пароль не передавать в аргументе командной строки.
2. В браузере проверить первое открытие списков, фильтр и его очистку, редактирование условий без «Применить», обновление, сортировку, страницы и быстрые повторные загрузки.
3. Проверить статусы и кнопки, действия над ArchivedBlocked и Deleted, конфликт двух открытых форм, отсутствие изменений сотрудников и потомков при изменении статуса подразделения.
4. Проверить «Только свои / Свои и подчинённые», включая Root. Если у пользователя нет подразделения, оба режима пустые. Проверить обновление области после изменения доступа и подразделения.
5. Проверить часовые пояса двух браузеров и фильтры дней на границе UTC; карточку сотрудника, информацию об аудите и детали журнала.
6. Проверить отмену, закрытие и повторную отправку диалогов; уведомления об успехе должны появляться только после сохранения.
7. Проверить автообновление журнала, частое переключение режима и закрытие страницы; сохранение настроек логирования, ошибку записи файла и завершение приложения.

## Существенные ограничения

- Приложение не запускалось: запуск создаёт БД и в Development выполняет seeding. Подключения, секреты и существующие данные для проверки не менялись.
- Полная история старых времён не восстанавливается. Раньше `logs.timestamp` получал локальное время без часового пояса; новые события записываются как UTC. Для достоверного отображения старых записей нужен отдельный согласованный перевод с известным исходным часовым поясом; в текущем просмотре они интерпретируются как UTC.
- Таблица логов не имеет уникального ключа. Для событий с одинаковым Timestamp нельзя гарантировать стабильную пагинацию; добавление ключа и миграция БД логов остаются отдельной задачей.
- Повтор после ошибки записи означает новый вызов сервиса с новым контекстом. Автоматические повторы транзакций на прежнем ChangeTracker не выполняются; настройка retry для нового контекста требует отдельной политики идемпотентности.
- Version защищает изменения отдельных записей и затронутых потомков. Координация всех вариантов конкурентного перестроения дерева и исправление прежних алгоритмов относятся к отдельно выделенным пунктам про иерархию.
- Изменённый пользователем `Guard/wwwroot/images/backg.jpg` не относится к этому рефакторингу и исключён из коммита.
