## 1. Утверждённое направление

Сохранить слоистый монолит с одним развёртываемым веб-приложением и общей основной PostgreSQL-БД. Выделить четыре основных проекта и два тестовых. Внутри проектов организовать код по функциональным областям, установить разрешённые зависимости и проверять их автоматически.

Условия пользователя: один разработчик, один сервер. Для интеграционных проверок разрешено создавать отдельную временную БД через текущее подключение. Это не разрешение изменять рабочую БД или применять к ней миграции.

| Проект | Содержимое | Разрешённые зависимости Guard |
| --- | --- | --- |
| `Guard.Domain` | Предметные сущности, значения, статусы и независимые правила | Нет |
| `Guard.Application` | Прикладные операции, DTO, параметры поиска, проверки доступа, интерфейсы хранилищ и интеграций | Domain |
| `Guard.Infrastructure` | EF Core, PostgreSQL, Identity-хранилища, реализации запросов и записи, внешний API, файлы, Serilog | Application, Domain |
| `Guard.Web` | Blazor, Radzen, страницы, HTTP endpoints, middleware, circuit, адаптер текущего пользователя, сборка DI | Application; Infrastructure для сборки приложения; Domain допустим для типов фильтра на переходном этапе |
| `Guard.UnitTests` | Независимые правила и операции с тестовыми реализациями интерфейсов | Domain, Application |
| `Guard.IntegrationTests` | PostgreSQL, EF-модель и миграции, Identity, HTTP, рендеринг и браузер | Необходимые основные проекты |

Конечный пользовательский поток: компонент → прикладная операция → интерфейс хранилища/интеграции → Infrastructure. Для чтения Infrastructure выполняет SQL-проекцию в DTO; для записи одна операция владеет контекстом и транзакцией. Web не получает `IQueryable`, `DbContext`, репозитории и модели Identity из прикладных контрактов.

Из обязательного объёма исключены микросервисы, отдельный worker, брокер сообщений, отдельная БД чтения, смена UI, введение MediatR, универсального CRUD-фреймворка или обязательного нового тестового фреймворка. Решение остаётся на .NET 10. Новые библиотеки добавляются только при доказанной необходимости.

## 2. Что нужно сохранить

- Маршруты, русские сообщения, оформление и поведение Library, диалоги, темы и локализацию.
- Наборы permissions и их числовые/строковые значения; права только из назначенных ролей; полный доступ Root и исключение Root из IP-проверки.
- Проверку области подразделений в прикладной операции. Некорректная или отсутствующая область обычного пользователя остаётся пустой.
- Различие полномочий на список сотрудников, детали, архив и экспорт; отсутствие лишних персональных данных в DTO.
- Проверку IP перед выдачей cookie и при новом соединении; существующие правила отзыва доступа без добавления периодического отзыва соединений.
- Значения `Status`, разрешённые переходы, ограничения редактирования, UTC, версии и конфликты конкурирующих изменений.
- Уникальность IP, привязок учётных записей, внешних идентификаторов, внешние ключи и поведение удаления.
- Атомарность перемещения дерева, синхронизации и операций Identity; назначение и порядок advisory locks.
- Режим ручного/API-управления. Учётные записи и их привязки остаются локально управляемыми; ограничения синхронизируемого справочника сохраняются.
- Аудит автора/времени, отдельные события безопасности и технические логи.
- Совместимость архива экспортов, JSON заданий, Data Protection, cookie и конфигурации.

Архитектурный перенос не должен скрыто изменять бизнес-поведение. Найденные независимые ошибки оформляются отдельно; изменение поведения с новыми правилами требует отдельного согласования.

## 3. Карта размещения кода

Не создавать отдельные сборки на каждую сущность. Существующие `Abstarct` и `Concrates` не переименовывать попутно.

| Текущая область | Целевое размещение и необходимые изменения |

| Сервисы справочника | Проверки, последовательность действий и контракты — Application; SQL-запросы, загрузка для записи и сохранение — Infrastructure |

| Hosted services | Тонкие BackgroundService-обёртки — Web; операции — Application, реализации I/O — Infrastructure |

## 4. Этапы и зависимости

Последовательность: 0 → 1 → 2 → 3 → 4 → 5 → 6 → 7. Один разработчик выполняет этапы последовательно. Каждый этап завершается собираемым результатом, проверками и отдельной пользовательской проверкой перед слиянием. Реализацию вести в отдельных ветках `codex/<этап>` от принятой main.

Ориентир — 10–14 небольших изменений для проверки: этапы поиска и прикладных операций делятся по областям. Это порядок поставки, а не обещание календарного срока. После этапа 0 уточняется объём по реальному числу вызовов и тестов.

### Этап 0. Зафиксировать исходное поведение и правила перехода

Действия:

1. Составить перечень прикладных операций, мест использования `IQueryable`, EF в UI, Identity-моделей в DTO, прямого получения сервисов из DI и публичных legacy-методов.
2. Зафиксировать карту permissions/области/статусов для каждой области; использовать код и актуальные тесты, проверить расхождения старых документов с текущей моделью доступа.
3. Сохранить перечень EF-миграций, FK, индексов, concurrency tokens, таблиц связей и используемых блокировок.
4. Зафиксировать базовый результат сборки и тестов, диагностические предупреждения, маршруты и способы развёртывания. Измерить на согласованных объёмах типовые списки и экспорт, не записывая персональные данные в отчёт.
5. Подготовить реестр SQL/пользовательских сценариев для сравнения до и после переноса.
6. Согласованно обновить `AGENTS.md`, `docs/frontend-subagent.md` и документацию Library: текущие требования выполнять проекцию в UI и передавать query-делегат заменить на вызов поиска, сохранив порядок обработки, RadzenDataFilter и пользовательское поведение.

Результат: воспроизводимая база сравнения и правила, которые не противоречат целевой архитектуре. Обновление инструкций входит в утверждаемый план; текущий документ сам по себе их не изменяет.

Критерий готовности: известен объём переноса, перечислены непроверенные сценарии, новые тесты покрывают существенные пробелы в доступе/транзакциях, а не повторяют код.

### Этап 1. Отделить UI от построения запросов

Account приведён к согласованному объёму: локальный вход, выход и смена своего пароля. [Контракты и закрытие маршрутов](architecture-account-boundary.md): UI использует ILocalAccountService и IOwnPasswordService; ненужные шаблонные страницы, endpoints, JS и Manage-навигация удалены. Существующая 2FA запрещает новый вход с сообщением администратору, её данные сохраняются. Следующая поставка — ревизия legacy-контрактов и их потребителей перед завершением этапа 1. Более ранние упоминания Account ниже отражают историю перехода.

Выполнять внутри существующего проекта до физического переноса, небольшими изменениями: IP → подразделения/справочники → пользователи/роли → журналы. Сотрудников использовать как исходный пример SearchAsync и проверить полноту его контракта.

1. Для каждой области ввести явный запрос поиска, результат `Items + Count`, DTO списка/просмотра и ограниченные параметры сортировки.
2. Преобразовывать Radzen-фильтр в независимое дерево условий в Web. Проверять поля, операции, типы, глубину и размер повторно на сервере; не принимать произвольную строку Dynamic LINQ от UI.
3. RadzenDataFilter на переходном этапе может использовать предметную сущность как описание полей. Он не выполняет запрос к БД. Для Identity и технических моделей использовать специальные модели полей в Web, чтобы не протащить Infrastructure в страницы.
4. Сохранить последовательность: серверный доступ → статус → выбранная иерархия → применённый фильтр → Count → стабильная сортировка → пагинация → SQL-проекция DTO → материализация.
5. Перенести LINQ/EF из code-behind в реализацию поиска. Убрать зависимость от делегатов с IQueryable из публичных интерфейсов по мере переноса всех потребителей.
6. Разделить `ExportFilters.Capture` и исполнение условий. В Web остаётся преобразование Radzen; в серверном запросе — независимое построение выражения по разрешённым полям. Сохранить смысл старых сериализованных экспортных фильтров.
7. Перевести формы на явные DTO чтения/записи и справочные DTO выбора; убрать возврат сущностей Identity и `IdentityResult` в прикладных контрактах. Ошибки Identity переводить в ограниченный результат операции без потери проверки каждого обязательного шага.

Проверки: первая загрузка, отмена/устаревшие ответы, фильтр до/после «Применить», очистка, сортировка, пагинация, статусы, иерархия, Root/обычный пользователь, недопустимые поля, совпадение списка и экспорта.

Критерий готовности: прикладные интерфейсы UI не содержат EF, IQueryable, Radzen и Identity-модели; страницы не выполняют EF-запросы. Разрешённые типы Domain в фильтрах не содержат инфраструктурных зависимостей.

[Модель отображения текущего пользователя отделена от серверных данных автора](architecture-user-display.md): UI получает DTO без графа Identity, права и область вычисляются отдельно. Контекст исполнителя на каждую операцию остаётся этапом 2. [Синхронизация переведена на DTO настроек и запусков](architecture-synchronization-dtos.md), пароль исключён из контракта чтения. [Граница экспорта разделена](architecture-export-boundary.md): Capture остаётся в Web, архив проверяет фильтр без IQueryable, настройки хранения возвращаются как DTO. Исправлено применение вложенных групп и календарного дня. [Политика учётных записей разделена на публичные требования, административные DTO/команду и узкие серверные снимки](architecture-account-policy-dtos.md); даты включения назначаются только сервером. [Настройка логирования переведена на независимый уровень и DTO](architecture-log-configuration.md); UI читает активную конфигурацию через сервис. Следующая поставка — реестр сценариев Account и их адаптеры. При браузерной проверке обнаружена прежняя отсутствующая регистрация IEmailSender для /Account/Register; учесть в реестре Account. Детальный порядок и условия перехода к сборкам приведены в отчёте; физическое разделение проектов пока не начинать.

### Этап 2. Отделить текущую сессию и согласовать операции записи

1. Ввести независимый контракт контекста текущего исполнителя. Web получает идентификатор из доверенного HTTP/Blazor principal; прикладной код не принимает идентификатор исполнителя из формы.
2. Разделить проверку текущей сессии и вычисление актуальных permissions/области. Сохранить security stamp, блокировку, срок пароля и правила Root. Не считать данные principal самостоятельным источником permissions.
3. Для фоновых заданий использовать сохранённого автора или явного системного исполнителя по существующим правилам, повторно проверять доступ на критических этапах. Фоновый scope не должен зависеть от AuthenticationStateProvider.
4. Для каждой независимой записи обеспечить один контекст на операцию; репозитории и транзакция используют его же. Сохранить фабрику UoW как основу, убрать неоднозначное смешение scoped-контекста circuit и контекста операции.
5. В Identity-операциях все обязательные изменения выполняются через менеджеры в одном scope и одной транзакции. Ошибка любого IdentityResult отменяет весь составной результат.
6. Сохранить аудит для фабричных контекстов, отмену, конфликт версий, откат и действующий порядок блокировок. Уведомления отправлять после успешного commit.
7. Выделить интерфейсы хранилищ по требуемым возможностям. Не строить оболочку для каждого метода EF. Специальные атомарные операции дерева, Identity и синхронизации допустимо реализовать в Infrastructure за узким интерфейсом.
8. Удалять прикладные проверки из generic ReadRepository только одновременно с появлением эквивалентной защиты во всех новых путях. Не оставлять временное окно с незащищённым чтением.

Проверки: отказ прямому вызову операции вне области, устаревшая версия, конкурирующая запись, ошибка обязательного Identity-шага, откат после SaveChanges, автор/UTC, работа задания без HTTP, режим API и локальные операции учётных записей.

Критерий готовности: операции отделены от транспорта, каждая составная запись имеет ясного владельца контекста/транзакции; публичный прикладной контракт не требует EF или ASP.NET Core.

### Этап 3. Выделить Guard.Domain

1. Создать библиотеку net10.0 и перенести только независимые сущности/правила. Сохранить существующие namespace, имена типов и значения enum там, где это позволяет избежать лишнего изменения EF-метаданных и сериализации.
2. Устранить обратную ссылку Personal → ApplicationUser. Настроить одностороннюю связь Identity в Infrastructure/будущей Infrastructure с сохранением уникального FK и SetNull.
3. Распределить остальные типы по карте раздела 3. Не превращать перенос в массовую инкапсуляцию всех свойств и переписывание доменной модели.
4. Проверить отсутствие ссылок Domain на Application, EF, Identity, Radzen, HTTP и конфигурацию сервера.
5. Сравнить реляционную модель до/после: таблицы, столбцы, ключи, FK, индексы, default/computed значения и concurrency tokens. Удаление CLR-навигации само по себе не должно удалять столбец или связь.

Критерий готовности: Domain собирается отдельно, приложение и все проверки проходят, непредусмотренного DDL нет. Изменение snapshot при необходимости отражает только актуальную модель; старые миграции не переписываются.

### Этап 4. Выделить Guard.Application и Guard.Infrastructure

Это связанный перенос двух сборок после подготовки контрактов. Не оставлять промежуточные коммиты с циклическими ссылками; разбивать по функциональным операциям там, где каждый результат собирается.

1. Создать Application с зависимостью только от Domain и необходимых общих abstractions, например ILogger. Перенести DTO, входную проверку, независимую оркестрацию, контракты permissions/области/хранилищ/внешнего API.
2. Создать Infrastructure, перенести EF, контексты, репозитории, UoW, Identity-модели и адаптеры, HTTP, OpenXml, файловое хранилище, криптографию и логирование.
3. Для каждой операции проверить направление зависимости: Application не знает ApplicationDbContext, UserManager, Npgsql, IWebHostEnvironment, Radzen или Serilog. Infrastructure реализует интерфейсы Application; если операция целиком осталась в Infrastructure, отдельно выделить её независимые проверки и последовательность, не создавать пустой посредник ради слоя.
4. Применение снимка API сохранить атомарным; PostgreSQL-специфичные загрузку/блокировки/запись оставить за интерфейсом Infrastructure. Правила валидности снимка и состояний отделить от SQL.
5. Сохранить один основной ApplicationDbContext и отдельный LogsDbContext. В рамках перехода не делить основную БД по модулям и не вводить межконтекстные транзакции.
6. Перенести миграции и design-time factory вместе с контекстом. Явно проверить migrations assembly, обнаружение конфигураций и Snapshot; не менять migration IDs и историю применённых миграций.
7. Заменить сканирование только `typeof(Program).Assembly` на явные методы регистрации по слоям/marker types. Typed HTTP client регистрировать однозначно; проверить scope, отсутствие дубликатов и корректное освобождение singleton-ресурсов.
8. Разнести пакеты по фактическим потребителям: Radzen — Web, EF/Npgsql/OpenXml/Serilog/SSH.NET при наличии использования — Infrastructure. Не выполнять попутно массовое обновление пакетов.

Проверки: сборка каждого проекта, DI с валидацией scopes и разрешением ключевых сервисов, фактические PostgreSQL-сценарии, техническое логирование, аудит, HTTP-клиент с его настройками, отмена и восстановление фоновых заданий.

Критерий готовности: четыре слоя не имеют циклов; Application и Domain не зависят от инфраструктуры; миграции обнаруживаются, SQL-модель и операции совместимы с исходной базой.

### Этап 5. Завершить Guard.Web и безопасный запуск

1. Существующий веб-проект преобразовать в Guard.Web; перенос папки и имени csproj делать отдельным механическим изменением после стабилизации зависимостей. Namespace и AssemblyName не переименовывать автоматически.
2. Обновить slnx, ссылки тестов, маршрутизацию компонентов, static assets, isolated CSS/JS, launch profiles, инструкции запуска/публикации и фактические серверные команды.
3. Сохранить действующие имена cookie, схемы аутентификации, UserSecretsId и эффективные настройки Data Protection, включая discriminator, key directory и сертификат. Смена каталога content root не должна сделать старые cookie/архивы нечитаемыми.
4. Проверить относительные пути архива, логов, файлов конфигурации и сохранённой темы. При необходимости сохранить прежний рабочий каталог либо явно сопоставить пути без перемещения рабочих данных в коде запуска.
5. Оставить hosted services в том же веб-процессе. Каждый проход создаёт собственный scope и вызывает прикладную операцию.
6. Убрать создание физических БД из обычного production-запуска. Предоставить явный режим подготовки/обновления БД в том же host либо документированный deployment-шаг. Его запуск против рабочей БД остаётся отдельным разрешением; не добавлять седьмой обязательный проект только ради этой команды.
7. Ограничить development seeding явным режимом подготовки тестовой/локальной среды. Обычный старт должен сообщать о неподготовленной БД без скрытого создания или изменения схемы.

Проверки: publish и запуск опубликованного результата на изолированной среде, вход/выход/переподключение, IP за прокси, страницы/стили/JS, старый экспорт и новые выгрузки, перезапуск, прежние пути и конфигурация.

Критерий готовности: приложение публикуется одним комплектом, работает на одном сервере, обычный запуск не требует права CREATE DATABASE. Доступность функций и условия безопасности сохранены.

### Этап 6. Разделить тесты и закрепить архитектурные ограничения

1. Разнести существующие проверки по UnitTests и IntegrationTests. На время перехода сохранить рабочий старый runner; переносить проверки, не удаляя их до появления эквивалентного запуска.
2. Сохранить исполняемый harness и ненулевой exit code при ошибке. Переход на отдельный test framework не является условием завершения.
3. Отдельно запускать независимые проверки, PostgreSQL и браузер. Рендеринг, host и файловые ACL относятся к IntegrationTests даже при отсутствии реальной БД.
4. Сохранить защиту временной БД: разрешённый host, фиксированный префикс и случайный идентификатор, изоляция всех контекстов, удаление только созданной данным запуском БД. При ошибке удаления сообщать имя тестовой БД без credentials, не расширять очистку.
5. Добавить самостоятельную проверку цепочки миграций: текущий harness использует EnsureCreated и сам по себе не доказывает применимость всех миграций. На отдельной временной БД проверить создание миграциями, обновление с согласованной предыдущей версии, состояние history и итоговую модель.
6. Проверять граф ProjectReference и запрет зависимостей Domain/Application от EF, Identity, Radzen и Web. Отдельно проверять отсутствие EF-запросов в компонентах; разрешённые framework-зависимости Web для Identity UI не путать с утечкой Identity в Application.
7. Добавить один воспроизводимый сценарий проверки для разработчика: restore при необходимости → build → unit → интеграции на временной PostgreSQL → browser. Автоматизацию выполнять средствами имеющейся среды; отдельный CI-сервис не обязателен.

Критерий готовности: шесть проектов в slnx; нет потерянных сценариев старого runner; обязательные наборы завершаются успешно, запреты зависимостей проверяются автоматически.

### Этап 7. Приёмка и развёртывание

1. Выполнить полную матрицу ниже на принятом результате, подготовить publish-артефакт и список изменений конфигурации/команд.
2. Получить отдельную проверку и подтверждение слияния актуального результата в main. Утверждение этого плана не заменяет подтверждение слияния реализации.
3. Перед рабочим развёртыванием подготовить резервную копию БД, архива и ключей Data Protection по принятой процедуре; подтвердить возможность восстановления.
4. Согласовать остановку на время замены приложения: при одном сервере не усложнять переход параллельным запуском разных версий и конкурирующих worker.
5. После отдельного разрешения на развёртывание проверить вход Root и обычного пользователя, область доступа, ключевые списки, экспорт, расписание синхронизации, аудит и журнал.

Критерий готовности: пользователь принял поведение, проверки сохранены, известна процедура отката, приложение эксплуатируется одним комплектом. Push и публикация не входят в разрешение подготовить план.

## 5. Обязательная матрица проверки

| Область | Сценарии |
| --- | --- |
| Доступ | Root; ограниченный оператор; отсутствие permissions; пустой/некорректный путь; запись вне области; смена роли/подразделения; актуальный stamp |
| IP/Identity | IPv4/IPv6/CIDR; пустые назначения; заблокированные IP/сотрудник/учётная запись; прокси; новый вход/подключение; проверка каждого IdentityResult |
| Чтение | Нет доступа к деталям при наличии списка; архив/экспорт проверяются отдельно; недопустимое поле/операция; SQL-проекция; стабильная пагинация; отмена |
| Формы | Создание/чтение/изменение; ReadOnly; двойное сохранение; закрытие; конфликт версий; уведомление только после успешного результата |
| Транзакции | Ошибка посередине; откат после промежуточного SaveChanges; отдельные контексты параллельных операций; аудит автора и времени |
| Дерево | Перемещение ветви; запрет себя/потомка; пути всех потомков; пустой префикс; конкурентные изменения; индекс Path |
| Синхронизация | Полный/дельта-снимок; режим API; изменения settings/version; прерывание/повтор; locks; локальное редактирование учётных записей; целостность справочника |
| Экспорт | Доступ при создании/обработке/выдаче; отзыв прав; старое сериализованное задание; архив до переноса; шифрование; отмена; нехватка места; retention |
| Модель БД | Таблицы/колонки/FK/индексы/defaults/concurrency; старые migration IDs; миграции на временной БД; отсутствие лишнего DDL |
| Развёртывание | Publish; маршруты; CSS/JS; ключи/cookie; пути; корректный shutdown; обычный запуск без создания БД; подготовка БД явным режимом |

После каждого существенного изменения запускать затронутые проверки. Полную матрицу выполнять на границах переноса сборок и перед финальной приёмкой. Не повторять весь набор без изменения кода или новой причины.

## 6. Контроль рисков и откат

| Риск | Предотвращение / откат |
| --- | --- |
| Пропуск проверки доступа при смене репозитория | Перенос по операции, негативные серверные тесты до удаления старой защиты |
| Цикл Domain ↔ Identity либо Application ↔ Infrastructure | Удаление обратной навигации, интерфейсы в Application, проверка графа ссылок |
| Непредусмотренное изменение схемы при переносе CLR-типов | Сохранение namespace где возможно, явные mapping, сравнение модели и SQL; остановить этап при разрушительном DDL |
| Потеря миграций/конфигураций после смены сборки | Marker types, migrations assembly, design-time factory, проверка всей цепочки на временной БД |
| Потеря cookie или расшифровки архива | Сохранение discriminator/ключей/purposes/сериализации/путей; проверка существующих артефактов до замены |
| Частичная запись Identity/дерева/снимка | Единый контекст и транзакция, интеграционные проверки отказа, сохранение блокировок |
| Длительный незавершённый перенос | Малые собираемые изменения, временные внутренние адаптеры с перечнем потребителей и удалением на конкретном этапе |
| Недоступность тестовой PostgreSQL или CREATE DATABASE | Продолжить независимые работы, но не считать соответствующий этап принятым до интеграционных проверок; рабочую БД вместо тестовой не использовать |

До слияния откат — возврат к предыдущему проверенному коммиту в ветке без сброса чужих изменений. После слияния — отдельный revert соответствующего этапа. При неизменной схеме откат развёртывания выполняется предыдущим publish-комплектом с прежними конфигурацией и ключами. Если понадобилась реальная миграция данных/схемы, её план восстановления и совместимость версий согласуются отдельно до применения; автоматический Down против рабочей БД не является стандартным откатом.

## 7. Что отложено и когда возвращаться к этому

- `Guard.Worker`: только если измерения покажут влияние экспортов/синхронизации на UI или потребуется независимый перезапуск. Сначала проверить хранение файлов, ключи, checkpoint/retry и доступ; общая БД на этом шаге допустима.
- Несколько серверов: потребуют распределённого уведомления об изменении доступа вместо process-local AccessChangeNotifier, согласованного хранения файлов/ключей и стратегии Blazor-подключений. В текущий объём не входит.
- Микросервисы: пересмотреть при независимых командах/релизах, отчётливом владельце данных и обоснованной необходимости изоляции/масштабирования. Не разделять сотрудников, подразделения и IP-допуск на сетевые сервисы без согласованной модели консистентности.
- Отдельные Contracts/BrowserTests/DbMigrator: выделять только при самостоятельном потребителе или отдельном жизненном цикле. Сейчас обязательны шесть проектов.
