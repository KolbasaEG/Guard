# Модель отображения текущего пользователя

Ветка: `codex/architecture-ip-search`. Продолжение этапа 1 архитектурного перехода.

## Изменение границы

`CurrentUserDisplayDto` заменяет каскадный `UserContext`. Контракт содержит только идентификатор, логин, признак Root для отображения, подписи сотрудника/подразделения и справочные DTO подразделений. Навигаций ApplicationUser, Personal и Subdivision, password/security stamp, набора доступных ID и метода проверки доступа в нём нет.

Layout получает снимок через `ICurrentUserDisplayService`. Меню, шапка, списки и формы IP/сотрудников используют новый тип каскадного параметра. Оболочки форм и поведение списков не менялись. Выбор подразделений для записи по-прежнему загружается прикладными операциями редакторов.

`CurrentUserService` выбирает скалярные поля и справочные DTO непосредственно в SQL без Include и материализации графа Identity. Подразделения ограничены серверной областью и явными активными статусами; порядок стабилен по имени и ID. Результат содержит read-only коллекцию. Перед выдачей повторно проверяются исполнитель, Root, permissions и область. Изменение контекста во время загрузки отвергает результат.

`ICurrentUserService` оставлен отдельным узким контрактом автора существующего аудита. Оба интерфейса получают один scoped-экземпляр через явную регистрацию Program; CurrentUserService исключён из Scrutor. Серверные скаляры автора задаются внутри сервиса после проверки, а не из DTO. Подмена DTO не меняет автора. Защищённые операции продолжают самостоятельно использовать IPermissionService и IDataAccessScopeService.

## Границы результата

Эта поставка устраняет граф сущностей из общей модели UI. Она не завершает этап 2: синхронный аудит ещё использует сохранённые серверные скаляры с HTTP fallback, контекст исполнителя на каждую операцию и время жизни записи предстоит согласовать отдельно. Смена DTO не означает периодический отзыв уже открытого соединения.

Layout по-прежнему получает снимок при инициализации; автоматическая актуализация подписей и справочных вариантов в открытом layout при изменениях вне него не добавлена. Серверные permissions и область пересчитываются независимо от этого снимка.

Схема БД, настройки подключения и рабочие данные не изменяются. Следующий участок этапа 1 — DTO настроек, обзора и истории синхронизации, затем экспорта/настроек и Account.

## Проверка

В AuthorizationTests добавлены интеграционные сценарии Root, собственной области и потомков, отсутствующего подразделения, read-only снимка, независимости автора от замены DTO, отмены, некорректного пути, блокировки и смены области во время загрузки. Запуск — через существующий runner с `--postgres Guard/appsettings.json`, который создаёт и удаляет отдельную временную БД.

Интерактивная браузерная проверка в этой поставке не выполнялась. Требуется проверить подписи шапки/меню и фильтр подразделений IP при входе Root и обычного пользователя.

Результаты: `dotnet build Guard.slnx --no-restore -v quiet` — 0 ошибок, 36 предупреждений; runner с `--postgres Guard/appsettings.json` — 1536 проверок, интеграции PostgreSQL успешны во временной изолированной БД с удалением после завершения. `git diff --check` — без ошибок. Обычное приложение не запускалось.
