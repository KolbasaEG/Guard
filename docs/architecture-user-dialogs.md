# Формы пользователей и граница Identity

Седьмая поставка этапа 1 [плана перехода](architecture-transition-plan.md).

## Контракт

`IUserAdministrationService` содержит чтение редактора/доступных сотрудников и явные операции `CreateFromDtoAsync`, `SaveDetailsAsync`, `ResetPasswordFromDtoAsync`. Формы `Users/Add`, `Edit` и `ResetPassword` используют этот интерфейс: они не передают `ApplicationUser` и не обрабатывают `IdentityResult`. Создание возвращает ID после фиксации; сохранение и сброс завершаются без результата только при успехе, иначе выбрасывают исключение.

Команда создания содержит только имя, email, пароль и обязательный ID сотрудника. Роли, подтверждение email и флаги безопасности отсутствуют. Роли по-прежнему назначаются отдельно через `IRoleAccessService`. Команды с паролем — неизменяемые классы без автоматически генерируемого вывода значений через `ToString`. Изменяемый DTO редактирования копируется до первого ожидания сервиса.

Реализацию предоставляет существующий `SecurityService`; Scrutor регистрирует новый интерфейс через `AsImplementedInterfaces`. Старые методы `ISecurityService` остаются совместимыми для переходных потребителей. Это подготовка границы Application/Infrastructure, а не физическое выделение сборок.

## Доступ и запись

- Сервер проверяет обязательные поля, длину имени/email, формат email и пароль через Identity. Создание формы требует сотрудника; legacy API сохраняет возможность Root создать учётную запись без привязки.
- Сохраняются Users.Manage, серверная область подразделений, активность и уникальность привязки сотрудника, защита Root, запрет изменения заблокированного пользователя, проверка ConcurrencyStamp и сброс SecurityStamp при редактировании.
- Снимок доверенного автора, Root, permissions и подразделений проверяется после ожидания advisory lock и перед commit. Изменение любого из этих значений или отмена приводят к откату. Чтение данных редактора и вариантов выбора также повторно проверяет доступ перед возвратом.
- Identity и его хранилище используют один контекст отдельного DI scope и одну транзакцию. Проверяется каждый обязательный IdentityResult, включая назначение ролей legacy API. ID создаваемого пользователя передаётся вызывающему коду после успешного завершения операции.
- После commit создание отправляет `UserCreated = 32` с доверенным автором и ID назначения. Прежние числовые значения событий сохранены. События редактирования/сброса и уведомление об изменении доступа сохранены.

## Формы

Создание и сброс пароля получили `.razor.cs`. Оболочки Library сохранены; загрузка и сохранение разделены через IsLoading/IsSaving. Во время записи ввод заблокирован, закрытие остаётся доступным. Закрытие отменяет токен, поздний ответ/ошибка игнорируется и не может закрыть следующий диалог. Dispose идемпотентен, пароли очищаются при закрытии/освобождении.

- Сборка решения: 0 ошибок, 38 существующих предупреждений полной сборки.
- Полный runner: 1439 проверок; дополнительно 15 HTTP-проверок собственного пароля/logout. PostgreSQL выполнен в отдельной временной БД. Создание и фактический сброс пароля проверены интеграционно, через браузер не отправлялись.

## Ограничения

Контракт списка и управление ролями/журналами рассматриваются отдельными поставками. Legacy API с сущностями Identity сохраняются до переноса остальных потребителей. Чтение всех доступных сотрудников для dropdown пока сохранено; масштабирование этого выбора на 200 тысяч сотрудников требует отдельного поиска с пагинацией. Массовые замеры в этой поставке не повторялись.

Доставка аудита и уведомлений выполняется после commit существующими сервисами, без durable outbox: транзакция данных не гарантирует доставку внешнего события при аварийной остановке процесса. Изоляция контекста и повторные проверки не заменяют дальнейший аудит всех конкурентных операций этапа 2. Модель БД и миграции не изменены.

Ветка `codex/architecture-ip-search` ожидает проверки пользователя. Слияние и развёртывание не выполнялись; рабочие подключения и данные не изменялись.
