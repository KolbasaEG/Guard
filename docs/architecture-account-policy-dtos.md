# Контракты политики учётных записей

Дата: 16 октября 2026 года. Продолжение этапа 1 в `codex/architecture-ip-search`.

## Контракты и потребители

Полная сущность AccountPolicy больше не входит в прикладные интерфейсы и не
передаётся в UI. Её хранение, EF-конфигурация и правила проверки состояния
пользователя остаются серверными.

| Контракт | Результат / назначение | Доступ |
| --- | --- | --- |
| `IPasswordRequirementsService.GetRequirementsAsync` | `PasswordRequirementsDto`: минимум длины и разных символов, четыре переключателя сложности | Публичное чтение, включая страницы без входа |
| `IAccountPolicyAdministrationService.GetSettingsAsync` | Неизменяемый `AccountPolicySettingsDto` с редактируемыми параметрами, Version и датами включения | Только Root, повторная проверка исполнителя после чтения |
| `IAccountPolicyAdministrationService.SaveAsync` | `SaveAccountPolicyCommand` → подтверждённый `AccountPolicySettingsDto` | Только Root, повторная проверка под advisory lock |
| `IAccountPolicyService.GetLoginPolicyAsync` | Два параметра временной блокировки входа | Серверный адаптер Identity |
| `IAccountPolicyService.GetPasswordLifetimeAsync` | Включение срока пароля, длительность и серверная дата включения | Серверная проекция списка пользователей |
| Остальные методы `IAccountPolicyService` | CheckAsync, RecordActivityAsync, SweepAsync | Прежние серверные проверки жизненного цикла |

Все чтения проецируют нужные поля до материализации. Публичное чтение требований
не получает Version, интервалы блокировки, правила неактивности или служебные даты
и не разрешает IPermissionService. Это сохраняет работу до авторизации и исключает
рекурсию между проверкой сессии, Identity и политикой.

`PolicyPasswordValidator` использует тот же публичный DTO, что подсказка;
`PolicyUserManager` получает параметры блокировки и проверяет их диапазоны.
Остальные ограничения таблицы политики продолжают обеспечиваться существующими
DB constraints. Поиск пользователей использует узкий снимок срока пароля.
Динамические пороги, локальность IdentityOptions, аудит, IP-допуск, cookie и
security stamp не заменялись новыми механизмами.

## Запись и форма

Команда не содержит Id или дат включения. Сервис явно переносит разрешённые поля,
а не использует SetValues входной сущности. Существующие серверная валидация,
транзакция, advisory lock 74162002 и проверка Version сохранены.
Повторная проверка Root также требует совпадения UserId: смена одного Root на
другого во время операции не меняет автора записи незаметно для вызывающего кода.

При первом включении сроков сервер назначает даты UTC, при редактировании уже
включённого правила сохраняет их, при отключении очищает, при повторном включении
начинает новый период. Новая Version и даты возвращаются результатом; входная
команда не изменяется. При отсутствии строки чтение административных настроек
возвращает значения по умолчанию с Guid.Empty, создание выполняется только записью.

Страница использует отдельную изменяемую AccountPolicyForm. Снимок команды
создаётся до await; форма принимает сохранённые значения и новую Version из
результата. Повторная отправка во время сохранения блокируется. После ошибки
загрузки или конфликта версии сохранение недоступно до обновления настроек.
Закрытие отменяет запросы, поздние результаты игнорируются. Общий EditEntity
и существующее расположение элементов сохранены. Подсказка пароля также отменяет
чтение при уничтожении компонента.

AccountPolicyService реализует три интерфейса. В приложении они регистрируются
существующим Scrutor AsImplementedInterfaces со scoped lifetime; дополнительных
пакетов и изменений схемы/подключений нет. Тестовый DI адаптирован к новым контрактам.

- Стенд и интеграции работали с синтетическими данными в изолированных временных

## Ограничения и следующая поставка

В браузере обнаружен прежний дефект `/Account/Register`: страница не создаётся,
так как отсутствует DI-регистрация `IEmailSender<ApplicationUser>`. Отсутствие
регистрации подтверждено в Program.cs до этой поставки. Это не отказ нового
контракта требований: публичная страница восстановления отобразила его успешно.
Регистрация почты, фактическая доступность самостоятельной регистрации и остальных
шаблонных маршрутов требуют решения при переносе Account. Этот сценарий нельзя
помечать как проверенный или автоматически включать через фиктивный отправитель.

Перенос адаптеров Account и полный аудит времени жизни/атомарности не завершены.
Следующая поставка этапа 1 — независимый уровень журналирования и DTO его настроек
вместо Serilog.Events.LogEventLevel в UI. Затем остаются Account и очистка широких
legacy-контрактов перед завершением этапа 2 и выделением проектов.
