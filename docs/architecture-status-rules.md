# Независимые правила переходов статусов

Дата: 17 октября 2026 года. Ветка: `codex/architecture-ip-search`. База: `6a87347`.

## Выполненный участок

`EntityStatusTransitions` и `IpStatusTransitions` перенесены из Infrastructure в Application без изменения содержимого файлов и namespace `Guard.Core.Identity`. Они зависят только от Domain, BCL и прикладного `EntityRuleException`. Domain остаётся без зависимости от Application; тип исключения сохранён.

PersonalService, SubdivisionService и IpAddressService продолжают вызывать те же правила. UI сотрудников и подразделений получает доступность действий из того же класса. Проверки permissions/области, блокировки, версия, аудит, контекст, присвоение статуса и commit остаются у существующей операции Infrastructure. Правило перехода само по себе не разрешает доступ к записи.

Сохранены разные существующие политики: EntityStatusTransitions требует Root для восстановления Deleted; IpStatusTransitions принимает строковую операцию и не получает флаг Root. Их унификация была бы изменением поведения и в этот перенос не входит. Значения enum и схема БД не изменены.

`ApplyManual` возвращает следующий статус, оставляя присвоение вызывающему коду. Только после разрешённого перехода он снимает ArchivedBySynchronization у сотрудника/подразделения. Отказ сохраняет и статус, и исходный признак. Это поведение теперь проверяется независимо от хранения.

## Остаток этапов 1–2

Физическая структура 4 + 2 завершена; Application зависит только от Domain/BCL. Поиск по `Guard/Components` не обнаружил EF, IQueryable или семи legacy-интерфейсов. Публичные независимые контракты автоматически проверяются, но тела многих операций ещё находятся в Infrastructure. Этапы 1–2 целиком не закрыты.

| Участок | Текущее состояние и следующий шаг |
| --- | --- |
| UI и контракты | Поиски/редакторы используют DTO. Семь legacy-контрактов остаются в Infrastructure; перед удалением проверить внутренних потребителей, а не только UI |
| Сессия и доступ | ICurrentSession и три сервиса решений в Application; EF-чтение за узкими портами. Web получает доверенный principal |
| Статусы | Оба класса в Application; независимая матрица в UnitTests. Этот участок завершён |
| IP-полномочия | Перенесён в Application с явной DI-регистрацией и проверками отказов/отмены; см. architecture-ip-management-access.md |
| Валидация и маппинг | EntityInputValidation/EntityWriteMapping перенесены в Application и остаются internal; см. architecture-entity-input-rules.md. ApiSnapshotValidator также перенесён без изменения правил; см. architecture-api-snapshot-validation.md |
| Политика аккаунтов | AccountPolicyRules в Application использует независимый снимок AccountPolicyUserState. Повторное чтение и блокировка остаются в Infrastructure; см. architecture-account-policy-rules.md |
| Дерево, Identity, синхронизация | Транзакции и locks остаются специализированными адаптерами Infrastructure; не дробить их на вызовы репозиториев из Application |
| Экспорт, HTTP, workers | DTO независимы; файловое хранение, OpenXml, HTTP и часть оркестрации в Infrastructure. Расположение транспортных адаптеров/BackgroundService отличается от целевой карты и требует отдельной поставки |
| Владение контекстами | Описано в architecture-context-ownership.md; проверки покрывают откат, конкуренцию и обязательные IdentityResult. Неопределённый исход commit и гарантированная доставка событий остаются открытыми |

Семь legacy-интерфейсов: IPersonalService, IIpAddressService, ISubdivisionService, IClassifierService, ISecurityService, IApplicationRoleService, ILogService. Generic ReadRepository сохраняет серверную защиту до появления эквивалентной проверки всех заменяющих путей. Наличие EF в атомарном адаптере само по себе не требует нового слоя прокси.
