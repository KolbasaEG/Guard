# Проверка обновления прав по событиям через браузер

Инструкция относится к реализации в ветке `codex/access-events`. Цель: убедиться,
что меню и кнопки своевременно отражают права, открытые диалоги не закрываются
из-за обновления доступа, а отзыв прав блокирует запрещённые действия.

## Подготовка

1. Используйте тестовый экземпляр приложения с тестовой БД. Должен работать один
   процесс приложения: текущий транспорт уведомлений действует внутри процесса.
2. Подготовьте Root, обычного пользователя A и другого обычного пользователя B.
   У A и B должны быть привязанные сотрудники, подразделения и разрешённые активные
   IP для текущего адреса браузера. Пустой список IP запрещает вход обычному пользователю.
3. Создайте отдельную роль `Тест событий A` и назначьте её только A. Для B создайте
   отдельную роль. Сохраните исходные назначения и права для восстановления.
4. Для роли A включите чтение сотрудников, полный просмотр сотрудника и изменение
   сотрудников: `Permissions.Personals.Read`, `Permissions.Personals.ReadDetails`,
   `Permissions.Personals.Write`. Для формы могут понадобиться права чтения
   подразделений и используемых справочников; при ошибке загрузки настройте их заранее.
5. Убедитесь, что другие роли A не дают проверяемые права. Итоговые права — объединение
   всех ролей: снятие права в одной роли не отзовёт его, если оно есть в другой.
6. Подготовьте тестового сотрудника в доступном подразделении A. Не используйте
   реальные персональные данные. Запишите первоначальное значение проверяемого поля.
7. Откройте три изолированных профиля браузера или разные браузеры: R под Root,
   A под пользователем A и B под пользователем B. Дополнительно откройте вкладку A2
   под A. Обычное и приватное окна позволяют разделить R и A; несколько приватных
   окон одного браузера могут использовать общие cookies.

Root управляет правами на странице `/roles`; назначения меняются на `/users`
через «Роли и итоговые права». Страница сотрудников — `/personal`.
Во всех сценариях используйте один и тот же адрес приложения.

## Какие события проверяются

| Источник | Что вызывает обновление | Кому |
| --- | --- | --- |
| Изменение permissions существующей роли | Успешное сохранение роли | Всем открытым сеансам пользователей этой роли |
| Изменение назначений пользователя | Успешное сохранение назначений | Всем открытым сеансам этого пользователя |
| Удаление обычной роли | Успешное удаление | Пользователям, которым роль была назначена до удаления |
| Инициализация пустой роли «Администратор» | Успешная явная инициализация | Пользователям этой роли |
| Переход между страницами | Навигация | Текущему сеансу |
| Открытие защищённого диалога | Инициализация диалога | Текущему сеансу |
| Восстановление соединения Blazor | Подключение circuit | Текущему сеансу |
| Отправка формы | Проверка до и после обработчика сохранения | Текущему сеансу |
| Изменение состояния аутентификации | Сигнал AuthenticationStateProvider | Текущему сеансу |

Отклонённое сохранение и конфликт версии не должны публиковать событие изменения
прав. Создание неназначенной роли не меняет доступ существующих пользователей.
Прямая правка БД не публикует события. Обычное сохранение сотрудника также не является
событием изменения permissions. Обновление доступа не означает автоматическую
перезагрузку всех таблиц, карточек и данных формы.

## Сценарии

Перед каждым независимым сценарием восстановите исходные права роли A.
После действий Root не нажимайте F5, обновление таблицы и ссылки в A, если это
не предусмотрено шагами: иначе проверка события подменится ручной проверкой прав.
При нормальном соединении изменение должно появляться после сохранения Root,
без ожидания минутного интервала. Фиксированная гарантия времени доставки не задана.

### 1. Отсутствие периодического закрытия

1. В A откройте редактирование тестового сотрудника на `/personal`.
2. Измените текстовое поле на `EVENT-01`, не сохраняйте. Запишите введённое значение.
3. Оставьте окно открытым минимум на 130 секунд, не меняя права и не переходя по страницам.
4. Продолжите ввод и закройте форму обычной кнопкой отмены.

**Ожидается:** диалог сам не закрывается; введённый текст сохраняется, форма остаётся
доступной. После отмены карточка содержит первоначальные данные.

### 2. Отзыв права записи при открытой форме

1. В A откройте редактирование сотрудника, введите `EVENT-02`, не сохраняйте.
2. В R откройте роль A и снимите только изменение сотрудников (`Personals.Write`),
   оставив чтение и полный просмотр. Сохраните роль.
3. Не выполняя действий обновления в A, проверьте диалог, поля и кнопку сохранения.
4. Попробуйте изменить поле мышью, клавиатурой и отправить форму Enter.
5. Закройте форму и откройте карточку заново.

**Ожидается:** диалог остаётся открытым, `EVENT-02` сохраняется в форме; появляется
сообщение об отзыве редактирования. Поля заблокированы, кнопка сохранения скрыта,
Enter не сохраняет данные. В БД остаётся первоначальное значение. Кнопки изменения
на странице исчезают согласно правам.

### 3. Возврат права записи без повторного открытия

1. Повторите шаги 1–3 сценария 2, оставьте форму открытой.
2. В R верните `Personals.Write` и сохраните роль.
3. В A проверьте поле и сохраните корректные тестовые изменения.

**Ожидается:** форма снова доступна для изменения, предупреждение исчезает,
сохранение возвращается; введённое значение не теряется. После успешного сохранения
диалог может закрыться по обычной логике формы, карточка содержит новое значение.

### 4. Отзыв полного просмотра с сохранением доступа к списку

1. В A откройте полную карточку сотрудника либо форму редактирования.
2. В R снимите `Personals.Write` и `Personals.ReadDetails`, оставьте `Personals.Read`.
   Учитывайте зависимости селектора: сохранённый набор не должен оставлять запись
   без обязательного права просмотра.
3. Проверьте открытое окно и список сотрудников в A.
4. Закройте окно и попробуйте снова открыть полную карточку.

**Ожидается:** открытый диалог остаётся, его содержимое скрывается и появляется
«Просмотр недоступен: права доступа изменились». Сохранение и дополнительная
информация недоступны. Список сотрудников остаётся доступным, полная карточка — нет.
После возврата чтения содержимое может появиться из уже загруженного состояния;
отдельная повторная загрузка актуальных данных этим событием не гарантируется.

### 5. Полный отзыв доступа к модулю

1. В A откройте `/personal` и карточку сотрудника.
2. В R снимите все права сотрудников роли A, сохраните.
3. Проверьте меню, текущую страницу и диалог в A.
4. После закрытия диалога вручную введите адрес `/personal`.

**Ожидается:** пункт меню сотрудников исчезает, текущая страница показывает отказ
в доступе вместо списка; содержимое диалога скрывается. Прямой адрес не обходит
проверку. Отзыв права чтения допускает удаление содержимого из интерфейса,
но не должен принудительно закрывать само окно через DialogService.

### 6. Несколько сеансов и адресность

1. В A и A2 откройте редактирование разных тестовых сотрудников и введите разные
   несохранённые значения. В B откройте доступную B форму и также введите значение.
2. В R снимите `Personals.Write` только у роли A.
3. Проверьте все три вкладки без ручного обновления.

**Ожидается:** A и A2 получают ограничение, обе сохраняют свой ввод. B сохраняет
доступ к записи и введённые данные; его диалог не закрывается.
Если роль назначена нескольким пользователям, изменение этой роли должно затронуть
каждого из них — это проверяется отдельно с общей тестовой ролью.

### 7. Изменение назначенных ролей

1. Откройте в A редактирование сотрудника.
2. В R на `/users` откройте «Роли и итоговые права» для A.
3. Снимите роль, дающую изменение, и назначьте роль только с чтением и полным просмотром.
   Сохраните назначения.
4. Проверьте A и A2. Затем верните исходное назначение.

**Ожидается:** открытые формы переходят в режим без записи; возврат назначения
возвращает доступ. Повторный вход не нужен. Если назначений нет вообще, прикладные
права обычного пользователя становятся пустыми.

### 8. Удаление роли

1. Создайте отдельную тестовую роль с чтением и записью сотрудников, назначьте её A.
   У остальных ролей A оставьте чтение и полный просмотр, но исключите запись.
2. В A откройте форму и введите несохранённое значение.
3. В R удалите созданную роль через `/roles`.

**Ожидается:** A получает отзыв записи, хотя удалённая роль уже отсутствует в БД.
Диалог и ввод сохраняются. При удалении единственного источника чтения ожидается
поведение сценария 5. Root — защищённая роль, для этого теста её не используйте.

### 9. Сбой соединения и восстановление

1. В A откройте форму и введите `EVENT-09`.
2. Только для вкладки A включите Offline в панели Network инструментов разработчика
   либо временно отключите её соединение другим способом. Убедитесь, что R остаётся онлайн.
3. Дождитесь признака потери соединения в A. В R снимите право записи и сохраните.
4. Верните A в Online и дождитесь восстановления соединения.

**Ожидается:** после восстановления того же circuit форма показывает актуальный запрет
записи, ввод сохраняется, отправка недоступна. Состояние офлайн не является подтверждением
права. Если circuit истёк или приложение перезапущено и браузер требует перезагрузки,
сохранение несохранённого ввода не гарантируется: это отдельная граница текущей реализации.

### 10. Неуспешное сохранение и конфликт версий

1. В двух вкладках R откройте одну и ту же тестовую роль до изменения.
2. В первой вкладке измените права и успешно сохраните; проверьте реакцию A.
3. Во второй вкладке попробуйте сохранить другой набор из устаревшей формы.
4. Проверьте сообщение о конфликте и фактические права A.

**Ожидается:** второе сохранение отклоняется; права первой успешной операции остаются
действующими. Отказ не создаёт нового изменения доступа. По браузеру нельзя доказать
отсутствие внутренних лишних callback, но можно проверить отсутствие изменения прав,
закрытия форм и потери ввода. После конфликта откройте роль заново.

### 11. Объединение прав разных ролей и Root

1. Назначьте A две роли, каждая даёт изменение сотрудников с нужными зависимостями.
2. Снимите право изменения только в первой роли, затем во второй.
3. Параллельно проверьте открытый диалог Root.

**Ожидается:** после первой операции запись у A остаётся; после второй блокируется.
Root сохраняет полный прикладной доступ при изменении обычных ролей.

### 12. Повторение для остальных форм

Повторите сценарии 2–5 для следующих модулей, используя тестовые записи:

| Форма | Чтение | Запись |
| --- | --- | --- |
| Подразделение: добавление, изменение, перемещение | `Permissions.Subdivisions.Read` | `Permissions.Subdivisions.Write` |
| IP-адрес: добавление и изменение | `Permissions.IpAddresses.Read` | `Permissions.IpAddresses.Manage` |
| Разрешённые IP сотрудника | `Permissions.IpAddresses.Read` | `Permissions.IpAddresses.Manage` |
| Классификатор: добавление и изменение | `Permissions.Classifiers.Read` | `Permissions.Classifiers.Manage` |
| Тип органа: добавление и изменение | `Permissions.OrganTypes.Read` | `Permissions.OrganTypes.Manage` |
| Сотрудник: добавление | `Permissions.Personals.ReadDetails` | `Permissions.Personals.Write` |

Для разрешённых IP проверьте сохранение несохранённого выбора списка после отзыва
и возврата Manage. Не удаляйте IP, необходимый для входа тестового пользователя.
Для формы добавления проверьте несколько введённых полей: после возврата записи
они должны сохраниться. Для перемещения проверьте выбранное подразделение.

Дополнительно: открытая дополнительная информация сотрудника должна скрыть содержимое
при отзыве полного просмотра. Формы ролей, назначений и журналов доступны только Root;
их нормальное сохранение и отмена должны работать, без повторных или дублирующих диалогов.

## Дополнительные проверки восстановления актуальных прав

- После изменения прав перейдите на другую страницу и обратно: меню и доступ должны
  соответствовать БД. Навигация не обязана сохранять несохранённую форму.
- Закройте старый диалог и откройте новый: новый диалог проверяет текущие права.
- Попробуйте сохранить сразу после отзыва записи: при доставленном событии UI блокирует
  действие; при гонке сервер отклоняет запрещённую операцию. Не должно быть успешной
  записи с уже отсутствующими полномочиями на момент серверной проверки.
- Прямые изменения permissions в БД не подходят для проверки доставки событий.
  Если администратор тестовой среды отдельно меняет их в БД, актуализацию можно
  проверять навигацией, открытием диалога или восстановлением соединения. Это не
  гарантирует немедленного обновления без дополнительного триггера.
- Инициализацию «Администратор» проверяйте только при наличии пустой роли в отдельной
  тестовой среде: назначьте её тестовому пользователю, выполните явную инициализацию
  из панели перехода на `/roles`, проверьте появление разрешённых модулей. Не очищайте
  уже настроенную роль ради проверки. Повторная инициализация не перезаписывает права.

## Признаки ошибки и протокол

Ошибки: окно закрывается само при обновлении доступа; ввод пропадает при отзыве
только записи; данные остаются видимыми после отзыва чтения; запрет не приходит во
второй активный сеанс; запрещённая запись сохраняется; изменения одной персональной
роли влияют на другого пользователя; появляются два одинаковых диалога.

Для каждого сценария фиксируйте:

| № | Браузер и пользователь | Исходные роли | Изменение Root | Ожидание | Фактический результат | Статус |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | | | | | | Не проверено |

При сбое приложите номер сценария, время изменения, URL, скриншот без реальных
персональных данных и ошибку из Console, если она есть. Укажите, понадобился ли F5,
было ли восстановление старого circuit или полная перезагрузка. Не публикуйте cookies,
пароли и строки подключения. По окончании восстановите назначения и данные тестовых
записей; временные роли удалите только после снятия их назначений.

Инструкция описывает ожидаемое поведение. Создание документа не означает, что
перечисленные браузерные сценарии уже выполнены.
