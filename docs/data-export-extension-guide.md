# Руководство по расширению сервиса экспорта

Документ описывает реализацию в ветке `codex/data-export`.
Пользовательский сценарий, архив, настройки сервера и восстановление описаны
в [data-export.md](data-export.md). Правила выдачи permissions —
в [role-permissions.md](role-permissions.md).

## Назначение и границы универсальности

Сервис формирует Excel/Word по фиксированной схеме DTO для всех записей,
соответствующих применённым условиям списка и серверной области доступа.
Пагинация списка не ограничивает экспорт. Общая инфраструктура обеспечивает
очередь, снимок данных, формирование документов, упаковку частей в ZIP,
шифрование точной копии файла, расследование и очистку по сроку хранения.

Подключение сущности выполняется явно в коде. Добавление `DisplayName` к обычному
DTO или новой сущности в EF само по себе не включает экспорт. Автоматического
сканирования сущностей, реестра провайдеров и универсального публичного
`Export<T>` сейчас нет. Для новой области необходимо определить состав полей,
запрос, допустимые фильтры и правила доступа. Формирователи Word/Excel,
скачивание и файловый архив обычно менять не требуется.

## Как работает экспорт

1. Компонент списка сохраняет независимый снимок фильтра при «Применить».
2. `ExportActions` вызывает функцию построения `ExportRequest` и открывает
   `ExportProgress`. Пользователь выбирает формат в меню шапки таблицы.
3. `DataExportService.CreateAsync` проверяет параметры, текущего автора,
   права и лимит активных заданий; сохраняет запрос и метаданные в БД.
4. Worker получает задание и заново проверяет права автора. Контекст UI
   и cookie не используются как источник фоновых полномочий.
5. `ExportSnapshot` в транзакции RepeatableRead читает запрос, проецирует строки
   в DTO и сохраняет зашифрованный промежуточный снимок. Иерархия строится по
   подразделениям выбранных записей и их предкам в том же снимке БД.
6. `ExportDocumentWriter` формирует документы из снимка. Большая выгрузка
   разбивается на части; результатом становится один файл либо ZIP.
7. `ExportProcessor` сохраняет защищённую точную копию результата,
   повторно проверяет доступ и переводит задание в Ready.
8. POST скачивания проверяет автора, актуальные полномочия, область,
   security stamp, срок хранения, размер и SHA-256. Первое начало передачи
   потребляет возможность скачивания, включая передачу, завершившуюся обрывом.

Запрос фиксируется при создании задания; данные фиксируются при обработке
worker, а не в момент нажатия кнопки. За время ожидания значения в БД могут
измениться. Сохранённый файл после формирования уже не строится заново.

## Подключение новой сущности

### 1. Определить контракт

До изменения кода зафиксируйте:

- Какие собственные поля входят в экспорт и в каком порядке.
- Как запись связана с подразделением и допустимы ли записи без подразделения.
- Как совпадают условия списка и экспорта: статусы, иерархия, фильтр, сортировка.
- Какие права позволяют экспортировать активные, архивные и удалённые записи.
- Нужен ли Root переключатель «Все записи», присутствующий в конкретном списке.

Не включайте полную сущность, коллекции связей или содержимое закрытой карточки
ради удобства. Разрешение читать список не означает разрешения читать все
сведения сущности. DTO экспорта задаёт отдельный фиксированный контракт.

### 2. Добавить область и permission

Новому `ExportArea` присвойте новое уникальное числовое значение. Существующие
значения хранятся в БД: менять их и повторно использовать удалённые нельзя.
Добавьте permission в `Permissions` и `PermissionCatalog` согласно соседним
определениям; обычный экспорт должен зависеть от права чтения области.

В `ExportSchema.Permission` сопоставьте область с новым permission.
Root назначает право ролям через штатный интерфейс. Изменение каталога
само по себе не даёт это право существующим обычным ролям.

### 3. Создать DTO и зарегистрировать схему

Пример будущего DTO для оборудования; имена приведены как образец,
такой области в текущей реализации нет:

```csharp
public sealed record EquipmentExportDto(
  [property: DisplayName("Наименование")] string Name,
  [property: DisplayName("Инвентарный номер")] string? InventoryNumber,
  [property: DisplayName("Подразделение")] string? Subdivision,
  [property: DisplayName("Статус")] string Status);
```

В `ExportSchema` добавьте явный массив имён свойств в нужном порядке,
ветвь `Properties` с типом DTO и ветвь `Title` с русским названием области.
Заголовок каждого выбранного свойства обязан иметь `DisplayName`.
Порядок объявления свойств и reflection не определяют порядок колонок — его
определяет массив схемы. Лишнее свойство DTO автоматически не экспортируется.

Текущий `Cells` записывает `int` и конечные `double` как числа, `bool` как
логические значения с русским представлением, null как пустую ячейку.
Другие типы становятся текстом через invariant culture. Если понадобятся
`decimal`, `long`, даты или специальное форматирование, сначала определите
нужный тип ячейки и точность, затем совместимо расширьте преобразование и тесты.
Не преобразуйте денежные суммы и большие идентификаторы в double без проверки
потери точности. Текстовые значения, похожие на формулу, сохраняются как текст.

### 4. Реализовать серверный запрос

В `ExportQueries` добавьте запрос `AsNoTracking`, последовательно ограничивая:

1. Серверную область доступа пользователя.
2. Допустимые статусы выбранного режима.
3. Режим «Только свои / Свои и подчинённые» либо явно разрешённые все записи Root.
4. Применённый пользовательский фильтр.
5. Разрешённую сортировку со стабильным дополнительным ключом Id.

Экспорт не содержит `Skip`/`Take`. Пользовательский фильтр только сужает
доступную область. При отсутствии корректного собственного подразделения
режим «свои» должен возвращать пустую выборку, в том числе для Root.

Для сущностей, наследующих `BaseEntity`, можно использовать `Statuses`.
Состояния перечислены явно: активные — Inserted, Modified, Blocked; архивные —
Archived, ArchivedBlocked; удалённые — Deleted. Для другой модели статусов
нужен отдельный проверенный запрос.

Создайте allowlist полей сущности для `ExportFilters.Apply` и `Sort`.
Имена относятся к сущности (`Subdivision.Name`), а не к DTO (`Subdivision`).
Вычисляемые неподдерживаемые поля не должны появляться в серверной сортировке.
`Sort` по умолчанию использует `InsertedDate desc, Id asc`: для сущности без этих
свойств задайте подходящую сортировку явно или расширьте общий контракт.

Для совпадения со списком предпочтительна общая реализация условий чтения,
как сделано для сотрудников. Если запросы остаются отдельными, сравнивайте
результирующие ID в интеграционных проверках.

### 5. Дополнить валидацию и доступ

В `DataExportService.Validate` добавьте ветвь области и проверку допустимых
фильтров/сортировки до создания задания. Не оставляйте новую область с одной
проверкой `Enum.IsDefined`: это не проверяет её конкретный контракт.
Текущие общие ограничения — запрос до 32768 байт и фильтр до 100 узлов
с глубиной до 16. Передавайте CancellationToken до запросов БД.

В `ExportAccess.ForUserAsync` явно задайте право чтения архива для новой области.
Текущий выбор archivePermission содержит специальный случай сотрудников и
иначе использует право подразделений; новую сущность нельзя подключать,
оставляя это предположение без проверки. Правило удалённых записей сейчас
ограничено Root. Проверки выполняются и в фоновой обработке, и при выдаче.

Текущая область `ExportAccessScope` предназначена для доступа по подразделениям.
Для сущности с другим правилом доступа (владелец, документ, проект, несколько
подразделений) требуется отдельное серверное правило и повторная проверка
перед выдачей. Нельзя считать такой случай обычным добавлением DTO.

### 6. Добавить проекцию снимка

В `ExportSnapshot.CaptureAsync` добавьте ветвь `request.Area`:

- `ids` — запрос уникальных ID подразделений выбранных записей.
- `rows` — проекция в `RawRow(SubdivisionId, ExportDto)` с `AsAsyncEnumerable`.

Оба запроса должны исходить из одной отфильтрованной выборки. Проекция включает
только нужные поля; коллекции связанных сущностей не загружаются.
`RawRow` — внутренний тип компонента снимка, а не новый публичный API.

Для подразделения строка ссылается на свой Id, для зависимой сущности — на
её SubdivisionId. Общий код добавит цепочку от корня до непосредственного
подразделения и выровняет глубину Excel. Word содержит только таблицу DTO.
Цепочка сверяется с ParentId и materialized Path; цикл, пропущенный предок,
несогласованный путь или глубина свыше 64 приводят к ошибке формирования.

Null SubdivisionId означает отсутствие цепочки. Текущая защита выдачи запрещает
обычному пользователю выгрузку с такими строками. Решение, допускаются ли
они в запросе Root, должно быть явным в правилах новой области.

### 7. Подключить меню таблицы

В code-behind добавьте `BuildExportRequestAsync(ExportFormat format)` по образцу
IP-адресов. Передавайте область, формат, текущий режим статусов, иерархию,
сохранённую сортировку и **применённый снимок** фильтра. Часовой пояс получается
через `BrowserTimeService.InitializeAsync()` и `Zone.Id`.

`ExportFilter` применяется к подразделениям и IP; сотрудники используют
существующий `PersonalFilter`. Для обычной новой области используйте
`ExportFilters.Capture` при «Применить», проверьте снимок через allowlist и
только после успешной проверки замените сохранённое условие. Чтение живого
`dataFilter.Filters` при нажатии экспорта нарушит правило применённого фильтра.

Внутри `RadzenMenuItem` «Меню» в шапке таблицы разместите `ExportActions`,
защитите его проверкой permission экспорта и передайте:

| Параметр | Значение |
| --- | --- |
| `Area` | Новое значение ExportArea |
| `BuildRequest` | Метод BuildExportRequestAsync |
| `Disabled` | Состояние, запрещающее запуск во время загрузки списка |

`ExportActions` сейчас рендерит вложенные `RadzenMenuItem`, поэтому его следует
помещать внутрь меню, а не в обычный стек кнопок. Он сам создаёт диалог прогресса
и открывает незавершённые задания этой области. Не добавляйте собственное
скачивание через JavaScript или URL к каталогу файлов.

### 8. Проверить подключение

Минимальная проверка новой области включает:

- Состав и порядок колонок, DisplayName, типы, null и формулоподобный текст.
- Excel и Word при нуле строк, обычной выборке и превышении RowsPerPart;
  проверку Open XML и содержимого предпросмотра архива.
- Совпадение ID списка и экспорта с применённым фильтром, статусом и иерархией;
  изменение конструктора без «Применить» не меняет выгрузку.
- Root, обычную роль с правом и роль без права; чужую ветвь, отсутствие
  подразделения, архивные и удалённые записи.
- Отзыв права и сужение области между запросом, обработкой и скачиванием.
- Браузерное открытие меню, запуск, закрытие диалога и возврат к заданию.

Запускайте сборку и существующий набор проверок по командам из data-export.md.
Проверки PostgreSQL выполняются только на изолированной временной БД.
Фактическую верстку документов проверьте в Word и Excel; проверка XML не
подтверждает удобство чтения широкой таблицы.

## Изменение существующих полей и версия схемы

Добавление поля требует изменения DTO, явного массива `ExportSchema`, проекции
снимка и проверок. Добавление допустимого фильтра дополнительно требует
allowlist, валидации, настройки списка и русского названия в `Conditions`.
Состав выводимых полей и состав фильтруемых полей могут различаться.

В текущей реализации `SchemaVersion = 1`, а worker принимает только версию 1.
Это общая версия, а не полноценный реестр версий каждой области. Сохранённый
ExportRequest не содержит снимка DTO: незавершённое задание будет обработано
кодом, действующим после обновления приложения.

Поэтому перед изменением состава или смысла полей определите судьбу очереди.
Для первой эксплуатации можно завершить Queued/Processing до обновления,
а готовые файлы сохранить. При дальнейшем росте поддержите отдельные версии
контрактов и обработчиков либо явное завершение несовместимых заданий с
понятной ошибкой. Простое увеличение номера без поддержки версии в worker
сделает задания ошибочными.

Сформированные файлы сохраняют свои заголовки: Root-предпросмотр читает документ,
а не новую DTO-схему. Добавление значения ExportArea обычно не требует миграции
экспортных таблиц. Изменения модели новой сущности или метаданных архива требуют
обычной EF-миграции; прежнюю AddDataExport не редактируйте.

## Рост числа сущностей и объёма данных

Количество областей само по себе не требует отдельной очереди или файлового
архива. Текущий worker обрабатывает задания последовательно, поэтому длительная
выгрузка одной области задерживает остальные. RowsPerPart ограничивает размер
части документа, но не число строк задания и не размер итогового ZIP.

Строки обрабатываются потоком, однако ID подразделений и их предки находятся
в памяти, а снимок удерживает транзакцию чтения на время выборки. Проверяйте
нагрузку PostgreSQL, длительность транзакций, число уникальных подразделений,
временный диск и скорость формирования. Увеличение TimeoutMinutes не устраняет
неэффективный запрос; сначала проверяйте фильтры, SQL и индексы.

Если повторение ветвей в Schema/Validate/Queries/Snapshot/Access начинает
мешать поддержке, следующим отдельным этапом можно ввести реестр провайдеров
по ExportArea. Провайдер должен объединять версию, DTO-схему, валидацию,
запрос и правила доступа. Общий pipeline хранения/выдачи сохраняется.
Это направление развития, а не уже существующий API.

Параллельный worker, несколько серверов, внешнее объектное хранилище и
планировщик нагрузки требуют отдельного проектирования блокировок,
восстановления, жизненного цикла файлов и ключей. Общий scoped DbContext
нельзя использовать параллельно. Нынешний контракт эксплуатации — один сервер
и последовательный обработчик.

## Критерий готовности новой области

Область подключена, когда оба формата формируются из разрешённой выборки,
фильтры совпадают со списком, архив хранит точные байты результата, закрытие
диалога и возврат к заданию работают, сервер повторно проверяет доступ перед
выдачей, а тесты подтверждают эти свойства. Завершение регистрации DTO без
этих проверок не означает готовности экспорта.
