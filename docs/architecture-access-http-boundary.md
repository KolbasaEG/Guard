# HTTP-адаптеры доступа в Web

Дата: 17 октября 2026 года. Ветка: `codex/architecture-ip-search`. База: `4ac4e28`.

## Изменение

IpCheckMiddleware, AccountPolicyMiddleware, PermissionAuthorizationHandler и PermissionRequirement перенесены из Infrastructure в Guard/Web/Identity. Namespace Guard.Core.Identity сохранён, как у соседних адаптеров circuit; исходные реализации не изменены. В middleware добавлен явный импорт Microsoft.AspNetCore.Http вместо глобального импорта Infrastructure.

Регистрация обработчика уже принадлежала AddGuardWeb и остаётся scoped. Порядок Program сохранён: ForwardedHeaders, Authentication, Authorization, журналирование пользователя, IpCheckMiddleware, AccountPolicyMiddleware, Antiforgery. Авторизация маршрута по-прежнему выполняется до двух middleware; перенос не меняет эту семантику.

IP-адаптер использует независимый IIpAccessService. Сохранены обход для анонимного запроса и выхода, запрет при отсутствующем ID, доверенный RemoteIpAddress, передача RequestAborted, аудит и русский ответ 403. IpAccessDeniedException из следующего обработчика преобразуется в 403 только до начала ответа.

AccountPolicyMiddleware сохраняет чтение пользователя и security stamp через UserManager, SignOut при блокировке/устаревшем stamp, redirect на вход, требование смены пароля и запись активности только для HTML. Выход пропускает эти проверки. PermissionAuthorizationHandler получает актуальные права через IPermissionService, игнорирует анонимный запрос/отсутствующий ID, записывает отказ и перехватывает UnauthorizedAccessException как раньше.

Перенос сборки публичных типов требует перекомпиляции внешних бинарных потребителей, если они существуют вне решения. Исходные потребители внутри репозитория продолжают использовать прежние namespace и имена без правок.

## Сохраняемые зависимости

AccountPolicyMiddleware по-прежнему зависит от инфраструктурного ApplicationUser через UserManager. ClientIpAddress остаётся в Infrastructure: его используют также Identity sign-in и другие инфраструктурные операции. Это осознанные оставшиеся зависимости Web → Infrastructure. Независимые правила доступа и политики остаются в Application; транзакции, блокировки, проверки перед выдачей cookie и работа Identity не затронуты. Схема, миграции, данные и настройки не изменены.

## Проверки

Проверки границ подтверждают размещение четырёх типов только в Web. В четырёх вариантах DI проверяются единственная scoped-регистрация обработчика и отсутствие её в Infrastructure. PostgreSQL-сценарий совместного вызова двух middleware проверяет отказ IP для /_blazor до проверки истёкшего пароля, redirect при разрешённом IP, доступ к смене пароля и выход при запрещённом IP. Существующие проверки маршрутов после отзыва прав, смены пароля, IP-отказов, отсутствующего ID, доверенных proxy и перехвата исключения сохранены.

Результат полного прогона приведён в docs/testing.md. Рабочий Program не запускался. Браузерные и нагрузочные сценарии в этот участок не входят.

## Следующий участок

Сверить размещение трёх фоновых адаптеров: AccountPolicyWorker, ApiSynchronizationWorker и ExportWorker. Отделять host-цикл от операции только с сохранением времени жизни scope, отмены, блокировок и восстановления; не дробить атомарные EF-операции. Этапы 1–2 остаются открытыми. Неопределённый исход commit, гарантированная доставка аудита и масштабирование проверки уникальности IP требуют отдельных участков.
