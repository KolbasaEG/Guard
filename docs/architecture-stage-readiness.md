# Сверка готовности этапов 1–2

Дата: 17 октября 2026 года. База: `06cce88`, ветка `codex/architecture-ip-search`.

Это текущая сверка критериев, заменяющая устаревшие пункты «следующего участка» в исторических отчётах. Цель остаётся прежней: четыре производственных проекта и два тестовых, один процесс и одна основная БД. Физическое разделение ещё не начато.

## Публичные контракты

В пространствах `Guard.Core.Services` и `Guard.Core.Services.Exports` обнаружены 39 публичных интерфейсов. Семь legacy-контрактов остаются инфраструктурными: IPersonalService, IIpAddressService, ISubdivisionService, IClassifierService, ISecurityService, IApplicationRoleService, ILogService. Удалять их по одному только отсутствию потребителей в UI нельзя: например, SecurityService использует IIpAddressService для старого query-метода.

Остальные 32 интерфейса — прежние 24 контракта операций, семь служебных и порт IDirectoryApiClient из [реестра](architecture-application-contracts.md). Новый ApplicationContractBoundaryTests обнаруживает их автоматически, проверяет количество и рекурсивно обходит публичные сигнатуры, DTO, конструкторы, поля, события, наследование, массивы и callbacks. Запрещены IQueryable и типы за пределами BCL/независимых прикладных типов, включая EF, ASP.NET Core, Identity, Radzen и сущности. Два исторических enum синхронизации разрешены явно. Отрицательные примеры проверяют вложенный query, сущность в методе модели, HTTP в callback, наследование и массив сущностей; независимый callback разрешён.

Это проверка доступных типов, а не IL или тел реализаций. Например, UserAccessSnapshot.Has обращается к независимому PermissionCatalog: каталог и Permissions должны переноситься вместе с ним, хотя публичная сигнатура Has содержит только string/bool. Отсутствие EF в контракте не означает отсутствие EF в реализации.

Поиск по Components не обнаружил EntityFrameworkCore, IQueryable, обращений к семи legacy-интерфейсам или SearchQuery. Технические адаптеры Account/HTTP и получение доверенного principal остаются частью Web; их наличие само по себе не нарушает прикладной контракт.

## Изменения этой поставки

- ISynchronizationService, IDirectoryManagementService, IApiDiagnosticService и IDirectoryApiClient вынесены в отдельные файлы без изменения сигнатур, необязательных параметров и namespace.
- DataManagementMode и SynchronizationStatus вынесены из файла сущностей в `Core/0-Enums/SynchronizationStates.cs`. Сохранены namespace Guard.Core.Entities и все числовые значения. По назначению это независимые состояния управления и выполнения синхронизации; их можно переносить с остальными независимыми состояниями в Domain без сущностей настроек и запусков.
- Добавлена общая проверка границы 32 контрактов. Прежние проверки DI и отдельных функциональных границ сохранены.

Реализации, SQL-модель, сериализация заданий, настройки подключения и UI не изменены. Новой миграции не требуется: CLR-типы и их полные имена сохранены.

## Следующий конкретный участок

Начать с IP-допуска: IpAccessService сейчас совмещает чтение пользователя/роли Root/активных IP через EF и независимое решение о допуске. Выделить получение минимальных данных для этого решения за узким портом, а правило проверки оставить независимым от EF. Сохранить существующий порядок: неизвестный пользователь запрещён, Root освобождён от проверки адреса, неактивный сотрудник и пустой набор IP запрещены, только активные привязки, прежняя обработка IPv4/IPv6/CIDR и отмены. Не использовать PermissionService как замену проверки Root в этой операции: вход ещё не создаёт текущую сессию.

После этого тем же способом разобрать permissions/область и остальные операции по [реестру владельцев контекстов](architecture-context-ownership.md). Атомарные операции дерева, Identity и синхронизации могут оставаться специализированными адаптерами Infrastructure; блокировки и транзакции нельзя дробить на отдельные вызовы репозиториев из Application. Generic ReadRepository сохраняет нынешнюю защиту до появления эквивалентной проверки во всех заменяющих путях.
