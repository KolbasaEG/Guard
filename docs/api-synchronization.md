# Актуализация данных из кадрового API

## Серверные задания и события выхода персонала

Ручной запуск из интерфейса сохраняется в БД со статусом «ожидает запуска». Фоновый работник проверяет очередь каждые 30 секунд, создаёт собственный контекст и выполняет сохранённый запрос. Закрытие страницы после подтверждения приёма не отменяет выполнение. Панель обновляет состояние каждые 15 секунд и показывает этапы: классификаторы, подразделения, персонал, события выхода, зависимости и применение. Нельзя принять второй запрос, пока имеется ожидающий или выполняющийся запуск. После перезапуска ожидающие задания сохраняются; незавершённые выполнявшиеся операции отмечаются как прерванные и требуют повторного запуска.

Перед выполнением задания заново проверяются полномочия и подразделение инициатора. Изменение настроек после постановки в очередь отклоняет запрос; во время получения изменение версии настройки отменяет загрузку. Остановка приложения отменяет работу корректно. Сохранение уже начавшейся транзакции согласовано с изменением настроек общей блокировкой.

Запуск с датой получает также `POST /personnel/out-of-scope` с той же явной `UpdatedAt` на каждой странице. Контракт события: `PersonalId` — внешний ID, `EventAt` — момент фактического перевода со смещением часового пояса. Получение последней страницы сдвигает серверную отметку экспорта, но не удаляет события. Guard не полагается на эту отметку: явную дату можно повторить после ошибки сохранения. Полный ручной запуск без даты выполняет сверку по трём основным ресурсам и не использует серверную автоматическую отметку событий.

Событие выхода архивирует импортированного сотрудника с сохранением GUID, аккаунта и IP-связей. Blocked переходит в ArchivedBlocked; ручное удаление/архив сохраняются. Таблица ApiPersonnelExits хранит последнюю обработанную дату по внешнему ID, включая неизвестные ID; пустая карточка для неизвестного сотрудника не создаётся. Более новое состояние сотрудника из /personnel подтверждает возвращение и восстанавливает только автоматический архив. Повтор старого события не архивирует возвращённого сотрудника. Одинаковые даты записи и события считаются неоднозначностью и отклоняют набор. Для этой последовательности UpdatedAt записи должен отражать изменение принадлежности сотрудника, EventAt — фактический перевод. Сравнения выполняются в UTC с точностью PostgreSQL.

Поступившие события, изменения и отметки повторов сохраняются атомарно. При отказе БД ни новые отметки, ни архивирование не остаются применёнными. Счётчики ExitEvents, RepeatedExitEvents и UnknownExitEmployees показываются в результате запуска. События обрабатываются централизованным запуском; неизвестные ID не создают карточки и не расширяют доступ пользователей.

В частичной выгрузке Guard сначала использует имеющиеся зависимости, затем запрашивает недостающие подразделения по Data.Id, классификаторы по ClassifierType/ClassifierCode. Эти точечные запросы выполняются без фильтра даты. Дозагрузка ограничена 512 запросами, ссылки проверяются после её завершения. Граница головного подразделения сохраняется: недоступный внешний родитель над ней не превращается в обычное локальное подразделение.

На странице Root доступна проверка GET /ping, использующая сохранённые параметры подключения и не применяющая данные. Диагностика с датой читает все четыре ресурса, сообщает число событий и конфликт одинаковых дат записи/выхода, но не дозагружает зависимости и не записывает изменения. Отдельно показываются последняя полная сверка и последнее обновление изменений. После пропущенного суточного окна требуется загрузка с более ранней датой или полная ручная сверка; интерфейс показывает предупреждение о пропущенном периоде. RecoveryRequiredFrom сохраняет начало непокрытого периода даже после успешной узкой ежедневной загрузки и очищается только после успешной загрузки, охватывающей этот период, либо полной сверки. Новые контрольные даты начинают заполняться после применения новой версии; исторические запуски не классифицируются задним числом автоматически.

## Ключи Data Protection в рабочем окружении

Поддерживаются необязательные параметры среды: DataProtection:KeyDirectory, DataProtection:ApplicationName и DataProtection:CertificateThumbprint. Если они не заданы, прежнее поведение хостинга сохраняется. Для серверного развёртывания задайте постоянный каталог ключей с доступом только служебной учётной записи и резервным копированием. При явном файловом хранилище настройте шифрование ключей сертификатом через CertificateThumbprint; процессу нужен доступ к его закрытому ключу. Для нескольких экземпляров используйте одно имя приложения и совместимое хранилище/сертификат. Имя приложения и доступность прежних ключей влияют на расшифровку уже сохранённого пароля и cookies: при изменении настроек потребуется новый вход и, если прежняя защита недоступна, повторное сохранение пароля Root. Параметры в репозитории и реальные ключи этой доработкой не изменялись.

## Фильтр даты UpdatedAt

Root может указать необязательную дату ручного запуска. Она передаётся как `Data.UpdatedAt` в формате `yyyy-MM-dd` во всех страницах всех трёх ресурсов. Если дата не указана, параметр полностью отсутствует в JSON и выполняется полная выгрузка. Остальные пользователи не могут запускать синхронизацию.

Каждый автоматический запуск обязательно передаёт дату начала этого запуска по времени сервера минус один календарный день. Например, начало 10 октября в 02:00 даёт `UpdatedAt=2026-10-09`. Это фиксированное суточное окно, а не дата последнего успешного запуска. Дата сохраняется в истории и диагностике.

Первая синхронизация также может выполняться с датой; обязательная предварительная полная загрузка не требуется. Если ответ ссылается на отсутствующие локально записи, выберите более раннюю дату или выполните полную загрузку без даты. При загрузке изменений ссылки проверяются по объединению ответа и ранее импортированных данных; неизвестная ссылка отклоняет весь импорт. Полученные записи обновляются полностью, включая очистку необязательных полей. Отсутствующие в ответе записи не архивируются и не деактивируются. Архивация по отсутствию доступна только при полной ручной выгрузке без даты. После длительного простоя или пропущенных запусков выполните полную ручную загрузку, чтобы получить изменения старше суточного окна и выявить исчезнувшие записи.

Пошаговые действия для первого и последующих запусков, диагностика и сценарии проверки: [Тестирование в закрытой сети](api-synchronization-testing.md).

## Режимы и доступ

В списках подразделений и персонала только Root доступны переключатели «Все подразделения» и «Весь персонал». При первом открытии Root этот режим включён: привязка Root к сотруднику не требуется для просмотра импортированных данных. Статус, применённые фильтры, сортировка и пагинация продолжают ограничивать выдачу. Отключение общего режима возвращает «Только свои / Свои и подчинённые»; без собственного подразделения эти два режима дают пустой список. Остальные пользователи не получают общего режима, серверная область доступа сохраняется. Общая дата актуализации в аналитике не зависит от выбранной области просмотра.

Страница `/synchronization` доступна Root и пользователям с разрешением
`Permissions.Synchronization.Run`. Оно назначается через существующее управление
permissions ролей и требует `Permissions.Subdivisions.Read`. Имя роли само по себе
не разрешает запуск.

Root задаёт общий режим и ежедневное время в БД. Время интерпретируется в часовом
поясе сервера; интерфейс показывает его название. Моменты событий хранятся в UTC,
дата выполненного планового события — как календарная `DateOnly`.

* **Локальное управление:** действуют прежние правила ручного редактирования;
  автоматическая и ручная синхронизация отключены.
* **Управление из API:** три области доступны для просмотра. Создание, изменение,
  перемещение, ручные статусы, экспорт персонала и изменение его привязок запрещены
  на сервере, включая Root. Управление настройками и запуск синхронизации являются
  отдельными разрешёнными операциями. Самостоятельные разделы ролей, политик
  аккаунтов и каталога IP сохраняют свои правила доступа.

Только Root управляет синхронизацией всей системы, настройками, диагностикой и историей на странице `/synchronization`. Разрешение `Synchronization.Run` исключено из каталога ролей; прежние назначения не дают доступа. Ожидающие задания прежних операторов отклоняются до получения API. Автоматические задания продолжают выполняться системным процессом.

## Подключение

### Головное подразделение области API

Root может задать на странице `/synchronization` «Внешний ID головного подразделения API» — положительный ID источника, а не локальный номер Guard. Для тестового аккаунта, по подтверждению разработчиков API, это `4448`. Значение сохраняется вместе с настройками, проверкой версии и аудитом; оператор пула изменять его не может. Пустое поле отключает исключение для внешнего родителя.

Только указанный узел становится локальным корнем: его локальные `ParentId` и `ParentSubdivisionId` пусты, `Path` начинается с его локального номера. Исходный `ExternalParentId` (например, `2`) сохраняется. Отсутствующие родители остальных узлов и циклы остаются ошибками. Полученные подразделения и сотрудники должны принадлежать согласованному дереву; за пределами этого дерева полная сверка не архивирует сотрудников и подразделения.

При первой загрузке головной узел должен присутствовать в ответе. При загрузке изменений он может разрешаться ранее импортированными данными. Ошибочный ID отклоняет применение данных. Диагностика учитывает настройку, отмечает головной узел с исходным родителем и сообщает отсутствие настроенного корня.

Перед использованием требуется миграция `20261010130000_AddApiHeadSubdivision`. Она добавляет nullable bigint с проверкой положительного значения, не меняя существующие подразделения. Внешний ID не настроен автоматически. Для работы задайте его явно и выполните подходящую первоначальную загрузку с ранним UpdatedAt. Изменение настройки использует существующую смену версии и отмену активной загрузки.

Источник (HTTPS-адрес API) и размер страницы (1–500, по умолчанию 500) задаются Root на странице `/synchronization` и сохраняются в БД. Они используются во всех запросах ручной и автоматической синхронизации. Пустой источник допустим только в локальном режиме. После миграции Root должен указать источник перед первым запуском. Размер страницы не ограничивает общий объём выгрузки.

Логин и пароль Basic auth задаются только Root в этой же форме. Логин хранится в БД, пароль — в защищённом виде ASP.NET Core Data Protection. Сохранённый пароль не возвращается в интерфейс; пустое поле оставляет прежний пароль. Изменение учётных данных отменяет текущую загрузку и применяется при следующем запуске.

Для расшифровки после перезапуска необходимо сохранять хранилище ключей Data Protection и права доступа к нему. При нескольких экземплярах приложения хранилище ключей и имя приложения должны быть общими. При утрате ключей Root должен задать пароль заново. Миграция не копирует секреты из конфигурации; перед первым запуском задайте логин и пароль в форме.

| Ключ конфигурации | Назначение |
| --- | --- |
| `DirectoryApi:CompleteSnapshotGuaranteed` | Подтверждение полноты и согласованности выгрузки, по умолчанию false |

Для переменных окружения вместо `:` используется `__`.

`CompleteSnapshotGuaranteed` можно включить только после подтверждения владельцем
API, что выгрузка возвращает полный согласованный набор, включая ситуации с
изменением данных во время обхода страниц. Проверки счётчиков, ключей и ссылок
обнаруживают часть ошибок, но не доказывают эти гарантии сами по себе. Пока флаг
выключен, синхронизация завершится понятной ошибкой без применения данных.

Проверка сертификата TLS обязательна. HTTP timeout — 60 секунд на запрос.
Для сетевых ошибок без HTTP-статуса, 429 и 5xx предусмотрено до трёх попыток.
Ошибки авторизации, валидации и противоречивые ответы не повторяются как временные.
Адреса и учётные данные из примеров запросов не используются как значения по умолчанию.

## Получение и применение

Каждый запуск получает полные наборы `/classifiers`, `/subdivisions`, `/personnel`
через POST с оболочкой `Data` и полями `page`, `per_page`. Ручной запуск Root может
передавать `UpdatedAt`; автоматический передаёт его обязательно, как описано выше. HTTP-запросы не удерживают транзакцию записи.

Проверяются успешность каждого ответа, пагинация, количество записей, отсутствие
повторных внешних ключей, поля, ограничения длины, ссылки на классификаторы и
подразделения, существование родителей и отсутствие циклов.

Значение ParentId null или 0 обозначает корень. Отрицательный ID родителя и
неизвестный положительный родитель являются ошибкой. Это правило должно
соответствовать контракту установленного API.

Полная запись очищает отсутствующие необязательные поля. Код классификатора 0 и
пустое Value допустимы. IsActive должен быть 0 или 1. Даты читаются с часовым поясом
и переводятся в UTC; точность хранения источника соответствует микросекундам PostgreSQL.

Состав применения: классификаторы → подразделения и пути → персонал → исчезновение
и возвращение → результат и актуальность. Все записи выполняются в одной
транзакции. Ошибка получения или проверки не применяет ничего; ошибка сохранения
откатывает весь набор. В журнале не показываются положительные счётчики применения
для откатившейся операции.

Внешние статусы копируются в StatusType/StatusCode и не преобразуются в локальный
Status. Исчезновение из полной выгрузки — отдельное правило: импортированные
подразделения и сотрудники архивируются, классификаторы становятся неактивными.
Blocked при исчезновении переходит в ArchivedBlocked. Автоматическая архивация
отмечается отдельно: вернувшиеся записи восстанавливаются в Modified или Blocked.
Ранее ручной архив/удаление автоматически не снимаются. Физическое удаление не выполняется.

Классификаторы, подразделения и персонал обновляются централизованно. Исторические запуски пулов сохраняются в журнале, но не определяют общую актуальность. Изменённые пути пересчитываются с учётом всех локальных потомков.

## Идентичность и переход существующей базы

Локальные GUID сохраняются, поэтому существующие связи импортированных сотрудников
с пользователями и IP не пересоздаются. `ExternalId` хранит ID API для подразделений
и сотрудников. Локальные `SubdivisionId` и `PersonalId` продолжают генерироваться
локально. Это исключает автоматическое сопоставление внешнего ID с совпавшим
номером тестовой записи. `PersonalSubdivisionId` хранит внешний ID подразделения
сотрудника и допускает повторения.

Тестовые локальные записи без внешней идентичности не удаляются и не архивируются
на основании отсутствия в API. Сопоставление по ФИО или совпавшему локальному номеру
не выполняется. Их дальнейшую судьбу необходимо определить отдельно; пользовательские
данные не очищаются миграцией ради подключения API.

Сущность OrganType удалена. Subdivision.OrganTypeId/OrganTypeCode напрямую ссылаются
на Classifier.Type/Code. Миграция сначала преобразует прежние связи через
OrganTypes.ClassifierType, затем удаляет таблицу. Старые permission claims OrganTypes
перестают учитываться каталогом разрешений.

Миграция создаёт настройки в безопасном начальном состоянии: локальное управление,
расписание выключено, время 02:00. Автоматический Down этой миграции запрещён:
удалённую таблицу и старую уникальность подразделения персонала нельзя достоверно
восстановить после импорта. Откат требует резервной копии.

Если учётные записи ещё не привязаны к импортированным сотрудникам: Root выполняет
первую полную загрузку, временно возвращает локальный режим для назначения нужных
привязок и permissions ролей, затем включает API и расписание.

## Расписание, конкуренция и актуальность

Дата выполненного планового запуска определяется по началу запуска в часовом поясе сервера. Завершение после полуночи не отмечает следующий день выполненным. Ошибка или отмена не изменяет эту дату, поэтому повтор остаётся доступным. Автоматический `UpdatedAt` рассчитывается из того же момента начала.

Перед записью сравниваются даты сотрудников с последними событиями выхода как из текущего ответа, так и из сохранённых отметок `ApiPersonnelExits`. Равенство в UTC с точностью до микросекунд отклоняет весь запуск, включая полную загрузку и появление ранее неизвестного сотрудника. Данные, отметки событий и даты успешной синхронизации при этом не изменяются.

Worker проверяет расписание каждые 30 секунд. После пропуска из-за остановки
приложения выполняется один догоняющий запуск за текущую календарную дату, если
назначенное время уже прошло. Неуспешный плановый запуск повторяется с задержкой
не менее пяти минут. Пропущенные дни не воспроизводятся отдельными запусками.

Глобальная session advisory lock PostgreSQL допускает только один запуск,
включая несколько экземпляров приложения. Изменение режима и применение
согласуются transaction advisory lock. Переключение настройки отменяет получение;
перед записью режим, версия настройки, полномочия и принадлежность инициатора
пула проверяются заново. Запись, уже находящаяся в транзакции применения,
завершится до вступления изменения режима в силу.

Потерянные после остановки процесса запуски переводятся в Interrupted только при
получении глобальной блокировки, чтобы не прервать работающий другой экземпляр.

В аналитике списков классификаторов, подразделений и персонала все пользователи с правом просмотра видят общую дату завершения последнего успешного запуска всей системы, включая исторические полные загрузки и загрузки с датой. Запуски пулов, ошибки и отмены эту дату не изменяют. При отсутствии успеха отображается «Данные из API ещё не актуализированы». В локальном режиме прежняя дата сохраняется с пометкой «Синхронизация отключена». Панелей управления над таблицами нет, включая Root. Аналитика проверяется каждые 15 секунд и обновляет таблицу при изменении общей даты. Подробности ошибок, история и предупреждения о пропущенном периоде доступны только Root на странице синхронизации.

Изменение только даты проверки не меняет бизнес-версию, статус и аудит подразделения.
События настройки и успешного запуска отправляются через IAuditService;
технические ошибки — через ILogger без полного тела ответа API.

## Проверки

Аналитика отдельно хранит последнюю дату, для которой обновление таблицы успешно завершилось. Временная ошибка получения актуальности не сбрасывает эту отметку: после восстановления связи новая дата вызывает обновление, прежняя — нет. Обработчик `ReloadData` возвращает явный результат загрузки. Списки классификаторов, подразделений и персонала подтверждают только запрос, начатый этим обновлением и применивший данные; ошибка внутри `LoadData`, отмена, вытеснение другим запросом и отсутствие вызова загрузки возвращают отказ. Перед обновлением сбрасывается кеш параметров загрузки Radzen. При отказе или исключении дата не отмечается обработанной, и обновление повторяется при следующей проверке. Первое успешное чтение устанавливает начальную отметку без дублирования первой загрузки таблицы.

Сборка: `dotnet build Guard.slnx --no-restore`.

Проверки без БД: `dotnet run --project Guard.IpRules.Tests/Guard.IpRules.Tests.csproj`.

Интеграционные проверки:
`dotnet run --project Guard.IpRules.Tests/Guard.IpRules.Tests.csproj -- --postgres <путь-к-настройкам>`.
Этот режим допускает только localhost и создаёт собственную временную БД с
префиксом guard_ip_test_ и UUID; она удаляется в finally. Исходная база из настроек
не используется для проверок или очистки.

Фабрика ApplicationDbContextDesignFactory позволяет генерировать и проверять
миграции без запуска приложения и seeding. Применение миграции к целевой среде
и проверка реального API выполняются отдельно от локальных проверок.
