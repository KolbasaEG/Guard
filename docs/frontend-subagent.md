# Инструкция фронтенд-субагенту Guard

Применяй эту инструкцию при создании и доработке списков, форм добавления,
редактирования и просмотра. Образец — текущая реализация `IpAddresses`;
её пользовательское поведение описано в [эталоне компонентов](ip-address-components.md).
Обязательные правила репозитория находятся в [AGENTS.md](../AGENTS.md).
Явные требования пользователя имеют приоритет. Предметные правила области
уточняй до зависимых изменений; независимую работу продолжай.

## 1. Начало работы и границы задачи

1. Прочитай корневой и применимые вложенные `AGENTS.md`, проверь ветку и
   `git status`. Продолжай существующую задачу в её ветке. Для новой задачи
   ветку `codex/<задача>` согласованно подготавливает основной агент по правилам
   репозитория; в общей рабочей директории не переключай ветку параллельно с ним.
2. Зафиксируй разрешённые файлы и существующие изменения. Не сбрасывай их,
   не помещай в stash и не включай автоматически в коммит.
3. Прочитай [Library README](../Guard/Components/Library/README.md), исходники
   подходящих оболочек, их параметры, события и стили, затем компоненты целевой
   области, её сервис, DTO, permissions и правила статусов.
4. Перед изменениями определи: поля и обязательность, права списка/деталей/записи,
   доступные статусы и переходы, область подразделений, поведение Root,
   режим API, необходимость существующего экспорта и ожидаемый результат диалога.
   Не переноси ответы для IP-адресов на другую сущность без проверки.
5. Выполняй только порученный объём. Не добавляй импорт, экспорт, действия,
   зависимости или универсальный CRUD-фреймворк без требования. Недостающий
   серверный контракт обозначь основному агенту; не заменяй его UI-проверкой
   или методом, возвращающим фиктивный успех.

Сохраняй принятое разделение `.razor`, `.razor.cs`, `.razor.css` и namespace соседних
файлов. Чистое представление может содержать небольшой `@code` с параметрами
и вычислением отображаемых значений. Компоненты сущности размещай в
`Pages/<область>/Components`; общие, независимые от сущности — в Library.
Перед расширением Library оцени существующий API; новые параметры делай
совместимыми со старыми вызовами и проверь затронутых потребителей.

## 3. Визуальный контракт

- Используй Radzen и `Forms/CreateEntity`, `Forms/EditEntity`, `Views/ViewEntity`.
  Они используют общий каркас `EntityForm`, `Cards` и `Loading`. Не создавай
  собственные копии заголовка, карточки, кнопок сохранения и индикатора загрузки.
- Компонуй каркас через `RadzenStack Gap="0px"`. Между строками/полями добавления
  и редактирования используй `Gap="5px"`, поля — `RadzenFormField Variant="Variant.Text"`.
  Не размножай внутренние карточки и декоративные отступы.
- Для простых диалогов образец — ширина `640px` с
  `max-width:calc(100vw - 24px)`. Большую ширину выбирай по содержимому задачи.
  Открывай с пустым заголовком Radzen, `ShowTitle = false`,
  `ContentCssClass = "rz-p-1"`: заголовок уже предоставляет Library.
- Просмотр оформляй через `RadzenTable`, `padding:2px` у ячеек, значок и подпись
  слева, значение справа. Для короткой карточки ориентир ширины подписи — 40%.
  Используй перенос длинных значений, `vertical-align:top`, пустые значения «—».
  Ссылочные поля показывай понятным названием, а не техническим GUID.
- Дополнительные сведения показывай через `Views/EntityInfo`; существующий
  `Shared/DialogInfo` поддерживает `Compact=true`. Основная карточка содержит
  предметные данные, служебная — идентификатор, авторов и даты. Время храни в UTC,
  отображай с принятой в проекте локализацией через BrowserTimeService.
- Используй переменные темы Radzen. Стили области изолируй в `.razor.css`;
  `::deep` ограничивай корневым HTML-контейнером. Проверяй контраст кнопок.
- У кнопок со значками должны быть понятные `title` и `aria-label`, у полей —
  подписи, у чисто декоративных значков — `aria-hidden`. Сохраняй клавиатурный
  доступ. На узком экране элементы панели переносятся, подписи читаются,
  диалог помещается в окно; страница не получает лишнюю горизонтальную прокрутку.

## 4. Список, фильтр и загрузка

Сохраняй каркас, локализацию, компактность, пагинацию и оформление кнопок Index.
Статусы центрируй относительно всей панели, а не свободного места между кнопками.
Обновление, область и добавление размещай справа. На узком экране выноси статусы
в отдельную центрированную строку, как в [Index.razor.css](../Guard/Components/Pages/IpAddresses/Index.razor.css).
Если аналитики нет, используй `ShowAnalitycs="false"`: фильтр постоянно занимает
всю ширину. Для IpAddresses принят `TopPaneSize="180px"`; не заполняй пустую
панель заглушкой и не меняй общие значения по умолчанию ради одной области.

Обязательное разделение типов:

```csharp
protected IEnumerable<Entity> data = [];
protected IEnumerable<EntityDto> filteredData = [];
protected RadzenDataGrid<EntityDto> grid = default!;
protected RadzenDataFilter<Entity> dataFilter = default!;
```

`Entity` и `EntityDto` здесь обозначают типы целевой области.
В колонках указывай `Property` DTO и соответствующий `SortProperty` сущности.
Неподдерживаемую сортировку вычисляемых полей отключай.

Последовательность запроса обязательна:

```text
серверная область доступа → статус → выбранная иерархия → применённый фильтр
→ CountAsync → разрешённая сортировка + уникальный ключ → Skip/Take
→ Select DTO → ToListAsync
```

Материализуй результат внутри query-делегата, пока контекст существует. Не загружай
полные графы ради таблицы. Для нового чтения используй сервис и
`IReadRepository.QueryAsync` согласно AGENTS.md; для новых контрактов предпочитай
явные параметры поиска и DTO. Существующие query-делегаты поддерживай совместимо.
`IpAddressService` сейчас использует фабрику контекстов напрямую — это локальная
реализация сервиса, а не разрешение обращаться к DbContext из UI.

- У фильтра `Auto="false"` и одна кнопка «Применить». До её нажатия изменения
  конструктора не влияют на запросы. Снимок должен копировать вложенные условия
  и изменяемые значения, включая массивы; присваивания ссылки недостаточно.
- Разрешай только поддержанные поля, типы значений и операции. Ограничивай
  сложность условий. Если снимок некорректен, сохраняй предыдущий действующий
  фильтр и показывай понятную ошибку. Очистка конструктора + «Применить» снимает фильтр.
- Применение фильтра, смена статуса и области возвращают на первую страницу.
  Обеспечь автоматическую загрузку после готовности grid и каскадного контекста.
  Списки выбора обновляй при получении/изменении контекста, не только при инициализации.
- При новой загрузке отменяй предыдущую. Снимай параметры до первого `await`;
  перед применением результата проверяй отмену, уничтожение компонента и то,
  что запрос ещё актуален. Старый `finally` не должен сбросить загрузку нового запроса.
  При изменении области доступа очищай старые данные и перезагружай их.
- При ошибке актуального запроса очищай недостоверные строки и Count,
  логируй подробности, показывай уведомление. Ожидаемая отмена не является ошибкой.
- Если экспорт уже входит в задачу, передавай ему снимок действующих статуса,
  области, фильтра и сортировки. Экспорт повторно проверяет полномочия на сервере;
  не обещай доступность экспорта лишь на основании доступности таблицы.

## 5. Просмотр, редактирование и жизненный цикл диалога

Клик по строке открывает просмотр (`ReadOnly=true`), отдельная кнопка —
редактирование. У действий строки ставь `@onclick:stopPropagation="true"`.
Допустимо использовать один `Edit` с параметром ReadOnly и отдельными Fields/Details,
как в образце; отдельный файл View нужен только при самостоятельном сценарии.

Используй `AccessDialog` с permissions целевой области. Право записи не отменяет
явный ReadOnly и ограничения статуса. В IpAddresses редактируются только
`Inserted` и `Modified`; наборы допустимых статусов и переходы каждой области
определяй явно. Не сравнивай enum численно. Показывать заблокированную запись
в активном списке не означает разрешать её редактирование.

| Состояние | Поведение |
| --- | --- |
| Первичная загрузка | `isLoading=true`, индикатор, нет ложных пустых деталей и сохранения |
| Данные получены | `isLoaded=true`, представление по праву, статусу и ReadOnly |
| Сохранение | `isSaving=true`, поля и повторный submit заблокированы, значения остаются видны |
| Ошибка сохранения | Значения сохраняются, уведомление, возможность исправить и повторить |
| Закрытие/Dispose | Отмена запроса; поздний ответ не меняет UI и не закрывает другой диалог |

Разделяй эти состояния; блокировку делай и в разметке, и в обработчике отправки.
Не заменяй содержимое формы индикатором при сохранении. Кнопка закрытия остаётся
доступна; кнопку сведений блокируй во время операции, повторное открытие сведений
защищай флагом. Передавай CancellationToken в сервис, отменяй и освобождай CTS.
После `await` проверяй актуальность диалога до Close, уведомления или изменения UI.

При подтверждённом успехе сервиса возвращай `EntityDialogResult(true, id)`;
при отмене — `null`. Родитель показывает успех и обновляет таблицу только после
`EntityDialogResult.IsSuccess(result)`. Просмотр и закрытие крестиком не означают
изменение записи. Не показывай одно уведомление об успехе одновременно в форме и списке.

Валидаторы поля размещай в Helper у FormField и привязывай к точному Name ввода.
Обязательность и формат не должны выдавать две одинаковые ошибки для пустого поля.
Серверная валидация обязательна даже при полностью проверенной форме.

## 6. Доступ и уведомления

Серверный доступ определяют permissions назначенных ролей и область доступа
через принятый для сервиса механизм (`IDataAccessScopeService` или специализированный
сервис области). UserContext, UserAccessSnapshot и DialogAccessState помогают
построить UI, но не заменяют серверные проверки чтения по ID и каждой записи.
Не доверяй переданным из UI подразделению, пути, Root-флагу или признаку редактора.
Проверяй отдельные права на детали, архив и экспорт там, где они предусмотрены.

Различай серверную область и выбранное отображение. «Только свои» и «Свои и
подчинённые» сужают данные также у Root; нет корректного своего подразделения —
пустой результат. В IpAddresses Root может отдельно выбрать «Все доступные»,
включая общие адреса; это явно проверяется сервером. Пустой путь сам по себе
никогда не означает полный доступ. Не переноси IP-исключения Root и правила API
в другие разделы: управление IP и синхронизируемыми справочниками различается.

Ошибки ввода показывай рядом с полем. Информацию о режиме доступа, ошибки операции
и успех показывай через `NotificationService`. Плашки внутри формы не добавляй.
`AccessDialog` уже уведомляет о доступе с защитой от повторов при перерисовке;
не дублируй эти сообщения. Точный стиль каждого уведомления:

```csharp
Style = "position: fixed; top: 3%; left: 50%; transform: translate(-50%, -50%); z-index: 1000;"
```

Пиши сообщения на русском с понятным действием. Ожидаемую прикладную ошибку
показывай через существующий безопасный классификатор `UserOperationErrors`;
не выводи произвольный `Exception.Message`. Подробности записывай через ILogger
без секретов и избыточных персональных данных.

## 7. Что нельзя переносить из образца автоматически

- IPv4/IPv6/CIDR, канонизация, уникальность адреса и общие адреса без подразделения —
  предметная логика IP. Чистый компонент Fields не должен реализовывать её серверную часть.
- `IpListQuery` поддерживает конкретные строковые поля и наборы строк.
  Числа, даты, другие ссылки и типы фильтров требуют явного проектирования
  и проверки перевода в SQL; простой замены имени сущности недостаточно.
- Передача сущности в текущие формы и EF query-делегата из UI — существующий
  контракт, а не основание расширять такую зависимость. Для новых операций
  предпочитай параметры/DTO; не переписывай архитектуру попутно.
- Отмена и защита от позднего ответа решают гонку UI. Они не гарантируют откат
  уже зафиксированной серверной транзакции. Не сообщай пользователю, что данные
  точно не изменились, если результат операции неизвестен.
- У IP-редактирования нет проверки версии записи. Не описывай его как защиту
  от потери изменений при двух редакторах. При требовании конкурентного редактирования
  нужен отдельный серверный контракт и обработка конфликта.
- Загрузка Edit в `OnInitializedAsync` рассчитана на новый экземпляр диалога.
  Компонент, у которого Id меняется без уничтожения, должен реагировать на смену
  параметра и исключать применение старой загрузки.
- В текущем Index режим удалённых записей доступен читателю, а `ExportAccess`
  разрешает их экспорт только Root. Учитывай это при приёмке; согласование этого
  различия требует отдельного решения, не скрытого изменения полномочий.

## 8. Проверки и сдача

Для C#/Razor выполни `dotnet build Guard.slnx --no-restore`; restore нужен при
изменении пакетов или отсутствии восстановленных зависимостей. Не запускай
приложение ради сборки: запуск может создать БД и выполнить seeding. Для проверки
в браузере сначала подтверди назначение среды, не меняя подключения и данные
рабочей БД. PostgreSQL-проверки проводи только на изолированной тестовой БД.

Проверь затронутые сценарии:

- первое открытие и получение каскадного контекста; пустой список и ошибка загрузки;
- применение и очистку фильтра, правку без применения с последующим обновлением,
  сортировкой и переходом страницы; стабильную пагинацию и возврат на первую страницу;
- статусы, оба режима иерархии, Root и пользователя без своего подразделения;
- просмотр по строке, отдельное редактирование без второго диалога, права и статусы;
- валидацию, двойное сохранение, ошибку с сохранением ввода, повторную отправку;
- закрытие при загрузке/сохранении, запоздалые ответы и открытие следующего диалога;
- служебные сведения, длинные/пустые значения, клавиатуру, тему и узкое окно;
- соответствие разрешённого экспорта действующему фильтру, если он затронут.

Для существенных правил доступа и гонок добавляй содержательные тесты по образцу
[IpAddressReferenceTests](../Guard.IpRules.Tests/IpAddressReferenceTests.cs) и
[IpIndexTests](../Guard.IpRules.Tests/IpIndexTests.cs). Простые обратимые визуальные
изменения не требуют тестов, повторяющих разметку. Сборка не заменяет проверку
поведения, а тесты на коллекциях — проверку перевода запроса PostgreSQL.

Перед сдачей проверь diff и отсутствие несвязанных изменений. Отчёт основному
агенту: ветка, изменённые файлы, результат и его назначение, фактически выполненные
проверки, ограничения и нерешённые вопросы. Не заявляй о проверках, которые
не выполнялись. Ветка ожидает проверки пользователя; merge, push и удаление
ветки требуют соответствующего отдельного разрешения.

## Шаблон поручения субагенту
