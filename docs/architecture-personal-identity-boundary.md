# Устранение зависимости сотрудника от Identity

Дата: 17 октября 2026 года. База: `4f4f25f`, ветка `codex/architecture-ip-search`.

Из Personal удалена обратная навигация User типа ApplicationUser. Зависимость теперь направлена от инфраструктурной учётной записи к сотруднику: ApplicationUser.Personal и PersonalId сохранены. Конфигурация использует HasOne(u => u.Personal).WithOne(), прежний уникальный nullable FK и DeleteBehavior.SetNull.

Найдены и обновлены оба исполняемых потребителя навигации: проекция карточки в PersonalService.GetDetailsAsync и тест входа. Карточка сначала получает DTO через прежний защищённый ReadRepository<Personal>, затем при наличии результата читает только Id/UserName связанной учётной записи по PersonalId. Оба результата материализуются до освобождения своих контекстов; запросы последовательны, CancellationToken передаётся в EF. Для отсутствующего или недоступного сотрудника чтение учётной записи не выполняется. Публичный DTO не изменён; Identity-секреты не выбираются.

Это добавляет один запрос по уникальному индексу PersonalId при открытии доступной карточки. Карточка и привязка теперь читаются двумя запросами без общего транзакционного снимка; одновременное изменение привязки может отразиться уже во втором запросе. Новых гарантий согласованности при конкурентных изменениях нет. Списки, поиск и экспорт этого дополнительного запроса не получают. Производительность карточки на полном объёме отдельно не измерялась.

## Реляционная модель и проверки

PersonalIdentityBoundaryTests проверяет метаданные связи и Database.HasPendingModelChanges(): EF сравнивает текущую реляционную модель со снимком последней миграции и не обнаруживает различий. Новая миграция не нужна. Применённые миграции и снимок, включая историческую строковую навигацию User в нём, не редактировались.

Проверки PostgreSQL выполняются только в отдельной временной БД:

- Привязанная учётная запись отображается в карточке; чужой и отсутствующий сотрудник скрыты, отсутствие ReadDetails вызывает отказ.
- Все шесть статусов сохраняют прежнюю видимость обычного пользователя; ReadArchive открывает архивную карточку, Root видит чужого сотрудника без учётной записи.
- Второй пользователь для того же сотрудника отвергается уникальным индексом; несуществующий сотрудник — внешним ключом. Несколько пользователей без сотрудника допустимы.
- Повторные вызовы того же сервиса видят снятие и замену привязки.
- SQL-удаление сотрудника без отслеживаемых сущностей оставляет учётную запись и обнуляет PersonalId на стороне БД.
- Отмена запроса распространяется вызывающему коду; прежние сценарии входа работают через прямую навигацию ApplicationUser.Personal.

Добавлено 22 проверки. Сборка завершилась без ошибок; заключительная инкрементальная сборка — без предупреждений. Полный runner с PostgreSQL: **20 470 проверок**, код завершения 0. Временная БД удалена. Рабочие данные и настройки подключения не менялись. Приложение и браузер не запускались.

## Состав будущего Domain

Повторный просмотр сущностей и enum после удаления навигации показывает следующую границу:

| Код | Назначение при разделении |
| --- | --- |
| BaseEntity, IHasSubdivision, HasFolderEntity, HasArchiveBatchIdEntity; Personal, Subdivision, IpAddress, Classifier | Domain: BCL и связи между предметными сущностями |
| AccountPolicy, SynchronizationSettings/Run, ApiPersonnelExit, ExportJob и связанные модели хранения экспорта | Domain: независимое состояние; существующие атрибуты JSON/DataAnnotations относятся к BCL, EF-конфигурации остаются отдельно |
| Перечисления из Core/0-Enums | Domain: сохранить namespace, числовые значения и совместимость сериализации; два enum синхронизации исторически имеют namespace Guard.Core.Entities |
| ApplicationUser, ApplicationRole | Infrastructure: наследование от ASP.NET Core Identity; прямая ссылка на Personal допустима в направлении Infrastructure → Domain |
| LogEntry | Infrastructure: техническая модель отдельной БД логов |

Таблица фиксирует состав для следующего шага, а не выполненный перенос. Физическое разделение ещё не начато. Следующий конкретный участок — выделить Guard.Domain с указанными независимыми моделями и enum, сохранить полные имена типов и повторить сравнение реляционной модели, сборку и интеграционные проверки. При переносе отдельно проверить поиск типов по сборкам в тестах и сохранность EF-конфигураций; переносить весь Core целиком нельзя. Прикладные контракты и независимые правила доступа относятся к последующему выделению Application. Этапы 1–2 общего плана пока открыты; generic ReadRepository продолжает обеспечивать прежнюю защиту.
