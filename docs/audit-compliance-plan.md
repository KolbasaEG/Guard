**План приведения аудита Guard к согласованным требованиям**

Дата: 20 октября 2026 года. Ветка продолжения задачи: `codex/logging-reliability`.

Статус: реализация подготовлена для проверки пользователем. Текущее поведение, проведённые проверки и ограничения выпуска описаны в [инструкции аудита](audit-operations.md). Рабочая БД не обновлялась; приёмка реальной RuSIEM остаётся эксплуатационным шагом.

Цель — обеспечить полноту аудита аккаунтов и экспорта, обязательное локальное сохранение событий, два режима эксплуатации и запрет обычной работы при неисправном аудите. Это план разработки; описанные ниже гарантии должны появиться после реализации и проверки. Прежнее разрешение продолжать изменения при сбое локального аудита отменено.

**1. Согласованные требования**

| Требование | Локальный режим | Режим с SIEM |
| --- | --- | --- |
| Среда применения | Компания без SIEM | Компания с RuSIEM |
| Локальное сохранение обязательного аудита | Обязательно | Обязательно |
| Отправка событий | Не выполняется | Обязательна, Syslog через TLS с CEF |
| Максимальный возраст неотправленного события | Не применяется | Настраивается Root |
| Ограничение объёма очереди | Не применяется как ограничение доставки | Настраивается; превышение запрещает работу |
| Ошибка обязательного локального сохранения | Запрет обычной работы | Запрет обычной работы |
| Временная недоступность SIEM | Не влияет | Работа допустима, пока очередь в пределах ограничений |
| Просмотр обычных данных | Доступен при исправном аудите, отдельно не журналируется | То же |
| Экспорт | Обязательный аудит | Обязательный аудит и отправка в SIEM |
| Исключения во время блокировки | Выход, узкая диагностика и восстановление Root | То же |

Root выбирает режим, настраивает соединение и срок хранения. Отключение отправки означает переход в локальный режим, а не отключение самого аудита. Общего обхода запрета рабочих операций для Root нет.

Исходный срок хранения технических логов и аудита — один календарный год. Срок хранения журнала и максимальный возраст очереди имеют разное назначение. Два разных срока хранения для режимов не вводятся. Неотправленные обязательные события сохраняются до доставки, даже если срок хранения уже истёк.

**2. Границы и состояние текущей реализации**

Сохраняются .NET 10, Blazor InteractiveServer, Radzen, существующий Unit of Work и разделение сборок. Новая система обработки команд или универсальная переработка репозиториев не требуется.

Текущие наработки используются как основа: таблица `AuditEvents`, журнал Root, отдельный канал аудита, TLS-транспорт, повторная доставка, аренда события обработчиком, фильтрация и очистка. Следующие участки требуют изменения:

| Участок | Текущее ограничение | Требуемый результат |
| --- | --- | --- |
| `AuditJournal`, `AuditService` | Ошибки сохранения подавляются; контракт не подтверждает обязательность | Успешный возврат означает локальное сохранение; ошибка запрещает операцию |
| `UnitOfWork`, прямые записи | Аудит публикуется после сохранения или commit | Изменение и его обязательный аудит фиксируются одной транзакцией |
| `AuditEventData` | Инициатор может подменить затронутый аккаунт | Явное разделение инициатора, объекта и введённого имени аккаунта |
| Identity | Есть пропуски отказов; cookie может выдаваться до аудита | Полное покрытие результатов и правильный порядок выдачи сессии |
| Состояние | Метрик процесса недостаточно для запрета работы | Проверяемая доступность, свежесть данных и общие ограничения очереди |
| Доставка | Нет локального режима и настройки Root | Явные режимы, версии настроек и понятное состояние доставки |
| Очистка | Ошибка доставки или одной БД мешает остальным шагам | Независимые циклы и результаты очистки каждого хранилища |
| UI Root | Есть журнал и небольшая сводка | Подробная диагностика, настройки и ограниченное восстановление |

События и очередь остаются в основной PostgreSQL-БД. БД технических логов и зеркальные файлы не становятся альтернативной очередью, успешная запись в них не подменяет обязательное сохранение аудита. Обычная неисправность технического Serilog-канала сама по себе не равна отказу обязательного аудита.

**3. Этап 1 — каталог событий и правила данных**

Составить проверяемую матрицу: источник операции, успех, отказ, техническая ошибка, обязательные поля, инициатор и объект. Для каждого включённого сценария назначить конкретное место формирования итогового события.

| Группа | Обязательное покрытие |
| --- | --- |
| Вход | Успех, неверный пароль, неизвестный аккаунт, недопустимый запрос, блокировка, истёкший пароль, отказ по IP, недоступность аудита |
| Выход и сессия | Явный выход, принудительный отзыв доступа, недействительный security stamp, прекращение доступа по политике; без приравнивания закрытия вкладки к выходу |
| Аккаунт | Создание, изменение, удаление, блокировка, разблокировка; отказ и ошибка операции; автоматические действия с системным инициатором |
| Пароль | Смена, административный сброс, требование смены, отклонённая попытка, ошибка; без паролей, токенов и хешей |
| Роли | Создание, изменение, удаление, изменение permissions, назначение и снятие роли, отказы по полномочиям и версии |
| IP и доступ | Изменение адресов и назначений, отказ до входа и при новом подключении, отказ в защищённой операции |
| Политики | Безопасные значения до и после изменения; срабатывание автоматической блокировки |
| Экспорт | Запрос, начало обработки, готовность, начало передачи, результат передачи, отмена, отказ и ошибка; срок действия и изменение политики хранения экспорта |
| Сам аудит | Режим, соединение, срок хранения, ограничения очереди, проверка, блокировка, восстановление, результаты очистки и действия Root |

Одна попытка входа имеет один итоговый результат. Сопутствующее событие блокировки или отзыва сессии сохраняется отдельно и связывается общим идентификатором операции. Повторные проверки middleware и circuit не должны создавать несколько одинаковых итогов одной попытки.

Обязательные поля: уникальный `EventId`, UTC-время, версия схемы, стабильный тип, результат, код причины, инициатор и его вид, затронутый аккаунт/объект, IP при наличии, идентификатор операции и безопасная связь с сессией. Введённое имя неизвестного аккаунта не обозначается как подтверждённый UserId. Неизвестные сведения не заменяются выдуманными значениями.

Для значимых изменений безопасности фиксируются безопасные значения до/после: роли, permissions, IP, признаки блокировки и параметры политик. Существующая история предметных сущностей сохраняется; расширение до полной истории всех персональных значений и всех строк импорта в эту задачу не включается. Обычные просмотры и поисковые запросы не создают самостоятельных событий аудита. Чтение метаданных или страниц архива экспорта относится к просмотрам: действующее событие `ExportArchiveViewed` для таких чтений больше не формируется. Выдача файла и остальные события жизненного цикла экспорта сохраняются; события отказа в доступе остаются обязательными.

Неактивные способы входа, например не предоставленные пользователям passkey или внешний вход, не объявляются покрытыми только по наличию enum. При их будущем включении аудит становится условием выпуска.

Критерий завершения: каталог сопоставлен с реальными операциями, поля проверяются на сервере, числовые значения существующих типов событий сохранены, исключены секреты и небезопасное усечение обязательных данных.

**4. Этап 2 — контракты, настройки и схема**

В Domain разместить только независимые значения режимов и состояний, если они нужны контрактам. В Application определить обязательную запись самостоятельного события, проверку допустимости рабочей операции, DTO настроек и состояния, а также отдельные операции Root. EF, Npgsql и HTTP в контракты Application не включать.

Контракт обязательной записи должен иметь явную асинхронную гарантию. Убрать возможность успешной default-реализации через необязательный синхронный метод. Совместимость legacy-вызовов обеспечить проверяемым переходом всех производственных потребителей, а не сохранением скрытого fail-open-пути.

Настройки хранить с версией и доверенными данными автора изменения. Они включают режим, RuSIEM host/port, параметры доверия TLS, срок хранения, максимальный возраст очереди и ограничения её объёма. Местоположение секретов задаётся средствами среды размещения; UI не возвращает их значения.

Расширить существующее хранение для разделения неизменного содержания события и изменяемого состояния доставки. Событие локального режима не считается неотправленной ошибкой: требуется явное состояние «Отправка не требуется». Для обязательной доставки нужны время постановки в очередь, версия назначения, размер учтённых данных, попытки, аренда и результат.

Предусмотреть сохраняемую историю попыток доставки: время, назначение, длительность, результат и безопасная причина ошибки. Её жизненный цикл и индексы согласовать с хранением события; повтор не является новым событием безопасности. Прикладной интерфейс не позволяет исправлять содержание события или удалять отдельные записи вручную. Штатная очистка по сроку выделена отдельно. Защита от администратора самой БД, WORM и криптографическое подтверждение неизменности требуют отдельного решения о среде хранения.

Определение объёма: суммарный размер сериализованных данных обязательных неотправленных событий в байтах; отдельно можно ограничивать их количество. Это не физический размер PostgreSQL-таблицы с индексами. Свободное место и общий размер хранилища контролируются отдельно.

Добавить общие сведения о состоянии очереди и версии конфигурации, необходимые для согласованных конкурентных проверок. Индексы и ограничения должны соответствовать поиску, доставке и очистке. Создать следующую миграцию; применённые миграции не переписывать.

Старые события не получают выдуманного инициатора или подтверждения доставки. Порядок классификации прежних pending-записей выбирается в процедуре выпуска до включения запрета. Настройка режима не определяется автоматически по наличию старого адреса в конфигурации.

Критерий завершения: схема и независимые контракты согласованы; миграция сохраняет старую историю, настройки защищены от потерянного конкурентного изменения, оба режима различимы без анализа текстовых деталей.

**5. Этап 3 — атомарность обязательного аудита**

Создать внутренний механизм Infrastructure, добавляющий событие в тот же `ApplicationDbContext` и транзакцию, что и изменение. Он не открывает независимое соединение для транзакционного события. Для самостоятельного отказа или попытки входа используется отдельная короткая транзакция обязательного журнала.

Порядок записи: начать транзакцию, согласованно проверить режим и очередь, выполнить операцию, сформировать обязательные события, сохранить их с изменением и подтвердить commit. Если ключ сущности требует промежуточного SaveChanges, транзакция остаётся открытой до записи аудита. Любое обязательное событие, не помещающееся в доступный бюджет, отменяет всю операцию.

Поддержать все варианты существующего Unit of Work: явную транзакцию, SaveChanges без предварительно открытой транзакции, синхронные legacy-операции и корректное владение внешней транзакцией. После rollback не остаётся события успеха. Не допускать двойного сохранения одного события при повторном SaveChanges.

Потеря ответа при commit не доказывает откат: изменение и аудит могли сохраниться вместе. Ввести исход «результат подтверждения неизвестен», устойчивую связь с идентификатором операции и сверку после восстановления. Не сообщать об откате без доказательства и не повторять неидемпотентную команду автоматически. Для повторяемых команд определить защиту от повторного выполнения.

Отдельно адаптировать Identity, `RoleAccessService`, `SecurityService`, `AccountPolicyService`, прямые IP-операции, экспорт и синхронизацию. Общая замена только Unit of Work эти пути не покрывает. Сохранить `PrepareAudit`, доверенного автора, проверки `IdentityResult` и существующие блокировки предметных операций.

Согласовать порядок блокировок очереди, ролей, политик и предметных данных, чтобы новый механизм не добавил взаимные блокировки. Не удерживать транзакцию и блокировку очереди во время TLS, генерации файла или передачи клиенту.

Ошибка обязательного аудита возвращает отдельный прикладной результат недоступности, переводит работу в запрещённое состояние и диагностируется независимым каналом. Рекурсивная попытка записывать ошибку аудита через тот же отказавший журнал запрещена. Зеркальный Serilog-канал остаётся диагностическим.

Критерий завершения: внедрённый отказ вставки аудита до commit откатывает изменение, включая промежуточные Identity-записи, пароль, stamps и роли. Изменения БД и их обязательные события сохраняются атомарно. Для внешних действий сохраняется начало, а результат при невозможности последующей записи остаётся неизвестным; они не включаются в гарантию атомарности БД.

**6. Этап 4 — состояние и контроль очереди**

| Состояние | Доступность |
| --- | --- |
| Первичная проверка не завершена | Рабочие операции запрещены |
| Локальный аудит исправен в локальном режиме | Разрешены |
| Локальный аудит и доставка исправны в режиме SIEM | Разрешены |
| SIEM недоступен, очередь в пределах ограничений | Разрешены; Root видит предупреждение |
| Возраст либо объём превысил предел | Запрещены |
| Нельзя надёжно сохранить обязательное событие | Запрещены в обоих режимах |
| Состояние неизвестно или его проверка недостоверна | Запрещены |

Проверка исправности должна подтверждать возможность обязательной записи, а не только успешный SELECT. Проверку очереди нельзя считать свежей, если обработчик остановился или обновление не завершилось. Нулевая очередь и неизвестная очередь — разные состояния. Эти показатели доставки влияют на допуск только в режиме SIEM. В Local остановленный отправитель, устаревшие показатели SIEM и сохранённая прежняя очередь не запрещают работу; обязательная проверка локального сохранения продолжает действовать.

Возраст отсчитывается от доверенного времени постановки события в очередь. Повторные попытки и перезапуск его не обнуляют. При равенстве пределу значение допустимо, превышение запрещает работу. Для объёма проверяется также событие текущей операции: операция, создающая превышение, не подтверждается.

Согласование вставки и бюджета выполнить средствами PostgreSQL. Проверки на одном экземпляре приложения не должны разрешать обход при работе другого экземпляра. Кэш не является самостоятельным источником разрешения и не маскирует обнаруженный отказ; допустимую задержку проверки явно определить и испытать.

Порог очереди ограничивает обычные операции, но не останавливает отправку и не удаляет события. Для отказов, выхода, проверки и восстановления предусмотреть служебный резерв. Резерв конечен: при полном отказе хранилища успешное сохранение этих событий не обещается; выход и диагностирование должны оставаться доступны. Защита от потока неуспешных входов не должна молча выбрасывать обязательные события.

Численные значения максимального возраста, байтов и количества событий пока не выбраны. Их задаёт Root; для SIEM-режима валидные обязательные пределы должны быть указаны до активации. Нулевое значение не означает скрытое отключение ограничения.

Критерий завершения: пограничные значения, конкуренция, перезапуск, остановка обработчика и неизвестное состояние дают воспроизводимые результаты; блокировка и причина понятны Root.

**7. Этап 5 — запрет рабочих операций и восстановление**

Серверная проверка доступности охватывает чтение списков и карточек, поиск, изменение данных, административные команды, экспорт и прямые endpoints. Обычные permissions и область данных проверяются дополнительно и не заменяются состоянием аудита. Root не получает освобождения для обычных данных.

HTTP middleware даёт ранний отказ и понятную страницу состояния. Уже открытый Blazor circuit получает обновление интерфейса, а сервис повторно проверяет доступность каждой операции. Полная остановка всех circuit-событий недопустима: она закроет выход и восстановление. Запрещён произвольный публичный параметр bypass от клиента.

Для чтения проверить доступность до запроса и перед возвратом данных; для изменения — до начала и в транзакционной точке подтверждения. Длительные задания и передачи проверяют состояние в предусмотренных точках. Сеть нельзя сделать атомарной с БД: уже показанные данные или переданные байты не отзываются.

Выход всегда доступен. Диагностика и восстановление Root реализуются отдельным узким серверным контрактом, который проверяет действительную сессию, stamp и актуальный Root без рекурсивного обращения к обычному запрету. Подделанная cookie или скопированное permission не дают доступ.

Предлагаемый порядок при отказе локального журнала: веб-диагностика доступна Root только при возможности достоверно проверить его актуальные права и stamp; изменения настроек требуют доступного обязательного аудита. Восстановление БД, диска и служебной учётной записи выполняется средствами обслуживания сервера. Если требуется новый вход Root при отказавшем аудите, это отдельный вход только в диагностику с серверным ограничением всех остальных операций; обычная рабочая cookie не выдаётся. При недоступной БД Identity сохранённая cookie сама по себе не открывает защищённую диагностику: остаются безопасная публичная страница отказа, выход и внешнее обслуживание сервера. Независимая аутентификация восстановления потребовала бы отдельного согласованного механизма.

Блокировка аудитом не должна сама отключать проверку политики аккаунта. Автоматическое выявление недопустимого состояния пользователя продолжает запрещать ему доступ, даже если запись изменения блокировки временно невозможна. Отделить вычисление запрета от побочной записи в `AccountPolicyService.CheckAsync`, чтобы восстановление не провоцировало рекурсию и рабочие изменения.

Предлагается приостанавливать новые задания синхронизации и экспорта при общем запрете. Доставка аудита, проверка состояния, безопасная очистка и необходимое завершение уже начатых попыток продолжаются. Эти операции имеют закрыто определённую область, а не общий обход для всех workers.

Критерий завершения: прямой сервисный вызов, endpoint, старый circuit и фоновая задача не обходят запрет; выход и разрешённая диагностика Root остаются доступны.

**8. Этап 6 — вход, пароли, сессии и роли**

Разделить проверку пароля и выпуск сессии так, чтобы подтверждённый обязательный аудит предшествовал рабочей cookie. Изменения счётчиков неуспешных попыток и автоматической блокировки участвуют в согласованной транзакции. Не менять существующие правила IP, Root, паролей и блокировок попутно.

«Вход разрешён сервером» не означает, что браузер получил cookie. При ошибке её выдачи фиксировать отдельный результат, если хранилище доступно. Проверить все действующие способы обновления cookie, включая смену своего пароля, а не только страницу Login. Ошибка обновления cookie после подтверждённой смены пароля не возвращает прежний пароль; интерфейс предлагает вход с новым паролем и не сообщает о несуществующем откате. Если последующая запись ошибки недоступна, соответствующий внешний результат остаётся неизвестным.

Зафиксировать отказы `NotAllowed`, истёкший пароль, неразрешённый IP, блокировку и неподдерживаемый способ входа без раскрытия существования аккаунта в публичном ответе. Изменение пароля, административный сброс, роли и политика не могут завершаться без обязательного события в их транзакции.

Различать системного инициатора автоматической блокировки, пользователя, вызвавшего проверку, и затронутый аккаунт. Не создавать массово одинаковые события отзыва для каждого последующего HTTP-запроса одной уже завершённой сессии.

Критерий завершения: негативные сценарии не выдают рабочую cookie; отказ обязательного транзакционного аудита до commit сохраняет прежний пароль, stamps, роли и данные; сбой cookie после commit трактуется отдельно; инициатор и цель корректны при действиях Root над другим пользователем.

**9. Этап 7 — обязательный аудит экспорта**

Связать события с JobId, инициатором, фактическим IP запроса, безопасным описанием выборки и областью данных. Не включать содержимое выгрузки и избыточные персональные значения фильтра. Для готового артефакта хранить количество записей, размер и существующий контрольный хеш.

Создание задания и аудит запроса фиксируются атомарно. Подтверждение готовности и её событие также согласованы. Файл, созданный до отката БД, не становится доступным без подтверждённой готовности; предусмотреть очистку такого артефакта.

Перед первым байтом клиенту сохранить начало выдачи вместе с записью попытки. При отказе этой записи не открывать передачу. Проверять доступ и исправность перед выдачей и во время длительной передачи; использовать IP текущего запроса скачивания, а не только IP создания задания.

Результат фиксируется после передачи. Успех означает завершение серверной передачи, а не прочтение файла пользователем. При аварии между началом и окончанием оставлять видимую попытку с неизвестным результатом, а не выдумывать успех или ошибку. Предусмотреть восстановительную сверку зависших попыток после перезапуска.

Критерий завершения: файл не выдаётся без сохранённого начала аудита; ошибки, отмена, разрыв клиента, отзыв доступа и сбой финальной записи различимы.

**10. Этап 8 — RuSIEM, режимы и настройки Root**

Сохранить Syslog через TLS с CEF и проверкой имени, доверия, срока действия и прочих применимых проверок сертификата. Не добавлять режим принятия любого сертификата. Проверить полноту полей, экранирование, UTF-8 и используемое разделение сообщений на локальном TLS-приёмнике и в целевой RuSIEM.

Обрабатывать события без открытой бизнес-транзакции, с арендой, таймаутами и повторными попытками. После падения процесса событие становится доступным повторно. Устойчивый EventId позволяет выявлять дубликаты; точную однократную доставку не обещать.

Успешная запись в TLS не подтверждает приём и сохранение RuSIEM. В UI и документации использовать точный статус «Отправлено по TLS». Проверка EventId в RuSIEM входит в приёмку интеграции. Если потребуется обязательное подтверждение приёма, это отдельное требование к протоколу и интеграции.

Настройки доступны только актуальному Root. Включение SIEM требует валидных параметров и пределов очереди. Проверка соединения не должна зависеть от разрешения обычных рабочих операций. Настройки изменяются с версией и аудитом; неудачный тест не заменяет действующую конфигурацию молча.

Локальный режим отключает влияние SIEM-очереди на рабочую доступность. Ранее обязательные неотправленные события не удаляются и не объявляются доставленными. Смена режима, снижение лимита и смена адресата выполняются после показа последствий для очереди; режим фиксируется согласованно с параллельными операциями и текущими отправками.

Следующие детали переключения вынесены на решение в пункт 17: доставка событий, созданных локально, судьба прежней очереди во время локального режима, смена назначения и автоматическое возобновление работы. До решения их не подменять неявным поведением.

Критерий завершения: оба режима работают после перезапуска; в локальном режиме адрес SIEM не обязателен; клиент без Root не меняет настройки; переключение не теряет историю и очередь.

**11. Этап 9 — хранение, очистка и эксплуатационная ёмкость**

Срок хранения настраивается Root. Исходно используется календарный год; это не максимальный возраст очереди. Уменьшение срока показывает дату отсечения и последствия, сохраняется в аудите и не запускает неограниченное синхронное удаление из формы.

Локальные события с состоянием «Отправка не требуется» удаляются по сроку. Доставленные обязательные события удаляются по сроку. Неотправленные обязательные события сохраняются до доставки, в том числе при временном переходе в локальный режим. Базовое правило отсечения — возраст события; необходимость дополнительного хранения после поздней доставки отражена в пункте 17.

Разделить циклы доставки, очистки аудита, технической БД и принадлежащих приложению файлов. Ошибка одного цикла не останавливает остальные. Ограничить пакет и длительность транзакции, предусмотреть догоняющую очистку и показатели её отставания.

Согласовать файловую ротацию с настраиваемым сроком, чтобы прежний фиксированный предел 366 дней не удалял данные раньше выбранного срока. Различать авторитетный журнал в БД и вспомогательную файловую копию; защита pending обеспечивается в БД. Посторонние файлы не удаляются.

Оценить требуемое место и пропускную способность по измеренному потоку. Отдельно показать объём истории, pending, свободное место там, где оно доступно приложению, и ограничения наблюдаемости управляемой PostgreSQL. Приближение к заполнению требует предупреждения; невозможность обязательной записи запрещает работу.

Критерий завершения: оба режима очищаются корректно; pending не удаляется; сбой SIEM либо технической БД не останавливает очистку доступного хранилища; нагрузка не создаёт неограниченно растущий долг очистки.

**12. Этап 10 — интерфейс состояния и журнал Root**

Использовать существующий раздел Audit и библиотеку компонентов Guard. До изменения форм изучить `Components/Library`; соблюдать жизненный цикл InteractiveServer, отмену загрузки, снимок применённого фильтра, стабильную сортировку и пагинацию.

| Блок | Сведения для Root |
| --- | --- |
| Общая доступность | Режим, статус, причина запрета, начало и последнее изменение состояния |
| Локальная запись | Последняя проверка и успешная запись, последняя безопасная ошибка, время ошибки |
| Очередь | Количество, байты, старейшее событие, возраст, заданные пределы, приближение к ним |
| Доставка | Последняя отправка, ошибка, повторы, следующая попытка, текущие аренды |
| Обработчики | Последний завершённый цикл, задержка обновления, остановка, восстановление |
| TLS | Активное назначение, версия настроек, последний тест, наблюдаемые сведения о сертификате |
| Хранение | Срок, дата отсечения, последний цикл, число удалённых записей, ошибка и отставание |
| Настройки | Действующие безопасные значения, автор и время изменения; без секретов |

Показывать «неизвестно» и «данные устарели», а не зелёный статус по последней удачной проверке. Для локальных событий отображать «Отправка не требуется». В карточке различать дату события, постановку в очередь, отправку, причину отказа и безопасные сведения о попытках. Требуемая детализация попыток должна действительно сохраняться, а не вычисляться из одного последнего сообщения.

Предусмотреть обновление панели без ручной перезагрузки, с ограниченной частотой и отменой при закрытии. Недоступность основной БД не должна приводить к бесконечному спиннеру: Root получает независимые сведения о самом отказе, насколько позволяет доступная инфраструктура.

Для обычного пользователя показать русское сообщение о временной недоступности, возможность обновить состояние и выйти. Внутренние исключения и параметры соединения ему не раскрывать.

Критерий завершения: Root понимает, что отказало, когда, какие данные достоверны и какое восстановление допустимо; нет общего обхода рабочих операций.

**13. Матрица проверок**

| Направление | Сценарии и ожидаемый результат |
| --- | --- |
| Правила | Два режима, границы возраста и объёма, неизвестное состояние, корректный UTC и ход времени |
| Атомарность | Отказ аудита до/после промежуточного SaveChanges; полностью отменённые данные и отсутствие успеха; потеря ответа commit даёт неизвестный исход и сверку без слепого повтора |

Использовать существующие исполняемые Check-runner. Для времени и отказов применять управляемые источники и детерминированные точки отказа вместо длинных ожиданий. Испытания отказов локального хранения и наполнения выполнять только в предназначенной изолированной среде.

Последовательность выполнения: `dotnet build Guard.slnx --no-restore`, `./scripts/Test-Guard.ps1`, затем `-Mode Postgres` и `-Mode Browser` в безопасном стенде. Restore нужен только при необходимости зависимостей. Сборки и тестовые стенды не запускать конфликтующим образом параллельно.

PostgreSQL-проверки используют временную БД с проверкой локального адреса. Browser-стенд использует временные БД, каталог и порт 5079. Обычный Program не запускать для проверки сборки. Итоговые числа проверок публикуются только по фактическому запуску актуальной реализации.

Реальная RuSIEM проверяется отдельно: совпадение EventId и полей, outage и повторная отправка, распознавание CEF, дубликаты и скорость приёма. Локальный TLS-тест не заменяет эту приёмку.

Координатор владеет общими контрактами, миграцией, ModelSnapshot, Program, регистрациями DI и тестами. Одновременно исходники меняет один исполнитель. Профильное делегирование допускается в точной области по правилам репозитория; независимая проверка guard_security обязательна для готовых изменений входа, доступа и восстановления Root.

При изменении DI учитывать Scrutor и время жизни сервисов: обязательный writer и singleton-обработчики не должны случайно перерегистрироваться scoped-сервисами или захватить scoped-контекст. Application по-прежнему зависит только от Domain и BCL. Несвязанные незавершённые изменения сохраняются.

1. Согласовать открытые правила из пункта 17 и подготовить эксплуатационные значения. Выбрать режим явно до допуска рабочих пользователей.

3. Подготовить следующую миграцию и SQL-проверки совместимости. Старые записи классифицировать без потери, фиксируя переход. Не смешивать старый writer, подавляющий ошибки, с новым обязательным режимом во время выпуска.
4. Отдельной разрешённой эксплуатационной процедурой применить схему. Не выполнять автоматическую миграцию, seeding или очистку рабочей БД ради разработки.
5. Установить приложение, проверить локальную обязательную запись, режим, права Root, серверный запрет, выход и восстановление. В SIEM-режиме проверить сертификат, тестовое событие и его наличие в RuSIEM.
6. На стенде подтвердить короткую недоступность RuSIEM, рост очереди, достижение порогов, блокировку, доставку после восстановления и правила возобновления.
7. Включить обычный доступ только после положительной проверки состояния и обязательных сценариев. Передать инструкции и наблюдение ответственному оператору.

Откат бинарной версии не должен незаметно возвращать разрешение изменений при отказе аудита. При невозможности безопасного отката сохранить ограничение доступа и очередь до исправления. Удаление новых таблиц через Down не используется как эксплуатационное восстановление.

Внешнее наблюдение должно обнаруживать недоступность самого приложения и хранилища, когда веб-панель Root недоступна. Канал таких оповещений не должен зависеть только от того же RuSIEM. Конкретный внешний канал выбирается со средой размещения; его настройка не считается выполненной наличием внутренних метрик.

**16. Критерии окончательной приёмки**

- Все действующие операции аккаунтов и экспорта имеют предусмотренные события и корректные результаты.
- Инициатор и затронутый аккаунт различимы; секретов в событиях, UI и диагностике нет.
- В обоих режимах изменение не подтверждается без обязательного локального аудита.
- Локальный режим не зависит от наличия RuSIEM и возраста её очереди.
- В SIEM-режиме допустимая временная недоступность не мешает работе; превышение любого действующего порога запрещает обычные операции.
- Блокировка действует на чтение, запись, экспорт, старые подключения и фоновые изменения; Root не получает общего обхода.
- Выход и согласованный ограниченный путь восстановления доступны в заявленных границах инфраструктуры.
- Перезапуск и смена режима не теряют историю и обязательную очередь.
- Root видит режим, свежесть состояния, причины, пределы, попытки, ошибки и результаты очистки.
- Срок хранения применяется корректно, неотправленные обязательные события не удаляются.
- Изолированные проверки и независимое security-ревью завершены; реальная RuSIEM принята отдельно.
- Ветка с актуальным результатом представлена пользователю. Merge, push и применение к рабочей среде выполняются только по соответствующему разрешению.

**17. Согласованные решения**

Правила Local, сохранения прежней очереди, явного подтверждения переноса, автоматического восстановления и ограниченного входа Root подтверждены пользователем. Реализация и эксплуатационные ограничения описаны в [инструкции аудита](audit-operations.md).

| Вопрос | Принятое правило | Затронутая область |
| --- | --- | --- |
| События, созданные в локальном режиме | Сохранять локально, не отправлять автоматически после включения SIEM; явная историческая отправка — отдельная возможность | Классификация событий и переход Local в SIEM |
| Прежняя обязательная очередь после перехода в локальный режим | Сохранить без удаления, приостановить отправку; возобновить после включения SIEM. Возраст не обнулять | Переключение режима и обработчик |
| Возобновление после восстановления | Автоматически после достоверной успешной проверки и возврата в допустимые пределы; переход журналировать. Отключение SIEM снимает только ограничения доставки | Проверка состояния и UI |
| Смена адресата при pending | Переносить только после отдельного подтверждения Root; без него отклонять изменение назначения | Версии назначения и доверие TLS |
| Блокировка во время выполнения | Новые операции запрещать, чтение перепроверять перед возвратом, длительную передачу прекращать в точках проверки, начатую запись перепроверять до commit | Обработка длительных операций |
| Восстановление Root при отказе локального журнала | Защищённая диагностика требует проверки актуального Root через доступную Identity-БД; иначе публичный отказ, выход и обслуживание сервера. Изменение настроек только при возможном аудите. Отдельно согласовать вход Root только в диагностику | Специальная аутентификация и эксплуатация |
| Фоновые изменения | Приостановить рабочую синхронизацию и новые экспорты; продолжать доставку, безопасную очистку и вычисление запрета доступа по политике | Workers и проверки политики |
| Численные параметры | Root задаёт возраст, байты и при необходимости количество; допустимые диапазоны, предупреждения и начальные значения выбрать по нагрузке и допустимому простою | Валидация, активация SIEM и нагрузочная приёмка |
| Поздняя доставка старого события | Основной срок считать от даты события; после доставки просроченная запись попадает в штатную очистку. Если нужен дополнительный срок после отправки, задать его отдельно | Очистка и эксплуатационный объём |

Этот план заменяет прежнее требование о разрешении изменений при отказе аудита. Описание ранее реализованного состояния остаётся историей; готовность новой модели определяется критериями пункта 16.
