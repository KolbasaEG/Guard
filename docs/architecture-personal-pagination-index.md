# Индекс для пагинации сотрудников

Дата: 17 октября 2026 года. Ветка: `codex/architecture-ip-search`.

## Причина и изменение

На согласованном стенде (200 тыс. сотрудников, 1 тыс. подразделений, **500 тыс. IP**,
экспорт 100 тыс. строк) глубокая страница сотрудников занимала около 1,16 с.
`PersonalService.SearchAsync` использует общий запрос `ExportQueries.PersonalsAsync`:
область доступа, статус, иерархия и фильтр, Count, сортировка, Skip/Take и DTO.
Порядок по умолчанию — LastName, FirstName, Id. Соответствующего индекса не было.

Добавлен неуникальный частичный B-tree `IX_Personals_ActiveName` по
`("LastName", "FirstName", "Id") WHERE "Status" IN (1, 2, 3)`.
Это точный существующий набор активного списка: Inserted, Modified, Blocked.
Повторяющиеся ФИО разрешены, Id сохраняет стабильный порядок.
Прикладной запрос, правила доступа, DTO и интерфейс Radzen не изменены.

Индекс поддерживает текущий порядок по умолчанию и явную LastName asc.
Он не предназначен для ускорения архива, удалённых записей, поиска по подстроке
или всех остальных сортировок. В частности, LastName desc с последующими FirstName/Id asc
не совпадает с обратным проходом этого индекса. Глубокий OFFSET по-прежнему читает
пропускаемые записи; точный Count остаётся отдельной операцией. Новые индексы
для каждого фильтра и курсорная пагинация этим изменением не вводятся.

## Проверка

Сборка успешна. Полный функциональный прогон: **4 711 unit + 21 073 integration = 25 784**.
Пересборка Web показывает 25 прежних предупреждений; последняя инкрементальная — 0.

`PersonalPaginationIndexTests` на временной PostgreSQL-БД проверяет откат до миграции
ключей IP и повторное применение индекса на существующих данных. До/после совпадают
Count и все поля DTO для первой/поздней страницы, архива, удалённых записей,
обратной сортировки и фильтра. Отдельно проверены одинаковые ФИО с порядком Id,
отсутствие пересечения страниц, обычная область подразделения и запрет AllSubdivisions
для пользователя без Root. Все 42 миграции обнаруживаются в прежнем порядке,
SQL генерируется без подключения, модель соответствует snapshot.

## Измерения

`ArchitectureBenchmark` сравнивает один набор данных до и после индекса во временной БД.
Для исходного состояния он явно удаляет только новый индекс из этой БД, затем создаёт
его обратно и выполняет ANALYZE. SQL берётся через EF CreateDbCommand с параметрами;
EXPLAIN ANALYZE BUFFERS использует обычные настройки планировщика, без отключения Seq Scan.
Отдельно измеряются Count и DTO-страницы, затем настоящий PersonalService.SearchAsync.
Permissions и область в последнем случае заданы фиксированными Root-заглушками;
стоимость реального чтения прав и HTTP в замер не входит.

Первый вызов отделён от медианы пяти прогретых. Это локальный Debug .NET 10.0.12,
12 логических CPU, синтетические имена с повторениями. Результат не является SLA.
Естественный план до индекса сортирует сотрудников; глубокая страница использует
quicksort в памяти, а не сброс сортировки на диск. После индекса PostgreSQL сам
выбирает Index Scan по IX_Personals_ActiveName и не выполняет сортировку сотрудников.

Итоговый повторный прогон завершился с кодом 0, временная БД и экспортные файлы удалены.
Локальный лог: `Guard/obj/personal-pagination-benchmark-final.log` (не входит в Git).

Глубокая DTO-страница ускорилась примерно в 29 раз. Медианы независимых измерений

также завершил экспорт ровно 100 тыс. строк: snapshot 1768,5 мс, XLSX/ZIP 2553,5 мс.
Разброс других операций не является доказательством ускорения или регрессии этим индексом.

## Выпуск и откат

Миграция `20261017160000_AddPersonalActiveNameIndex` только создаёт индекс;
Down только удаляет его. Бизнес-поля, связи, аудит и значения статусов не меняются.
Новая миграция ещё **не применена к рабочей БД**.

Обычный CREATE INDEX в транзакционной миграции блокирует запись в Personals на время
построения; существующее чтение допускается. Выполнить в согласованном окне обслуживания
после резервного копирования и проверки целевой БД штатным инструментом выпуска.
Размер индекса и длительность его построения на рабочем оборудовании не измерены.
Цена индекса — дополнительное место и обслуживание при смене ФИО/статуса.
Откат этой миграции к `20261017120000_AddIpCanonicalKeys` возвращает прежнюю
производительность без изменения данных или отката приложения. Откат предыдущих
ключей IP требует отдельного порядка из [инструкции каталога IP](ip-catalog-canonical-keys.md).

Браузерная проверка ключевых экранов после всей серии архитектурных переносов
и пользовательская приёмка ветки остаются перед слиянием.
