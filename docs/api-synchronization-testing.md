# Запуск и проверка синхронизации в закрытой сети

## Проверки восстановления страницы без БД и API

Запустите `dotnet run --project Guard.IpRules.Tests/Guard.IpRules.Tests.csproj`.
`SynchronizationRecoveryTests` использует подставные сервисы и HtmlRenderer:
проверяет независимость загрузки настроек и истории, ручное и автоматическое
повторение после ошибки, сохранение версии и введённых полей, блокировку
сохранения до перечитывания настроек после успешной записи, последовательное
обновление при наложении запросов и отмену при закрытии страницы.
Ошибку истории интерфейс отличает от пустого списка запусков.
История остаётся доступной при устойчивой ошибке чтения настроек. До первого
успешного ответа показывается загрузка, а пустое состояние — только после
успешного пустого ответа. Последняя попытка берётся из первого элемента истории.
Каждый фоновый цикл проверяет необходимость восстановления истории, даже если
общая сводка недоступна. При ошибке чтения по изменению запуска повтор переносится
на следующий цикл; исправная история без изменений повторно не читается.
Проверки вызывают тот же метод одного цикла, что и 15-секундный таймер, и включают
одновременный сбой сводки и истории, наложение ручного обновления и закрытие панели.

Эти проверки не запускают приложение и не обращаются к реальным БД или API.
Они не заменяют проверку переключения вкладок во время диагностики в работающем
Blazor-соединении на предназначенном для проверки окружении.

## Диагностика полного ответа с обязательной датой

Регрессионные проверки разделения блокировок входят в
`ApiSynchronizationIntegrationTests` и запускаются существующим режимом
`--postgres` (см. `docs/ip-access.md`). Используются временная БД, настоящий
`ExportWorker` с пустой очередью и подставной API. Проверяются диагностика и
синхронизация при занятой блокировке экспорта, исключение второго владельца
этой блокировки, её освобождение и получение новым обработчиком, взаимное
исключение диагностики и синхронизации (включая постановку в очередь), а также
повторная диагностика после отмены. Ожидание ограничено по времени.

При обновлении остановите все старые экземпляры Guard перед запуском новых:
прежний обработчик экспорта использовал ключ синхронизации. Новый ключ экспорта
и порядок обновления описаны в `docs/data-export.md`; миграция БД не требуется.

Диагностика доступна только Root на `/synchronization` в блоке «Диагностика API без применения данных». Это отдельная операция: основная БД только читается; импорт, архивация, история синхронизации и отметки актуальности не изменяются. Новых миграций для диагностики нет. Сохраните уже действующие настройки API, затем:

1. Обновите сборку и перезапустите Guard в предназначенной среде. Выберите уровень логирования Information (Debug и чувствительное EF-логирование не требуются). Не меняйте уровень до окончания диагностики.
2. Укажите обязательную раннюю дату UpdatedAt, предшествующую внесению данных в источник. Она отправляется как `yyyy-MM-dd` на каждой странице всех трёх ресурсов. Диагностика не требует `CompleteSnapshotGuaranteed`: она не применяет данные и не подтверждает полноту API.
3. Нажмите «Запустить диагностику». Сначала читаются все страницы classifiers, subdivisions, personnel. После загрузки проводится анализ всего набора с накоплением ошибок, без остановки на первой некорректной записи. Пагинация, JSON и HTTP должны быть корректны; иначе набор помечается как неполный. Диагностика и обычная синхронизация используют общую глобальную блокировку PostgreSQL, включая несколько экземпляров Guard.
4. Дождитесь результата и запишите идентификатор протокола. «Все страницы получены: да» и «Анализ завершён: да» означают, что получение и анализ завершены, а не что API гарантированно вернул всю организацию. Кнопка отмены, уход со страницы или остановка соединения могут прервать операцию; такой результат не считается завершённым анализом.
5. Дождитесь доставки накопленных событий в БД логов. При необходимости штатно остановите приложение для завершения доставки. Перенесите БД логов и сообщите идентификатор протокола. Если в перенесённой БД нет конца протокола, нельзя считать её полной копией результата.

Все события операции, включая запросы HTTP-клиента, связаны свойством `DiagnosticRunId` в `properties.Properties`. Для поиска:

```sql
SELECT timestamp, level, message, properties
FROM logs
WHERE properties->'Properties'->>'DiagnosticRunId' = '<идентификатор протокола>'
ORDER BY timestamp;
```

Протокол содержит обязательную дату, размер страницы и версию настроек, страницы и попытки HTTP, количества трёх ресурсов, корневые ID, все нарушения и сводку по их типам. Конец протокола содержит `FetchComplete`, `AnalysisComplete`, `DiagnosticIssueCount` и длительность. При ошибке записываются этап, тип исключения, HTTP-статус и признак отмены; сырой ответ и текст исключения десериализации не записываются, так как могут содержать данные источника.

Каждое нарушение содержит `ApiResource`, `ExternalRecordId`, `DiagnosticField`, `DiagnosticIssueCode`, `ExternalReferenceId` и `FoundLocally`. Имена, адреса, личные номера, значения полей и credentials не включаются. Основные коды:

| Код | Значение |
| --- | --- |
| MissingParentInResponse | ParentId отсутствует среди полученных подразделений |
| MissingSubdivisionInResponse | Подразделение сотрудника отсутствует в ответе |
| MissingClassifierInResponse | Пара Type/Code отсутствует в полученных классификаторах |
| DuplicateId / DuplicateKey | Повтор внешнего ID или справочной пары |
| SelfReference / CycleInResponse | Ссылка на себя или цикл дерева ответа |
| CycleWithLocalData | Цикл после объединения полученного дерева с ранее импортированным |
| Required / TooLong / InvalidId / InvalidState / InvalidNumber / OutOfRange / IncompletePair | Некорректное поле или неполная справочная пара |

Для Missing-кодов `FoundLocally=true` означает, что ссылка может разрешаться ранее сохранёнными данными. Это отличается от отсутствия записи и в ответе, и локально. Число нарушений включает такие ссылки и оба варианта проверки циклов; оно не является количеством уникальных повреждённых записей. Диагностика фиксирует наблюдаемые нарушения, но без контракта источника не может доказать, почему родитель не возвращён (дата, права, архив или технический корень).

Инструкция относится к реализации в ветке `codex/api-synchronization`.
Все действия с данными выполняйте на выделенной тестовой БД Guard и тестовом источнике API.

Для текущей версии дополнительно примените миграции `AddSynchronizationUpdatedSince` и `AddApiExitEventsAndQueue` и `AddApiRecoveryWindow`: они сохраняют дату запроса, серверную очередь, отметки событий и контрольные даты.

## 1. Подготовка первого запуска

1. Подготовьте сборку приложения с актуальными миграциями. На машине с доступными зависимостями выполните восстановление, сборку и публикацию:

   ```powershell
   dotnet restore Guard.slnx
   dotnet build Guard.slnx --no-restore
   dotnet publish Guard/Guard.csproj -c Release --no-restore -o artifacts/guard
   ```

   Перенесите весь каталог публикации в закрытую сеть. Для обычной публикации на сервере нужен ASP.NET Core Runtime .NET 10; для запуска из исходников — SDK .NET 10. Зависимости NuGet должны быть подготовлены до переноса или доступны из внутреннего источника.

2. Проверьте настройки основной БД и БД логов. Они должны указывать на предназначенную для проверки среду. Сделайте резервную копию основной БД до миграций и первого импорта. Не запускайте приложение с неизвестными подключениями: при старте оно проверяет существование БД и создаёт структуру логов.

3. Примените актуальные миграции к тестовой БД существующим порядком развёртывания. В Development приложение выполняет миграции и seeding; в Production автоматическое применение миграций в текущем старте не вызывается. Для отдельного применения можно заранее подготовить SQL:

   ```powershell
   dotnet ef migrations script --idempotent --project Guard/Guard.csproj --context ApplicationDbContext --output artifacts/guard-migrations.sql
   ```

   Проверьте скрипт и выполните его инструментом PostgreSQL именно на тестовой БД. Команда требует установленного `dotnet-ef`, совместимого с EF Core 10. Фабрика design-time использует служебный адрес `guard_design`; не используйте `dotnet ef database update` без явного определения целевого подключения. После применения проверьте наличие миграций `AddApiSynchronization`, `AddApiSourceSettings`, `AddApiBasicCredentials` в `__EFMigrationsHistory`. Первую миграцию синхронизации нельзя автоматически откатить через Down — для возврата нужна резервная копия.

4. Проверьте доступ к API с сервера приложения, под условиями его запуска, а не только из браузера на рабочем месте:

   ```powershell
   Resolve-DnsName <имя-сервера-API>
   Test-NetConnection <имя-сервера-API> -Port <порт-API>
   ```

   Проверьте маршруты, межсетевые экраны, прокси и доступность PostgreSQL. TCP-проверка не подтверждает корректность HTTPS и авторизации. Сертификат API должен соответствовать имени сервера и иметь цепочку доверия для процесса Guard. Для внутреннего центра сертификации установите доверенные корневые и промежуточные сертификаты установленным в организации способом. Не отключайте проверку TLS.

5. Согласуйте с владельцем API контракт полной выгрузки: доступны все классификаторы, подразделения и сотрудники; нет скрытых записей из-за прав аккаунта; страницы и ссылки между тремя наборами согласованы во время загрузки. Отсутствие записи в полном наборе используется для архивирования или деактивации.

6. Примените миграцию `AddApiSnapshotConfirmation` на предназначенной для проверки БД. Войдите как Root, откройте «Синхронизация» → «Настройки» и сохраните адрес и учётную запись API. Затем установите флажок «Подтверждена полнота и согласованность выгрузки API» и сохраните настройки повторно. Подтверждение хранится в БД и не требует перезапуска. При смене адреса или логина оно сбрасывается сервером; для нового источника нужно отдельное подтверждение. Диагностика и проверка подключения работают без него.

   Старый параметр `DirectoryApi:CompleteSnapshotGuaranteed` больше не используется. При миграции подтверждение устанавливается в false независимо от прежней конфигурации. До подтверждения расписание не запускается, ручной запуск и постановка в очередь отклоняются до HTTP-запросов.

7. Проверьте время и часовой пояс сервера. Расписание `02:00` означает 02:00 именно на сервере Guard.

8. Обеспечьте сохранение ключей ASP.NET Core Data Protection и запуск под стабильной учётной записью. Пароль API в БД зашифрован этими ключами. При переносе только БД на другой сервер или утрате ключей потребуется повторно задать пароль. Можно явно задать DataProtection:KeyDirectory, DataProtection:ApplicationName и DataProtection:CertificateThumbprint в конфигурации среды. Если они не заданы, хранилище зависит от среды хостинга. Для файлового хранилища используйте шифрование ключей сертификатом и ограниченные права доступа. Для нескольких экземпляров нужны общие ключи и согласованное имя приложения.

## 2. Первый импорт через интерфейс Root

1. Запустите Guard и войдите под Root. Откройте `/synchronization`.
2. Пока оставьте ежедневную синхронизацию выключенной.
3. Укажите источник — HTTPS-адрес корня API, включая его путь, без имени конечного ресурса. Например, `https://<сервер>:<порт>/<путь>/api`. Клиент добавит `classifiers`, `subdivisions`, `personnel`. Не добавляйте логин, пароль, query-параметры или фрагмент в адрес.
4. Укажите размер страницы от 1 до 500. Для первого сетевого теста можно использовать 30, как на скриншоте. Это количество записей за запрос, а не предел выгрузки: все страницы будут загружены.
5. Введите выданные владельцем API логин и пароль Basic auth. Это отдельные учётные данные API, не пароль входа в Guard.
6. Выберите «Управление из API» и нажмите «Сохранить настройки». В этом режиме ручное изменение трёх областей запрещено, включая Root.
7. Оставьте поле «Изменения с даты (UpdatedAt)» пустым и нажмите «Синхронизировать». Первый запуск выполняет Root для всей организации. Полная загрузка без даты рекомендуется для проверки всего набора, но не обязательна: можно сразу задать дату. Ссылки должны быть представлены в ответе либо уже существовать в локальной БД; при отсутствии зависимости потребуется более ранняя дата или загрузка без даты. Не меняйте настройки во время проверки: изменение их версии отменяет текущую загрузку до применения.
8. После уведомления о приёме задания можно закрыть страницу: выполнение продолжится на сервере. Дождитесь завершения. Проверьте статус «успешно», начало и окончание, счётчики и историю. При ошибке дата успешной актуальности не обновляется; данные не должны быть частично применены.
9. Откройте классификаторы, подразделения и персонал. Проверьте внешние ID, значения, внешние статусы, структуру дерева, принадлежность сотрудников и отображение «Актуально по состоянию на».

Локальные тестовые записи сохраняются. Совпадение ФИО или локального номера не объединяет их автоматически с API. Для подразделений и сотрудников используется отдельный ExternalId; классификаторы сопоставляются по Type/Code. Из-за непокрытых локальных подразделений общий список может показывать, что данные ещё не синхронизированы, даже после успешного импорта. Проверяйте историю и область отображения.

## 3. Подготовка и проверка администратора пула

Для просмотра результатов Root не требуется привязка к сотруднику: откройте подразделения или персонал, где по умолчанию включён режим «Все подразделения» / «Весь персонал». Привязка ниже нужна для администратора пула и для режимов просмотра собственных данных. После отключения общего режима Root также должен иметь подразделение, чтобы видеть «Только свои / Свои и подчинённые».

1. После успешного полного импорта оставьте режим «Управление из API».
2. Привяжите проверяемую учётную запись к нужному импортированному сотруднику через форму редактирования пользователя. Убедитесь, что сохранение работает без переключения режима.
3. Назначьте роли права просмотра проверяемых областей. Разрешение `Permissions.Synchronization.Run` больше не доступно для назначения; прежние claims не дают управления синхронизацией.
4. Проверьте активные разрешённые IP сотрудника. Если их нужно назначить вручную, временно включите «Локальное управление». Для пользователя без Root отсутствие допустимого IP запрещает вход; не отключайте IP-проверку ради теста.
5. Верните режим «Управление из API». Если привязки или роли менялись, начните проверку новым входом пользователя.
6. Войдите под администратором. Пункт «Синхронизация» должен отсутствовать. Прямой переход на `/synchronization` не даёт доступа к управлению, настройкам или истории.
7. В аналитике классификаторов, подразделений и персонала проверьте общую дату последнего успешного запуска всей системы. Панелей запуска над таблицами быть не должно, включая Root. В локальном режиме дата сохраняется с пометкой «Синхронизация отключена».
8. Проверьте запрет ручного создания, редактирования, изменения статуса и перемещения справочных записей, а также назначения IP сотрудникам в режиме API. Создание учётных записей и изменение их привязки к сотрудникам доступны через управление пользователями с проверкой прав, области подразделений и уникальности сотрудника. Проверки выполняются также на сервере.

## 4. Последующие ручные запуски

1. Убедитесь, что Guard работает, режим — API, источник доступен и предыдущий запуск завершён.
2. При прежних параметрах не вводите пароль повторно. Пустое поле нового пароля при сохранении оставляет действующий пароль. При смене учётных данных введите новый логин/пароль и сохраните настройки.
3. Нажмите «Синхронизировать»: Запуск доступен только Root и обновляет всю организацию. Root может указать дату для получения только изменений. Пустая дата исключает параметр UpdatedAt из запроса и включает полную выгрузку. При указанной дате отсутствующие записи не архивируются и не деактивируются; ссылки на уже загруженные записи разрешены.
4. Проверьте результат, историю и время актуальности. Повторная загрузка неизменённого набора должна сохранять ID, связи и бизнес-версии записей; время успешной проверки обновляется.
5. При ошибке устраните причину и запустите повторно. Предыдущие успешно импортированные данные сохраняются. Второй одновременный запуск должен быть отклонён как уже выполняющаяся синхронизация.

После обычного перезапуска повторная настройка не требуется: источник, размер страницы, логин, защищённый пароль и расписание хранятся в БД. Флаг полноты остаётся настройкой среды. Ключи Data Protection должны быть доступны новому процессу.

## 5. Автоматические запуски

1. После успешного ручного теста Root включает «Ежедневная синхронизация», задаёт время сервера и сохраняет настройки.
2. Guard должен продолжать работать в назначенное время; открытый браузер не требуется. Worker проверяет расписание примерно каждые 30 секунд и обновляет всю организацию.
   Во всех запросах обязательно передаётся UpdatedAt: дата начала запуска по времени сервера минус один календарный день. При начале 10 октября 2026 года в 02:00 передаётся `2026-10-09`. Автоматическая выгрузка не архивирует по отсутствию. Для проверки исчезновения записи используйте ручную полную выгрузку Root без даты. После длительного простоя также нужна полная ручная загрузка: окно автоматического запуска не охватывает изменения старше предыдущего календарного дня.
3. Для теста задайте время на несколько минут вперёд и проверьте запись «по расписанию» в истории. Если успешный плановый запуск за текущую дату уже был, смена времени не создаст второй плановый запуск в тот же день; используйте ручной запуск либо проверяйте на следующий день.
4. После теста верните рабочее время, например `02:00`.
5. Если приложение запускается после назначенного времени, оно выполняет один догоняющий запуск за текущую дату. Пропущенные прошлые дни отдельно не воспроизводятся. Неудачный плановый запуск повторяется с паузой не менее пяти минут.

## 6. Сценарии тестирования API

Изменения ниже выполняйте только в согласованном тестовом источнике. Перед проверкой исчезновения убедитесь, что удаление из выгрузки не является результатом фильтра или ограничения прав.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Полный первый набор | Записи созданы, ссылки и пути согласованы, запуск успешен |
| Повтор без изменений | Сохранены ID, привязки аккаунтов/IP и бизнес-версии; обновлена актуальность |
| Изменение полей | Значения обновлены, отсутствующие необязательные поля очищены |
| Изменение внешнего статуса | Обновлены внешние Type/Code; локальный Status не подменяется |
| Перемещение подразделения | ParentId и пути всей ветви изменены согласованно |
| Перевод сотрудника | Изменено подразделение; локальная идентичность и связи сохранены |
| Запись отсутствует в полном наборе | Импортированное подразделение/сотрудник архивированы, классификатор деактивирован |
| Автоматически архивированная запись возвращается | Восстановлена с учётом блокировки; ручное удаление/архив не отменяются |
| Ошибка страницы, неполная пагинация, неверная ссылка или цикл | Весь импорт отклонён; частичного изменения и новой успешной актуальности нет |
| API недоступен или Basic auth неверен | Понятная ошибка; ранее загруженные данные сохранены |
| Два одновременных запуска | Применяется только один запуск |
| Уход со страницы после принятия запуска | Выполнение продолжается на сервере, результат доступен после возвращения |
| Переключение в локальный режим во время загрузки | Загрузка отменена до применения; ручные операции разрешены по прежним permissions |
| Перезапуск Guard | Пароль расшифровывается при сохранённых ключах, настройки и история доступны |

## 7. Ошибки и действия

| Сообщение/симптом | Что проверить |
| --- | --- |
| «Подтвердите полноту и согласованность выгрузки API на вкладке «Настройки»» | Подтвердить контракт с владельцем API и сохранить флажок на вкладке «Настройки» от имени Root. Запросы к API ещё не выполнялись |
| Не настроено защищённое подключение | Сохранённые HTTPS-адрес, логин, пароль и размер страницы |
| Ошибка HTTP 401/403 в техническом журнале | Учётные данные и права API-аккаунта на все три полных набора |
| Ошибка подключения/TLS | DNS, порт, маршруты, прокси, цепочку доверия и имя сертификата со стороны сервера Guard |
| Превышено время ожидания | Доступность и скорость API; timeout составляет 60 секунд на HTTP-запрос |
| Ошибка пагинации/ссылок | Контракт API, полный набор записей и согласованность между страницами и сущностями |
| Не удалось прочитать пароль API | Доступность прежних ключей Data Protection; при их утрате Root сохраняет пароль заново |
| У администратора нет доступного подразделения | Привязку пользователя, подразделение импортированного сотрудника, permissions и первый полный запуск Root |
| История успешная, а Index без общей актуальности | Непокрытые локальные подразделения и выбранную область отображения |

В протокол проверки включите версию сборки, среду, время запуска, размер страницы, статус и счётчики, проверенные сценарии. Не включайте пароль, заголовок Authorization и полные ответы с персональными данными. Технические подробности ищите в журнале Guard.

## 8. Повторный тест с диагностическим логированием

1. Обновите сборку Guard и перезапустите приложение. Для этой доработки новые миграции не требуются.
2. В настройках логирования выберите уровень Information: он нужен для последовательности запросов. Debug/Verbose и вывод чувствительных EF-параметров для этой проверки не нужны.
3. Запишите время начала проверки. Запустите ручную синхронизацию один раз; дождитесь результата, не меняя настройки и не закрывая страницу.
4. Если потребуется отдельно проверить уход со страницы, выполните второй запуск и перейдите в другой раздел. Запишите время перехода. После принятия задания оно должно продолжиться на сервере и завершиться в том же журнале RunId, независимо от страницы.
5. Дождитесь доставки накопленных логов в БД; перед переносом при необходимости штатно остановите приложение, чтобы завершить доставку. Скопируйте БД логов с записями от начала запуска до результата, включая записи UI.

Новые записи связываются свойствами RunId и SyncPanelId. Для каждого запроса указаны ApiResource, ApiPage, ApiPageSize, ApiAttempt, ApiElapsedMs, HTTP-статус и количество записей без содержимого ответов. При отмене ApiTokenCancelled показывает, отменён ли токен всей операции. Причины SettingsChanged, ManualCallerToken/CallerToken, ApplicationStopping/WorkerStopping и PanelDisposed позволяют отличить изменение настроек, токен инициатора, остановку приложения и уничтожение страницы. HttpTimeoutOrTransportCancellation означает отмену HTTP при ещё действующем токене операции; это диагностическая категория, а не доказательство timeout. Версию и параметры настроек можно сопоставить без учётных данных API.
