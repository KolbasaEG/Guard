# Этап 1, первая поставка: серверный поиск IP

Дата: 16 октября 2026 года. Ветка: `codex/architecture-ip-search`.
База: этап 0, `2b745cb`. Ветка продолжает утверждённый переход; main остаётся
на `d71358e`, этапы 0 и 1 в неё не слиты. Текущий результат ожидает проверки.

## Изменение

`Index.LoadData` теперь вызывает `IIpAddressService.SearchAsync(IpSearchRequest)`
и применяет `Items + Count`. В компоненте нет IQueryable, EF, SQL-проекции,
материализации запроса или переданного серверу пути подразделения.

Сервер получает текущие permission/scope через IIpManagementAccessService,
читает собственный Path из БД по доверенному UserId, накладывает серверную область,
статус и выбранную иерархию, затем фильтр, Count, сортировку с Id, пагинацию и
проекцию в прежний IpAddressDto. Перед возвратом повторно проверяются permissions,
UserId, Root, множество доступных подразделений и собственный Path. Ошибка или
отмена не возвращает частичный успешный результат. Count и страница по-прежнему
не являются снимком RepeatableRead: конкурентное изменение данных между ними
возможно, как и до переноса.

Параметры запроса: Mode, Hierarchy, AllSubdivisions, Skip/Take, OrderBy и Filter.
Размер страницы ограничен 1–100; отрицательный Skip запрещён. Сортировка принимает
только Address, Description, Subdivision.Name, направления asc/desc и не более
трёх полей; Id добавляется сервером. По умолчанию InsertedDate desc, Id asc.
AllSubdivisions разрешён только Root. Без него собственный Path отсутствует или
некорректен — результат пустой, в том числе у Root. Чужую область нельзя передать
в запросе либо расширить пользовательским OR-фильтром.

`IpListQuery` стал Web-адаптером: копирует условия Radzen и значения в ExportFilter.
Это существующий независимый JSON-контракт заданий; его форма не менялась.
`IpSearchQuery` строит выражения без Radzen и Dynamic LINQ. Поля, типы и операции
проверяются повторно на сервере; глубина до 16, до 100 узлов, IN до 1024 значений.
Поддерживаются строковые Equals/NotEquals/Contains/DoesNotContain/StartsWith/
EndsWith, проверки null/empty и In/NotIn. Незаданный строковый фильтр и незаданный
список выбора не ограничивают выборку; пустой IN-массив сохраняет прежнюю семантику.
Регистр и null проверены относительно старого Radzen-исполнителя отдельно в
памяти и PostgreSQL, включая отсутствие связанного подразделения.

Поиск и существующий IP-экспорт используют один исполнитель условий и сортировки.
Это сохраняет старые сериализованные задания со штатными условиями UI.
Остальные области временно используют прежний ExportFilters; их общий адаптер
не переписывался в этой поставке. Произвольные операции/выражения, неизвестные
поля и нестроковые значения для IP отклоняются.

UI сохраняет прежние DTO, разметку, статусы, кнопки и диалоги. Конструктор
RadzenDataFilter работает без набора сущностей. Снимок меняется по «Применить»,
новый запрос отменяет предыдущий, поздний результат игнорируется. Изменения
каскадного контекста по-прежнему очищают старые строки и вызывают перезагрузку.

## Проверки

- Сборка решения успешна: 0 ошибок; полная сборка — прежние 52 предупреждения,
  заключительная инкрементальная — 0 предупреждений. Пакеты не менялись.
- Итоговый `--postgres Guard/appsettings.json`: 1126 проверок, успешный exit code.
  Тестовая БД создана отдельно и удалена штатным harness.
- Новые проверки: совместимость снимка, ограничения дерева условий/полей/типов,
  пустой выбор, серверные permissions, Root/оператор, область/иерархия,
  статусы, совпадение с экспортом, стабильные страницы, отмена, смена доступа,
  nullable-навигация в SQL и устаревшие ответы UI.
- Браузерный стенд с отдельной БД, тестовым Root, ключами и архивом: автоматическая
  первая загрузка (32 записи), вторая страница, сортировка по IP, фильтр
  «Содержит», сохранение действующего снимка до «Применить» (25 записей при
  изменённом конструкторе), применение (1 запись), очистка (32), архив (1),
  удалённые (1), Root «свои» и «свои и подчинённые» без подразделения (0),
  возврат полного списка и открытие/закрытие карточки. Дополнительно штатный
  стенд выполнил 15 HTTP-проверок смены собственного пароля/выхода.
- Браузер закрыт, host остановлен; временные БД, архив и ключи удалены.
- В IpAddresses нет ссылок на EntityFrameworkCore, IQueryable или query-делегаты.
  Схема, миграции, подключения, middleware IP-допуска и операции записи не менялись.

## Повторный замер согласованного объёма

Запуск: `dotnet run --project Guard.IpRules.Tests/Guard.IpRules.Tests.csproj --no-build -- --benchmark Guard/appsettings.json`.

200000 сотрудников, 1000 подразделений, 10 млн IP; условия синтетического набора
описаны в [исходной базе](architecture-baseline.md). IP-замер теперь вызывает
фактический SearchAsync с DTO, собственным Path из БД и повторной проверкой scope.
Сам permission/scope provider в замере заменён доверенным Root-контекстом;
стоимость реального входа и вычисления permissions сюда не входит. Под него
создаётся локальная тестовая учётная запись с привязкой к сотруднику.
Первый вызов не означает холодный диск. Прогретые значения — пять последовательных
вызовов без параллельной нагрузки.

| Сценарий | Первый вызов, мс | Прогретая медиана, мс | Прогретый максимум, мс |
| --- | ---: | ---: | ---: |
| IP SearchAsync, все 10 млн, Address asc | 371,8 | 346,3 | 366,4 |
| IP SearchAsync, своё подразделение, 10000 IP | 112,2 | 16,1 | 17,6 |
| IP SearchAsync, все, сортировка по умолчанию | 1196,8 | 1153,0 | 1205,0 |
| Сотрудники, Skip=0, прежний построитель запроса | 197,8 | 92,6 | 190,5 |
| Сотрудники, Skip=100000 | 1163,6 | 1175,5 | 1250,0 |

Экспорт 100000 сотрудников: снимок 1494,8 мс, XLSX/ZIP 2764,0 мс; границы
замера экспорта прежние — без очереди, checkpoint-запросов и HTTP-доставки.
Синтетическая БД около 2,23 GiB, все фактические количества проверены.
Замер завершился успешно; его БД и файлы удалены. После замера исправлен только
случай незаполненного IN-условия, не участвующий в этих сценариях; он проверен
заключительным регрессионным набором.

Сравнение с этапом 0 не показывает заметного роста времени сортировки по адресу
на всём каталоге; это наблюдение локального стенда, не SLA production. Сортировка
по умолчанию дороже и должна отдельно оцениваться перед эксплуатационной приёмкой.
Индексы, схема и алгоритм пагинации в этой поставке не меняются.

## Границы поставки и продолжение

Это первая часть этапа 1, а не завершение всего разделения на проекты.
Legacy QueryIpAddressesAsync и методы, возвращающие сущности, пока сохранены
для совместимости внутренних потребителей и тестов. Новый список их не использует.
Следующий объём IP — DTO просмотра/выборов и явная запись из форм; затем
подразделения и остальные списки. Физическое выделение сборок ещё впереди.

Полная история миграций, browser-сценарии обычного оператора, перекос реальных
данных, большие назначения одному сотруднику, фильтры на всех 10 млн строк и
конкурентная нагрузка не проверены этой поставкой. Серверные проверки обычного
оператора выполнены на PostgreSQL. Push, слияние и развёртывание не выполнялись.
