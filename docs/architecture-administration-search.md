# Этап 1: поиск ролей и журналов

Дата: 16 октября 2026 года. Ветка: `codex/architecture-ip-search`.

## Результат

Списки ролей и технических журналов вызывают отдельные `IRoleSearchService` и
`ILogSearchService`. Запросы `RoleSearchRequest` / `LogSearchRequest` содержат
Skip, Take, сортировку и независимый фильтр; результат — материализованные Items
и Count. Неизменяемый класс `LogEntryDto` сохраняет отдельные ключи строк даже для одинаковых событий и также передаётся в существующую оболочку ViewEntity.
В компонентах этих областей больше нет EF, Identity-сущностей, IQueryable и
query-делегатов. Старые API сервисов сохранены для переходной совместимости.

Роли читаются через IReadRepository, журналы — через отдельный LogsDbContext
фабрики на операцию. Count, сортировка, проекция DTO и пагинация выполняются
сервером. Поиск разрешает только перечисленные поля и операции, проверяет
типы, UTC, размер страницы 1–100, глубину и число условий.

Оба поиска проверяют permissions до чтения и перед возвратом, сравнивают ID
пользователя, Root и снимок permissions. Роли и журналы сохраняют Root-only
правила PermissionCatalog; фильтр не задаёт область доступа. У технических логов
нет области подразделений. Проверка доступа в UI дополнительно сохранена.

Записи ролей продолжают выполняться через IRoleAccessService. Формы уже
использовали RoleEditDto, проверку версии и транзакцию; их поведение в этой
поставке не менялось. Удаление списка теперь напрямую вызывает этот сервис.

Web использует RoleFilterFields / LogFilterFields и общий AdministrationListQuery:
условия становятся независимым снимком только после «Применить». Серверная
проверка фильтров выделена из UserSearchQuery в RestrictedSearchQuery<T>;
поиск пользователей использует ту же реализацию и сохраняет прежние контракты.

Списки отменяют предыдущую загрузку, отбрасывают поздние ответы, очищают данные
при ошибке и смене каскадного доступа. Автообновление журналов сохранено.

## Проверки

- Сборка Guard.slnx без ошибок.
- Полный runner: 1485 проверок, включая PostgreSQL во временной БД;
  дополнительно 15 HTTP-проверок собственного пароля и выхода.
- Новые проверки: SQL-перевод всех полей сортировки, фильтры групп/списков/null/UTC,
  Count до пагинации, запрет неразрешённых параметров, смена actor и отзыв Root,
  отмена, неизменность применённого фильтра, поздние ответы и очистка ошибок UI.
- Браузер: первое открытие ролей и журналов, применение и очистка фильтра, сортировка, пагинация, открытие и закрытие диалогов. Проверены независимость применённого фильтра и автообновление журналов. Проверка проведена на синтетических данных во временной БД.
  Рабочие подключения и данные не изменяются.

## Ограничения и следующий шаг

Таблица logs не имеет уникального ключа. Для постоянного набора данных сортировка
дополняется всеми отображаемыми полями. Полностью одинаковые строки остаются
неразличимыми; вставки между запросами могут сдвигать OFFSET-страницы. Count и
страница читаются последовательно без общей snapshot-транзакции. Сортировка по
длинным текстам может быть дорогой; массовые замеры журналов не выполнялись.
Для больших журналов отдельно потребуются ключ, подходящие индексы и решение
о cursor pagination. В этой поставке схема рабочих БД не меняется.

Этап 1 ещё требует аудита оставшихся UI-зависимостей (сотрудники, аудит,
синхронизация и вспомогательные сценарии). Затем — завершение доверенного
контекста операций и атомарности перед физическим выделением проектов.
Динамическое логирование и доставка аудита не перерабатывались. Скриншот просмотра: `Guard/obj/administration-search-verification.jpg` (локальный артефакт, не входит в Git).
