# Account: согласованные сценарии и смена своего пароля

Дата: 16 октября 2026 года. Продолжение этапа 1 в ветке `codex/architecture-ip-search`.

## Согласованный объём

Пользователь подтвердил: нужны только локальный вход, выход и смена своего пароля. Самостоятельная регистрация, восстановление по email, внешние провайдеры, 2FA и passkey не входят в требуемые сценарии. Это решение о целевом поведении: в этой поставке старые шаблонные маршруты ещё не удалены.

| Сценарий | Текущее состояние | Дальнейшее действие |
| --- | --- | --- |
| `/Account/Login` | Static SSR; поиск по email; PolicyUserManager и IpRestrictedSignInManager; аудит результата | Выделить контракт локального входа, сохранить lockout, IP-проверку и локальный ReturnUrl; убрать ветки passkey/2FA вместе с неиспользуемыми маршрутами |
| GET/POST `/Account/Logout` | Страница подтверждения и POST с cookie sign-out, аудитом и LocalRedirect | Сохранить POST/antiforgery и возможность выйти при обязательной смене пароля |
| `/Account/Manage/ChangePassword` и POST `/Account/ChangeOwnPassword` | Общий IOwnPasswordService, независимые результаты | Выполнено в этой поставке |
| `/Account/Manage/SetPassword` | Шаблон для аккаунта без локального пароля; переход из ChangePassword | При удалении маршрута заменить переход понятным сообщением об обращении к администратору; не давать установить пароль без подтверждения владения аккаунтом |
| Register, ConfirmEmail, Forgot/ResetPassword, ResendEmailConfirmation и страницы подтверждения | Шаблонные страницы; для части не зарегистрирован IEmailSender | Удалить маршруты и ссылки; не добавлять фиктивный отправитель |
| ExternalLogin, LoginWith2fa/RecoveryCode, Manage/ExternalLogins, Passkeys и управление 2FA | Шаблонные страницы, endpoints и JS | Удалить согласованно; определить обработку ранее включённой 2FA без автоматического изменения данных |
| Manage/Profile, Email, PersonalData, DeletePersonalData | Шаблонное самостоятельное управление профилем и удаление/выгрузка | Убрать вместе с навигацией Manage; учётными записями продолжает управлять административный раздел |

Удаление ссылок само по себе не закрывает маршруты. Следующая поставка должна проверить прямые GET/POST, отсутствие активных endpoints и ссылок на удалённые компоненты, включая `App.razor` и `ManageLayout`. Таблицы Identity, токены, миграции и существующие данные при этом не удаляются. Наличие реально используемых настроек 2FA необходимо проверить без вывода персональных данных перед изменением поведения входа.

## Контракт смены пароля

`IOwnPasswordService` не использует ApplicationUser, IdentityResult, UserManager или HttpContext в сигнатурах. Состояние чтения — MissingUser/NoPassword/Ready; запись возвращает Succeeded/Unauthorized/Rejected и сообщение отказа. Пароли передаются скалярными параметрами, не помещаются в DTO/record с автоматически генерируемым ToString и не логируются.

`Core/Identity/OwnPasswordService` — серверный адаптер, зарегистрированный scoped существующим Scrutor-сканированием по суффиксу Service. Исполнитель берётся из текущего аутентифицированного HTTP-запроса; идентификатор пользователя из формы не принимается. Сервис предназначен для Static SSR/HTTP, а не длительного интерактивного circuit.

Сервис проверяет заполнение и подтверждение пароля, вызывает существующий PolicyUserManager, проверяет IdentityResult и только после успеха обновляет cookie через действующий SignInManager. Сохраняются парольная политика, запрет заблокированной учётной записи/повторного пароля, изменение security stamp, PasswordChangedAtUtc, MustChangePassword, аудит и IP-проверка при обновлении cookie. Endpoint отвечает за antiforgery, чтение HTTP-формы и преобразование результата в HTTP; Razor-страница — за отображение и переходы. Обе точки используют одну операцию.

CancellationToken проверяется перед чтением и изменением, HTTP-потребители передают RequestAborted. API UserManager/SignInManager не принимает отдельный token. После успешной записи намеренно нет дополнительной проверки отмены перед обновлением cookie. Смена пароля в БД и выдача cookie не являются одной транзакцией: сбой обновления cookie не откатывает уже сохранённый пароль; это прежнее ограничение Identity, успех при исключении не возвращается.

Схема БД, cookie scheme, middleware, конфигурация и рабочие подключения не изменены. Нормальный запуск приложения для проверки не используется.

## Проверки

- Сборка `dotnet build Guard.slnx --no-restore -v quiet -p:UseAppHost=false -p:OutputPath=.../Guard/obj/own-password-build/`: успешно, 0 ошибок. Отдельный output нужен из-за запущенного пользовательского Guard, удерживающего стандартный Guard.exe; обычная сборка остановилась на MSB3027/MSB3021, процесс не останавливался.
- Runner из этого каталога с `--browser Guard/appsettings.json` и `GUARD_TEST_APP_DLL`, указывающим на проверочную Guard.dll: 1629 основных проверок, включая PostgreSQL на временной БД, плюс 20 отдельных HTTP-проверок. Сервер остановлен через Enter, временная БД и файлы стенда удалены штатной finally-очисткой, завершение 0.
- HTTP: подтверждение и пустой текущий пароль, неверный текущий/слабый новый пароль, отсутствие antiforgery, успех endpoint и SSR-формы, cookie refresh, отзыв предыдущей cookie, восстановление синтетического пароля и выход при MustChangePassword. Также проверен отказ анонимному POST. В первом прогоне SSR-тест ожидал относительный Location; после сравнения разрешённого пути вместо формата URI повторный прогон успешен.
- Локальные проверки адаптера: отсутствующий HTTP-контекст, анонимный вызов, отмена чтения/записи до обращения к Identity.
- `git diff --check`: успешно. Ручная браузерная проверка в этой поставке не выполнялась: форма проверена настоящими HTTP GET/POST через Static SSR. Удаление шаблонных маршрутов и сбой cookie refresh после сохранения здесь не проверялись и не входят в выполненное изменение.

Этап 1 не завершён: остаются локальный вход/выход, удаление ненужной поверхности Account и ревизия старых контрактов. Этап 2 с контекстом операции/атомарностью и физическое разделение проектов ещё впереди.
