# Аудит исполнителя, контекстов и завершения записи

Текущий срез: [независимый контракт сеанса](architecture-current-session.md) устраняет кэш автора в CurrentUserService и транспортные зависимости PermissionService. Legacy-аудит получает автора при сохранении, аудит операций через UnitOfWorkFactory сохраняется. Следующий участок — снимок входного DTO записи роли до await. Ниже сохранён исходный аудит.

Реализация после этого среза: [завершение собственной смены пароля](architecture-own-password-completion.md) устраняет неоднозначность подтверждённой записи при сбое cookie и аудита в ChangePasswordAsync. Следующий участок — независимая текущая сессия и автор. Остальной текст фиксирует исходный аудит; новые результаты проверок приведены в отчёте реализации.

Дата: 16 октября 2026 года. Ветка: `codex/architecture-ip-search`.
Срез кода: `1fe7f0e`, после отделения EntityWriteMapping от DTO.

## Вывод

Этап 2 ещё не завершён. Основные операции уже создают контекст на операцию, но получение principal остаётся внутри PermissionService, legacy-аудит зависит от состояния CurrentUserService, а контракты не описывают некоторые ошибки после сохранения. Перенос реализаций в сборки сейчас закрепил бы транспортные зависимости.

Это статический аудит кода и существующих проверок. Новых запусков PostgreSQL, HTTP, браузера и приложения в этой поставке нет. Наличие теста ниже означает покрытие в исходниках, а не результат нового запуска. Ошибки commit и конкурентные сценарии требуют runtime-проверок.

## Исполнитель и доверие

| Путь | Текущее поведение | Остаток перехода |
| --- | --- | --- |
| `PermissionService.GetCurrentAsync` | Principal из AuthenticationStateProvider, при InvalidOperationException — HTTP. Проверяет authentication, ID, security stamp в БД; вызывает GetForUserAsync | Получение доверенной сессии вынести в Web-адаптер. Проверку блокировки, срока пароля, ролей и permissions сохранить на сервере |
| `PermissionService.GetForUserAsync` | По ID проверяет политику, доступность пользователя, роли и role claims; индивидуальные permission claims не учитывает | Сохранить отдельный путь для автора задания из серверной очереди. Не принимать ID из формы как замену текущему исполнителю |
| `DataAccessScopeService.GetAsync` | Повторно запрашивает текущего пользователя, затем путь/потомков; Root обрабатывается явно | Нужен согласованный снимок исполнителя и области. Сейчас несколько запросов не составляют один снимок БД; повторные проверки конкретных операций сохранять |
| `CurrentUserService` | GetDisplayAsync заполняет actorId/actorName после проверок. Синхронные свойства используют эти поля либо HTTP | Отделить display от аудита. При исключении проверки изменившегося доступа прежние поля не очищаются во всех ветвях. Это риск legacy-аудита, а не источник permissions |
| `UnitOfWorkFactory.CreateAsync` | Берёт actor.UserId из PermissionService и замыкает его в PrepareAudit нового контекста | Уже независим от display DTO. Сохранить фиксацию автора на операцию |
| Синхронизация и экспорт | Сохранённый автор задания либо явный системный исполнитель; повторная проверка через GetForUserAsync и специализированные правила | Сохранить запуск без HTTP/Blazor; фоновые задания не направлять через адаптер текущей сессии |

Единственный потребитель ICurrentUserService для аудита — AuditSaveChangesInterceptor; UserName он не использует. CurrentUserService также реализует ICurrentUserDisplayService. Разделение требует согласованных изменений DI и scoped-интерцептора.

## Контекст и транзакция

| Область | Владение и атомарность | Аудит и ограничения |
| --- | --- | --- |
| Personal, Subdivision, Classifier | Новый контекст IUnitOfWorkFactory; репозитории используют его же. ExecuteInTransactionAsync фиксирует с дополнительным SaveChangesAsync | PrepareAudit задаёт автора; ApplicationDbContext обновляет версии. Повторять всю операцию с новым UoW |
| Перемещение подразделения | Один UoW/транзакция меняет ParentId и пути узла/потомков; проверяет версию и циклы | SaveChanges внутри действия и затем в обёртке — не commit на каждой строке. Нужна отдельная проверка конкурирующих перемещений пересекающихся ветвей |
| IP | Отдельный фабричный контекст, транзакция и замок каталога 74162001 | Автор/UTC задаются явно из IpManagementScope; scoped-интерцептора нет |
| Назначения IP | Отдельный фабричный контекст; ManagementLock → замок каталога → строка сотрудника; одна транзакция | Проверки статуса, подразделения, режима API; автор/UTC явно |
| SecurityService.WriteAsync | Отдельный async scope; контекст и UserManager из него; транзакция под 74162002; доступ перепроверяется до/после обязательных шагов | Обязательные IdentityResult проверяются; событие и уведомления после commit. Legacy UpdateUserAsync остаётся совместимым API |
| RoleAccessService | Отдельный scope с контекстом и Identity-менеджером; транзакция под 74162002; Root перепроверяется после замка | Версии, защита Root и последнего Root, проверка IdentityResult. RoleEditDto читается после await — нужен независимый снимок входа |
| Свой пароль | HTTP scope UserManager/SignInManager; PolicyUserManager сохраняет hash/stamp и поля политики через операцию Identity | Затем отдельно обновляется cookie. Общей транзакции БД/HTTP нет; периодический отзыв открытых соединений не добавлять |
| Политика аккаунтов | Фабричные контексты; административная запись, активность/блокировка используют транзакции и 74162002 | SaveAsync проверяет версию/Root. CheckAsync может записать блокировку: это не чистое чтение; try-lock не ждёт занятого административного замка |
| Синхронизация | Контекст на запуск; session advisory lock на открытом соединении; снимок и успешный статус в одной транзакции под ManagementLock | IsSynchronization явный; монитор использует отдельные контексты. Фазы до применения и Failed/Cancelled после отката намеренно вне атомарного снимка |
| Экспорт | Фабричные контексты; снимок RepeatableRead; файл отдельно, artifact + Ready одной транзакцией | БД/файл не имеют общей транзакции. При неизвестном commit очистка сверяет artifact отдельным контекстом перед удалением файла |
| Scoped ApplicationDbContext / IUnitOfWork | Сохраняются в Program.cs; scoped-контекст с AuditSaveChangesInterceptor | Вложенный scope Identity ограничен операцией; circuit scope этого не гарантирует. Удалять регистрации после проверки всех серверных/Identity-потребителей |

Поиск ApplicationDbContext/IUnitOfWork/UserManager/RoleManager в Components обнаружил только технический IdentityRevalidatingAuthenticationStateProvider с UserManager в отдельном scope. Это не разрешает удалить scoped-контекст: он нужен Identity store и серверным адаптерам.

## Ошибки после сохранения

1. **Свой пароль — следующая реализация.** OwnPasswordService возвращает Succeeded после RefreshSignInAsync. Если cookie не обновилась, hash/stamp уже сохранены. PolicyUserManager.ChangePasswordAsync также отправляет PasswordChanged после записи до возврата из менеджера: исключение аудита может скрыть сохранение. OwnPasswordChangeResult содержит лишь Succeeded/Unauthorized/Rejected. Нужен подтверждённый результат «пароль изменён, войдите заново», согласованный с endpoint, страницей и диалогом. Не откатывать пароль ради cookie и не повторять изменение автоматически. Сетевой обрыв после ответа остаётся неопределённым для клиента.
2. **События после commit.** SecurityService, RoleAccessService, AccountPolicyService.SaveAsync, создание экспорта вызывают аудит/уведомления до возврата успеха. Исключение уже не отменяет запись. AccessChangeNotifier ловит ошибки отдельных callback (AccessEventTests); обычный сбой подписчика commit не ломает. Но интерфейсы уведомления/аудита не гарантируют отсутствие исключений. Отделить подтверждённый результат от доставки, не повторяя команду автоматически.
3. **Синхронизация.** Флаг committed не позволяет внешнему catch перевести сохранённый успех в Failed. Ошибка последующего аудита/логирования или освобождения session lock всё ещё может выйти вместо результата. Сверять по RunId и сохранённому статусу, не повторять снимок вслепую.
4. **Экспорт.** После Ready ошибка аудита попадает в catch формирования. UPDATE ограничен Processing: Ready не станет Failed, но диагностика/событие могут ошибочно сообщить неуспех. Разнести завершение и аудит, сохранить сверку artifact перед удалением файла.
5. **Неопределённый commit.** Ошибка CommitAsync не доказывает откат в PostgreSQL. Обработку подтверждённого commit нельзя применять к потере его подтверждения. Нужна сверка по ID/версии либо требование перечитать состояние; слепой retry не вводить.

Гарантированную доставку событий текущий Serilog-аудит не обеспечивает. Брокер/outbox в этой поставке не предлагаются: сначала определить результат записи и обработку ошибки доставки в существующем монолите.

## Оставшиеся поставки этапа 2

| Порядок | Изменение | Критерий проверки |
| --- | --- | --- |
| 1 | Результат своей смены пароля при ошибке cookie/аудита; оба HTTP/UI пути | Инъекция отказа до/после записи; старый/новый пароль, stamp, поля политики; предложение войти заново только после подтверждённой записи. Пароли не логировать |
| 2 | Независимый контракт сессии, HTTP/Blazor-адаптеры; отделение display и автора | Запись до загрузки display, смена principal, отсутствие HTTP, неверный stamp, блокировка/срок пароля; задания работают по сохранённому автору |
| 3 | Снимок RoleEditDto до await; явное завершение Identity-записи и доставки событий | Изменение DTO во время ожидания не меняет команду; обязательный IdentityResult откатывает всё; сбой аудита после commit не изображает откат |
| 4 | Завершение синхронизации/экспорта после commit | Инъекция ошибки аудита; БД/artifact согласованы с результатом; неизвестный commit сверяется отдельно |
| 5 | Итоговый реестр контекстов/legacy DI и конкурентные сценарии | DI scopes, параллельные независимые операции, автор/UTC, откат дерева/Identity, API-режим; явный владелец каждой scoped записи |

Не вводить универсальный transaction runner для cookie, файлов, синхронизации и Identity: точки фиксации и сверка результата различаются. Замки 73460219, 74162001, 74162002 и session lock синхронизации не переставлять попутно.

## Существующие проверки и завершение этапа

- RefactorTests: разные контексты UoW, фабричный автор/UTC без БД; EF concurrency tokens и соответствие snapshot.
- RefactorIntegrationTests, UserAdministrationIntegrationTests, UserEditIntegrationTests, AuthorizationTests: PostgreSQL, UoW, Identity, версии/доступ.
- OwnPasswordBoundaryTests: анонимный вызов; OwnPasswordHttpTests: штатные HTTP-сценарии. Отказ обновления cookie после записи требует новой проверки.
- AccessEventTests: все сессии, удаление подписки, изоляция ошибки callback.
- ApiSynchronizationIntegrationTests, ExportIntegrationTests: интеграционные сценарии областей; дополнить отказами завершения, указанными выше.

Этап 2 закрывается после реализации и проверок границ, а не по наличию отчёта. PostgreSQL запускать во временной изолированной БД, рабочие настройки не менять. Перед выделением Domain также остаются размещение независимых enum/контрактов и Personal.User → Identity с сохранением FK, уникальности и SetNull.
