# Выделение Guard.Infrastructure

Дата: 17 октября 2026 года. База: `7e64fc3`, ветка `codex/architecture-ip-search`.

Создана библиотека .NET 10 Guard.Infrastructure. Решение теперь содержит четыре производственных проекта и один существующий исполняемый runner; целевое разделение тестов на два проекта ещё не выполнено. Приложение остаётся одним процессом.

## Состав и зависимости

После проверки ссылок перенесены оставшиеся реализации из Guard/Core и вся история Guard/Migrations: **202 файла**. Из них **201 совпадает с исходными Git blobs**; исключение — SynchronizationSettingsRules, чей строковый метод теперь делегирует независимому правилу Application. Все 81 файл истории миграций и снимка модели перенесены без изменения содержимого. Namespace и имена типов сохранены, включая Abstarct и Concrates.

В Infrastructure находятся модели Identity и LogEntry, EF-конфигурации, оба контекста, design-time factory, инициализация и seeding, репозитории, UoW, readers, транзакционные реализации операций, аудит, логирование, интеграции и workers. HTTP-адаптеры допуска и передачи экспорта пока находятся здесь как существующие адаптеры ASP.NET Core. Компонентов Blazor, адаптера сессии или circuit-кода в библиотеке нет.

Направления ссылок:

- Guard → Infrastructure, Application, Domain.
- Infrastructure → Application, Domain; FrameworkReference Microsoft.AspNetCore.App и необходимые пакеты EF/Npgsql, Scrutor, OpenXml, Radzen и Serilog.
- Application → Domain; только BCL помимо этой ссылки.
- Domain → только BCL.

Версии пакетов сохранены. Зависимости OpenXml, Identity EF, Npgsql, Scrutor и sinks File/PostgreSQL перенесены из Web; Radzen и Serilog.AspNetCore нужны обеим сборкам. Неиспользуемые прежние зависимости Web этим изменением не очищались. Явные global usings заменяют прежние implicit usings Web SDK, включая System.Net.Http.Json. Для runner в Infrastructure сохранён InternalsVisibleTo; доступ к внутренним членам для Web не открывался.

Скрытый потребитель внутреннего SynchronizationSettingsRules обнаружен в странице синхронизации. Сравнение URL/имени пользователя выделено в публичный SynchronizationSourceRules в Application, без сущностей или инфраструктурных типов в сигнатуре. Страница и сервер используют одно правило с прежними Trim/TrimEnd и Ordinal-сравнением; структура формы не менялась.

Scrutor сканирует сборку Infrastructure через ранее подготовленный маркер. Общая регистрация Guard продолжает собирать Infrastructure, три прикладных сервиса и Web. Проверка разрешения интерфейсов DI дополнена новой сборкой, чтобы физический перенос не сократил покрытие.

## EF и миграции

ApplicationDbContext, ApplyConfigurationsFromAssembly, конфигурации, миграции и snapshot теперь принадлежат одной сборке. Отдельный MigrationsAssembly не требуется. Исторические ID и таблица __EFMigrationsHistory не меняются; новая миграция схемы не создавалась.

Для последующей работы с миграциями указывать `--project Guard.Infrastructure/Guard.Infrastructure.csproj --startup-project Guard/Guard.csproj`. Design-time factory остаётся в библиотеке и создаёт контекст с прежним фиктивным подключением без запуска Program/seeding. Сам CLI dotnet ef на этом участке не запускался; обнаружение истории и генерация SQL проверены через EF API.

## Проверки

- Restore и сборка решения: 0 ошибок, 25 прежних предупреждений. Последующая инкрементальная сборка — 0 ошибок и предупреждений.
- Независимая сборка Guard.Infrastructure: 0 ошибок, 4 прежних предупреждения в перенесённых исходниках.
- Полный runner с PostgreSQL: **21 232 проверки**, на 257 больше предыдущего участка, код завершения 0. Изолированная временная БД удалена.
- InfrastructureAssemblyBoundaryTests проверяет отдельную сборку, отсутствие обратной ссылки на Web/runner, отсутствие компонентов и дубликатов типов. Проверки Domain/Application и публичных контрактов обновлены для обеих внешних сборок.
- EF обнаруживает ровно 40 исходных миграций в прежнем порядке и snapshot в Infrastructure. Генерируется SQL всей истории; соединение остаётся закрытым. Модель совпадает со снимком. Существующие PostgreSQL-проверки переходов схемы, Identity, доступа, атомарности, конкуренции, дерева, синхронизации и экспорта проходят.
- Девять случаев сравнения источника подтверждают прежнюю нормализацию, необязательные значения и чувствительность к регистру для Application и серверного делегата.
- Локальная Debug-публикация без запуска приложения успешна. Проверены четыре DLL, runtimeconfig/deps, четыре записи проектов в dependencies и JavaScript Radzen. Каталог проверки: Guard/obj/infrastructure-publish (не включён в Git).
- Статический инвентарь обновлён и выполняется с новыми путями; diff и неизменность перенесённых файлов проверены.

Первый запуск runner в песочнице остановился на Windows ACL временного хранилища экспорта; повторный полный запуск вне песочницы успешен. Подключения и данные рабочей БД не изменялись. Приложение, seeding, браузер, workers и внешние интеграции не запускались; Release-развёртывание и полнообъёмная нагрузка не проверялись. Сохранение namespace не сохраняет assembly-qualified names: выпускать нужно согласованный полный каталог публикации, включая все четыре сборки. Сторонние бинарные потребители не проверены.

## Оставшаяся работа

Физическая цель четырёх производственных проектов достигнута, но независимые прикладные контракты не означают завершения всех этапов. Транзакционные реализации и семь legacy-контрактов остаются в Infrastructure. Radzen используется серверными адаптерами фильтров в QueryableExtensions и ExportFilters; это явная переходная зависимость. Гарантированная повторная доставка аудита и определение исхода commit при потере соединения остаются прежними ограничениями.

Следующий участок — разделить существующий runner на два тестовых проекта с сохранением полного набора проверок и отдельно проверяемыми зависимостями. Затем сверить оставшиеся критерии плана, проверить публикацию в предназначенной среде и обновить нагрузочные замеры. Слияние с main ожидает проверки пользователя.
