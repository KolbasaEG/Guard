# Размещение фоновых workers

Дата: 17 октября 2026 года. Ветка: `codex/architecture-ip-search`. База: `e3d10df`.

## Решение и изменения

AccountPolicyWorker перенесён из Infrastructure в Guard/Web/Workers. Это host-адаптер: раз в минуту создаёт async scope и вызывает независимый IAccountPolicyService.SweepAsync с токеном остановки. Регистрация AddHostedService перенесена из AddGuardInfrastructure в AddGuardWeb. Тело класса, namespace Guard.Core.Identity, первый запуск после первой минуты, обработка ошибок и категория ILogger сохранены. Проверка политики, чтение/запись Identity, аудит и транзакции остаются в Infrastructure.

ApiSynchronizationWorker выделен из SynchronizationService.cs в отдельный файл в Infrastructure. Он восстанавливает прерванные запуски, выбирает очередь непосредственно через EF, читает настройки расписания и вызывает ApiSynchronizationRunner. Сохранены scope на итерацию, немедленная обработка следующего задания после очереди, задержки 30 секунд и 5 минут при неуспешном запуске по расписанию, токен отмены и повторные проверки внутри runner.

ExportWorker выделен из ExportProcessor.cs в отдельный файл в Infrastructure. Его lease — отдельный ApplicationDbContext с открытым соединением и session advisory lock ExportQueue; он живёт между итерациями, отдельно от scope обработки. Worker проверяет соединение, восстанавливает задания только после получения lease, выполняет очистку раз в 30 секунд и поиск orphan-файлов раз в день, затем обрабатывает очередь. При ошибке сбрасывает recovered и освобождает lease, при остановке освобождает блокировку с независимым пятисекундным токеном. Эти действия не менялись.

Оба worker с EF остаются инфраструктурными адаптерами. Их перенос в Web потребовал бы переноса туда владения контекстами и блокировками либо дополнительного контракта с новым жизненным циклом. Для одного сервера такой перенос не даёт самостоятельной пользы. Дополнительные проекты, процессы и пустые прокси-контракты не вводятся. Проверка содержимого подтвердила точное сохранение тел всех трёх классов.

Внутренние исходные потребители используют прежние namespace. Смена сборки AccountPolicyWorker требует перекомпиляции внешних бинарных потребителей, если они существуют. Вызов одного AddGuardInfrastructure теперь регистрирует два worker с EF; полная композиция AddGuardServices или Infrastructure + Application + Web регистрирует все три в любом проверяемом порядке. Отдельные инфраструктурные host вне решения должны явно подключить таймер политики, если он им нужен.

В общей композиции Infrastructure → Application → Web таймер политики теперь регистрируется после двух worker с EF. При композиции Web первой порядок обратный. Таймер начинает проверку только после первого минутного тика и не служит барьером готовности других workers; порядок выполнения разных фоновых сервисов не гарантируется. Проверяется корректность DI в обоих порядках, а не последовательность выполнения работ.

## Проверки

В четырёх конфигурациях DI проверяется единственная singleton-регистрация каждого IHostedService и отсутствие AccountPolicyWorker в Infrastructure. Проверки границ фиксируют принадлежность таймера Web и двух worker с EF — Infrastructure.

Новые проверки выполняют каждый цикл с заранее отменённым токеном и запрещающей фабрикой scope: ни одна операция и подключение не начинаются. Отдельно проверяется StartAsync/StopAsync таймера политики до первого минутного тика с завершением ExecuteTask и без открытия scope. Это не проверка периодической работы в течение минуты или обработки сбоя SweepAsync; тело таймера сохранено.

Полный PostgreSQL-прогон включает существующую обработку durable-очереди ApiSynchronizationWorker, изоляцию ExportWorker от блокировки синхронизации, освобождение export lease при StopAsync и получение lease замещающим worker. Результат записан в docs/testing.md. Рабочий Program не запускался; браузерные и нагрузочные сценарии не выполнялись. Схема БД, миграции и настройки не менялись.

## Следующий участок

Выполнить итоговую сверку оставшихся критериев этапов 1–2 с явным перечнем завершённых и открытых пунктов. Физическая структура 4 + 2 и размещение рассмотренных HTTP/фоновых адаптеров определены; это не закрывает автоматически все критерии этапов. Отдельно остаются неопределённый исход commit, гарантированная доставка аудита и масштабирование проверки уникальности IP, которая пока читает весь каталог адресов.
