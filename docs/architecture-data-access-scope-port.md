# Область подразделений: правило и порт чтения

Дата: 17 октября 2026 года. База: `2f2b647`, ветка `codex/architecture-ip-search`.

DataAccessScopeService больше не зависит от EF и ApplicationDbContext. Он получает подтверждённого пользователя через IPermissionService, явно предоставляет полный доступ Root, а для остальных проверяет сохранённый путь и формирует отдельный набор разрешённых ID. IDataAccessScopeReader предоставляет только путь сотрудника и материализованные ID подразделений. Контракт относится к будущей Application, конкретный DataAccessScopeReader — к Infrastructure.

## Правила и данные

- Root получает IsRoot=true и доступ ко всем ID без чтения сотрудника или дерева. Пустой набор ID у Root не означает запрет.
- Для обычного пользователя ID автора берётся из подтверждённого UserAccessSnapshot. Порт читает Users → Personal → Subdivision.Path; отсутствие пользователя, сотрудника или подразделения даёт null. Клиентский путь не используется.
- SubdivisionAccessPath содержит прежнюю проверку пути без изменения принимаемого формата: начальный/конечный разделитель, непустой набор положительных long-сегментов. Проверка доступна независимо от EF; её использует также прежняя проверка целевого подразделения в SubdivisionService. Строгость формата попутно не менялась.
- При отсутствии или некорректности пути сервис возвращает обычную пустую область и не читает потомков. Прямой вызов GetSubdivisionIdsAsync с некорректным путём отклоняется до создания контекста, исключая массовую выборку по пустому префиксу.
- Корректный путь передаётся полностью, с завершающим разделителем: /1/12/ не открывает /1/123/. ID собственного подразделения и потомков копируются в новый HashSet. Статусная фильтрация остаётся в операциях; область, как и раньше, сама не исключает архивные/заблокированные подразделения.

Каждый метод reader создаёт и освобождает собственный контекст фабрики; результат материализуется внутри, EF-операции получают CancellationToken. Сохранена форма SQL-предиката Path.StartsWith(path) и существующий индекс Path с varchar_pattern_ops. Ни схема, ни индексы не менялись; отдельный EXPLAIN на полном объёме этой поставкой не выполнялся. Порт не возвращает сущности, IQueryable или живой контекст.

IDataAccessScopeReader зарегистрирован явно единожды как scoped в AddGuardServices и не попадает в сканирование по суффиксу Service. Ручные композиции тестов обновлены. Инвентарь независимых публичных интерфейсов увеличился до 35: 32 сервисных контракта и три порта чтения.

## Проверки и ограничения

Независимые проверки подтверждают Root без чтения дерева, десять отсутствующих/некорректных путей, отдельный снимок набора ID, передачу доверенного автора/пути/токена, отказ permissions до чтения, распространение ошибок и отмены обоих этапов. Производственный DI проверяется в Development и Production; новый контракт включён в рекурсивную проверку публичных типов.

PostgreSQL проверяет своё подразделение/потомка/соседний похожий префикс, все шесть статусов потомка, удаление привязки сотрудника, три повреждённых пути с прямым отказом порта, свежесть пути при повторном вызове того же сервиса и отмену обоих методов. Собственная фикстура удаляется до остальных сценариев. Прежние сценарии авторизации, поиска, записей, синхронизации и дерева работают с новым reader.

Добавлено 46 проверок. Сборка: 0 ошибок, 25 прежних предупреждений. Полный runner с PostgreSQL: 20 448 проверок, код завершения 0; временная БД удалена. Рабочие данные и настройки подключения не менялись. Приложение и браузер не запускались, производительность на полном объёме не измерялась.

Как и раньше, permissions, путь и потомки не образуют атомарный транзакционный снимок; теперь оба чтения порта используют разные контексты. Эта поставка не меняет гарантии при конкурентной смене роли или перемещении дерева. Generic ReadRepository сохраняет существующую защиту. Физическое разделение проектов ещё не начато, этапы 1–2 остаются открытыми.

Следующий конкретный участок перед выделением Domain — устранение обратной навигации Personal.User на Identity. Нужно проверить все потребители, сохранить уникальный FK ApplicationUser.PersonalId, SetNull и реляционную модель; изменение схемы нельзя предполагать необходимым до сравнения моделей. Затем требуется сверить оставшиеся зависимости для фактического разделения сборок.
