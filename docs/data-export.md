# Экспорт Excel/Word и архив расследований

HTTP-выдача отделяет доставку аудита от передачи файла и фиксации результата.
После подтверждённого claim ошибка ExportDeliveryStarted не прерывает скачивание;
после фиксации Delivered ошибка ExportDeliveryCompleted не меняет результат.
Ошибка аудита отказа также не мешает обработать исходную ошибку. Каждый сбой
доставки, включая OperationCanceledException, регистрируется через ILogger
с исходным исключением, типом события и ID выгрузки; автоматического повтора нет.
Отмена самого HTTP-запроса по-прежнему передаётся операциям БД и потоку файла.
Успешная запись и flush в серверный HTTP-поток не гарантируют сохранение файла
на устройстве клиента. Одноразовая попытка расходуется после claim, в том числе
при настоящем обрыве передачи. Проверки CSRF, автора, доступа, срока, Range
и контрольной суммы остаются до claim; результат записывается отдельной
завершающей транзакцией с ограниченным временем даже при отмене запроса.
Существующие два события ExportFailed при ошибке после claim сохранены:
первое сообщает об ошибке передачи, второе — о сохранённом результате попытки.
ExportHttpCompletionTests проверяет реальный локальный HTTP-стенд с изолированной
PostgreSQL-БД: точные байты, состояния/попытки, ошибки аудита, отказы до claim
и внедрённую ошибку записи тела ответа. Обрыв TCP после частичной передачи,
неопределённый исход commit и отказ самого ILogger этой поставкой не моделируются.

Создание выгрузки, запрос отмены и изменение срока хранения подтверждают результат
после успешной записи в БД. Исключение последующей доставки событий ExportRequested,
ExportCancelled или ExportRetentionChanged регистрируется через ILogger с типом
события и ID цели и не превращает сохранённую команду в отказ. Это относится также
к отмене внутри аудита после записи. Доставка предпринимается один раз; гарантированного
повтора нет. Ошибки доступа, проверки версии, входных данных и БД продолжают выходить
вызывающему коду. Интеграционные проверки ExportCommandCompletionTests наблюдают
сохранение независимым контекстом и проверяют отказы до записи; HTTP-выдача этой
правкой не менялась.

Описание текущей реализации, порядок работы пользователя и настройки сервера
приведены ниже. Подключение новых сущностей и изменение состава полей описаны
в [руководстве разработчика](data-export-extension-guide.md).

После подтверждённого commit статуса `Ready` и метаданных файла сбой доставки
`ExportArchived` регистрируется как техническая ошибка аудита. Выгрузка остаётся
готовой; событие `ExportFailed` из-за этого сбоя не отправляется, файл сохраняется.
Это относится также к исключению отмены внутри доставки после commit. Гарантированного
повтора аудита нет. Ошибки формирования до commit обрабатываются по прежним правилам;
неопределённый исход commit и сверка архивной копии при очистке не менялись.

## Пользовательский сценарий

Списки сотрудников, подразделений и IP-адресов предоставляют Excel и Word через
«Меню» слева в шапке таблицы: «Экспорт в Excel», «Экспорт в Word»,
«Незавершённые выгрузки».
Экспорт содержит все строки по **применённому** фильтру, статусу, выбранному режиму
иерархии и сортировке, без пагинации. Правки конструктора до «Применить» не влияют
на выгрузку. CSV удалён. Управление данными через API не запрещает экспорт.

Поля фиксированы в отдельных DTO экспорта; заголовки читаются из DisplayName.
Сотрудники: фамилия, имя, отчество, подразделение, статус. Поля полной карточки
(личный номер, год службы, внешние идентификаторы и т. п.) не экспортируются.
IP-адреса: адрес/подсеть, описание, подразделение, статус; назначенные сотрудники
не загружаются. Подразделения: наименование, родитель, тип органа, статус,
наименование для должности, индекс, адрес, телефон, штатная численность,
порядок и признак отдела.

Excel начинается колонками «Уровень 1», «Уровень 2» и далее, от общего корня до
непосредственного подразделения (для строки подразделения включается оно само).
Колонки имеют одинаковую глубину в пределах выгрузки; короткие цепочки дополнены
пустыми значениями. Общие записи без подразделения имеют пустую цепочку.
Названия предков выводятся только для выбранных доступных записей; это не даёт
доступ к карточкам или другим ветвям предков.

Документ содержит автора, номер выгрузки и время формирования. Excel добавляет
лист «Сведения о выгрузке», Word — заголовок и колонтитул. Эти отметки помогают
расследованию, но не являются неснимаемой защитой от утечки.

Пустая выборка формирует документ с заголовками и строкой «Записи не найдены».
При превышении RowsPerPart создаётся ZIP из нескольких документов; каждый
документ имеет те же колонки и номер выгрузки. Архив хранит точную копию ZIP.

Задание создаётся в БД и обрабатывается последовательно фоновым worker.
Закрытие диалога не отменяет задание. Кнопка незавершённых выгрузок позволяет
вернуться к нему; явная отмена делает файл недоступным для передачи.

## Доступ

Personals.Export сохранён; Subdivisions.Export и IpAddresses.Export добавлены
с зависимостью от Read. Новые permissions не назначаются существующим ролям
автоматически: их назначает Root через установленный сервис управления ролями.
Архивные сотрудники/подразделения дополнительно требуют ReadArchive; удалённые
записи — Root. Полномочия берутся только из назначенных ролей.

Проверки выполняются при запросе, в worker от имени автора, после формирования
и непосредственно перед передачей. Проверяются блокировка/парольная политика,
security stamp, актуальная область подразделений. При сужении области, если
хотя бы одно подразделение готовой выгрузки стало недоступно, выдача запрещена.
Root сохраняет полный серверный доступ, но выбранный режим отображения
ограничивает выгрузку. Без собственного подразделения режим «свои» пуст.

POST /exports/{id}/download требует входа и antiforgery. Задание принадлежит
текущему пользователю. Начало передачи атомарно потребляет возможность выдачи;
повторные запросы и Range не поддерживаются. При обрыве нужно создать новую
выгрузку. Завершение HTTP-передачи не доказывает сохранение/открытие файла.
Ответы имеют Cache-Control: no-store и Content-Disposition: attachment.

## Архив

Файлы и снимки строк шифруются небольшими аутентифицированными блоками через
ASP.NET Core Data Protection. Индекс блока и назначение входят в криптографический
контекст: перестановка, усечение, подмена и дополнительные блоки обнаруживаются.
SHA-256 вычисляется по исходным байтам выдаваемого документа; перед выдачей
или расследованием проверяются размер и хеш расшифрованного файла.

Реестр в основной БД содержит автора, IP, время, фильтры, версию схемы, состояние,
количество строк, размер, SHA-256, срок хранения и результат передачи.
Автор сохранён снимком: удаление/переименование учётной записи не удаляет архив.
В таблицах нет каскадной связи с пользователем или подразделением.

Страница /export-archive доступна только Root через Exports.ReadArchive.
Права Root проверяются в сервисе повторно перед возвратом результата.
Предпросмотр читает до 100 строк **из архивного документа**, а не из текущих
сущностей БД. Предусмотрены часть пакета и переход по строкам. Endpoint
скачивания из архива отсутствует. Просмотр отражается в IAuditService.

Срок по умолчанию — три календарных года от запроса. Root может изменить его
на 1–30 лет через Exports.Configure с проверкой версии. Новый срок применяется
только к новым заданиям. Массовое сокращение/продление старого архива в этом
этапе не реализовано. Очистка просроченных копий выполняется примерно каждые
30 секунд, пакетами до 100 записей; ошибки повторяются. После удаления
очищаются автор, IP, параметры фильтров, security stamp, количество строк,
метаданные файла и попытки передачи. Остаётся обезличенная отметка номера,
области, формата, времени и состояния Expired. События IAuditService обслуживаются
независимой политикой аудита безопасности.

## Настройка сервера

Настройки необязательны для разработки, значения по умолчанию:

```json
{
  "Exports": {
    "Directory": "App_Data/Exports",
    "RowsPerPart": 50000,
    "MaxQueuedPerUser": 3,
    "TimeoutMinutes": 30,
    "MinimumFreeBytes": 268435456
  }
}
```

Для production задайте абсолютный Directory вне каталога публикации и wwwroot
через конфигурацию окружения. Каталог внутри wwwroot запрещён. На Windows ACL
разрешает доступ учётной записи приложения и локальным администраторам; на Unix
каталоги создаются с правами 0700. Доступ ОС/администратора сервера не может
контролироваться прикладным признаком Root.

**Ключи Data Protection нужно сохранять и резервировать на весь срок архива.**
Используйте существующие DataProtection:KeyDirectory, ApplicationName и
CertificateThumbprint. Каталог ключей должен быть постоянным, отдельным от архива;
ограничьте ACL. Не удаляйте старые ключи и не меняйте ApplicationName без плана
миграции. Для сертификата требуется доступ к закрытому ключу. Утрата ключей
делает архив нечитаемым. Настройки подключений и ключей реализация не меняет.

Формирование Office и предпросмотр требуют временных seekable файлов, которые
кратковременно существуют в открытом виде в закрытом подкаталоге work.
Снимок DTO зашифрован. Для защиты рабочего диска и удалённых блоков используйте
шифрование тома ОС. Work очищается после операции и восстановления после сбоя;
его не нужно включать в резервные копии.

Нужно резервировать основную БД, архив файлов и ключи согласованно. Политика
резервных копий должна учитывать срок хранения: удаление рабочего архива
не удаляет старые копии из backup. Проверяйте восстановление ключей и сверку
хеша на изолированной среде. Ограничение свободного места — страховка; необходим
мониторинг реального объёма и свободного пространства.

## Состояния и восстановление

Queued → Processing → Ready → Delivering → Delivered.
До передачи возможны Cancelled, при ошибках — Failed, по сроку — Expired.
Технические состояния отделены от enum Status сущностей.

Файл публикуется до Ready, а его реестр и Ready фиксируются одной транзакцией
БД. Общей транзакции диска и PostgreSQL нет: незавершённые объекты остаются
недоступными и удаляются. Ежедневная сверка удаляет файлы без реестра старше суток.
После перезапуска Processing возвращаются в очередь; Delivering завершаются
ошибкой без повторной выдачи. Рабочие файлы очищаются. Обработчик держит
сеансовую advisory-блокировку PostgreSQL для исключения двух worker при
перекрывающемся запуске процессов. Плановая работа — один экземпляр Guard.

Ключ очереди экспорта — `PostgresAdvisoryLocks.ExportQueue` (`73460221`).
Он удерживается и при пустой очереди, но не блокирует диагностику и синхронизацию
API: для них используется отдельный ключ `73460220`.

При обновлении с версии, где экспорт использовал ключ `73460220`, остановите
все старые экземпляры Guard, подключённые к этой БД, и только затем запускайте
обновлённые. Старый обработчик продолжает блокировать синхронизацию; одновременная
работа разных версий также допускает двух владельцев очереди экспорта с разными
ключами. Миграция БД для разделения блокировок не требуется.

Переход к новой версии схемы DTO при незавершённых заданиях требует отдельной
политики миграции. Первая реализация использует SchemaVersion=1.

## Миграция и проверки

Миграция AddDataExport создаёт ExportJobs, ExportArtifacts,
ExportDeliveryAttempts и ExportRetentionSettings с индексами и внешними ключами.
Она не изменяет существующие данные и не назначает новые права. Применять
миграцию следует после проверки на предназначенной среде; приложение не
выполняет database update автоматически.

```powershell
dotnet restore Guard.slnx
dotnet build Guard.slnx --no-restore
dotnet run --project Guard.IpRules.Tests/Guard.IpRules.Tests.csproj
# Только localhost: набор создаёт и удаляет собственную guard_ip_test_<UUID>.
dotnet run --project Guard.IpRules.Tests/Guard.IpRules.Tests.csproj -- --postgres Guard/appsettings.json
```

Проверки включают Open XML schema validation, пустые и составные документы,
DisplayName, буквальные формулоподобные значения, шифрование, повреждение архива,
иерархию, область доступа, API-режим, Root-only просмотр, срок хранения,
CSRF и однократную HTTP-передачу с совпадением SHA-256.
ExportCompletionTests дополнительно проверяет отказ и отмену аудита после Ready,
видимость commit из независимого контекста, сохранность точной архивной копии,
совпадение хеша в аудите с метаданными, очистку рабочих файлов и отсутствие повторной
генерации. Отдельный сценарий с неподдерживаемой схемой сохраняет Failed без artifact.
