# Полная проверка Guard через браузер

Инструкция объединяет проверку ролей, области данных, создания учётных записей,
назначения IP сотрудникам и обновления прав по событиям. Выполняйте её на версии
из ветки `codex/personal-ip-editor`, которая включает предыдущие изменения.
Документ описывает ожидаемые результаты; он не является отчётом о выполненных тестах.

## 1. Подготовка среды и сеансов

1. Перезапустите тестовое приложение с актуальным кодом, обновите вкладки браузера.
   Используйте тестовую БД и один процесс приложения. Не меняйте реальные учётные
   записи, персональные данные и назначения IP ради проверки.
2. Войдите как Root в профиль браузера R. Оставьте его открытым для управления
   ролями и восстановления тестовых назначений.
3. Откройте отдельные профили или другие браузеры для пользователей A и B.
   В профиле A откройте вторую вкладку A2. Это два сеанса одного пользователя.
   Несколько приватных окон одного браузера могут разделять cookies.
4. Пользуйтесь одним адресом приложения во всех профилях, например текущим
   `http://localhost:7063`. Схему и порт берите из реально запущенного приложения.
5. Запишите исходные права, роли, поля сотрудников и IP-назначения для восстановления.
6. Для проверки событий не обновляйте страницы A/A2/B после изменения прав Root,
   если конкретный сценарий этого не требует.

Нужные разделы:

| Раздел | Адрес |
| --- | --- |
| Персонал | `/personal` |
| Пользователи | `/users` |
| Подразделения | `/subdivisions` |
| IP-адреса | `/ip` |
| Роли | `/roles` |
| Классификаторы | `/classifiers` |
| Типы органов | `/OrganTypes` |

## 2. Подготовка тестовых данных под Root

Создайте следующую структуру подразделений через интерфейс:

| Подразделение | Родитель | Назначение |
| --- | --- | --- |
| Тест A | Доступный тестовый родитель | Основная область пользователя A |
| Тест A1 | Тест A | Проверка доступа к потомкам |
| Тест B | Тот же родитель, что у Тест A | Чужая область для A |

Создайте активных сотрудников: «Тестовый А» в Тест A, «Тестовый Потомок» в Тест A1,
«Тестовый Б» в Тест B и дополнительного сотрудника «Тестовый Новый» в Тест A.
Первые два основных сотрудника будут связаны с пользователями A и B;
«Тестовый Новый» нужен для проверки создания дополнительной учётной записи.

В справочнике IP создайте активные адреса/подсети с явным подразделением:

| Запись | Подразделение | Использование |
| --- | --- | --- |
| IP-A-вход | Тест A | Реальный адрес соединения браузера A |
| IP-A-дополнительный | Тест A | Второй вариант выбора |
| IP-A1 | Тест A1 | Не должен предлагаться сотруднику Тест A |
| IP-B-вход | Тест B | Реальный адрес соединения браузера B |

На одном компьютере IP-A-вход и IP-B-вход могут иметь одинаковый адрес в разных
подразделениях. При обращении через localhost соединение может быть IPv4 `127.0.0.1`
или IPv6 `::1`: назначьте нужные адреса своего тестового подключения. Через прокси
используйте адрес, который приложение определяет согласно своей конфигурации.
Адреса для примеров ниже не гарантируют вход с вашего компьютера.

## 3. Проверка справочника IP

Выполняйте проверки на отдельных тестовых записях, не блокируя адрес своего входа.

| Действие | Ожидается |
| --- | --- |
| Создать IPv4 `192.0.2.10` | Запись сохраняется |
| Создать IPv6 `2001:db8::10` | Запись сохраняется в нормализованном виде |
| Создать CIDR `192.0.2.77/24` | Сохраняется `192.0.2.0/24` |
| Создать CIDR `2001:db8::abcd/64` | Сохраняется `2001:db8::/64` |
| Ввести `999.1.1.1`, `localhost`, `192.0.2.1/33`, `::/129` | Ошибка, запись не создаётся |
| Повторить адрес после нормализации в том же подразделении | Дубликат отклоняется |

После каждой ошибки проверьте список: не должно быть частично созданной записи.
Если форма показывает ошибку серверной проверки, исправление ввода должно позволить
повторить сохранение без повторного входа.

## 4. Назначение IP сотруднику

1. В R на `/personal` откройте редактирование «Тестового А».
2. Измените поле на тестовый маркер, не сохраняйте сотрудника.
3. Нажмите «Назначить IP-адреса» под полями.
4. Проверьте список: есть IP Тест A, нет IP Тест A1 и Тест B.
   Для Root действует такое же ограничение по подразделению выбранного сотрудника.
5. Выберите IP-A-вход и сохраните кнопкой в заголовке окна IP.
6. Проверьте, что основная форма осталась открытой и несохранённый маркер не потерялся.
7. Отмените основную форму. Снова откройте сотрудника и назначения IP.

**Ожидается:** маркер поля не сохранён, IP-A-вход назначен. Сохранение IP независимо
от сохранения сотрудника. Кнопка открытия IP не отправляет основную форму.

Повторите выбор нескольких адресов, отмену окна IP и повторное открытие.
Отмена не меняет назначения, успешное сохранение сохраняет весь выбранный список.
Для сотрудника Тест A1 доступны только IP Тест A1, для сотрудника Тест B — только Тест B.
Без подразделения список выбора пуст. Если нужного IP нет, добавьте его в справочник
с подразделением сотрудника.

Если существуют старые назначения вне подразделения сотрудника, окно предупреждает
об этом. Они не показаны в селекторе и не удаляются при сохранении. Поэтому очистка
видимого списка не гарантирует полного отсутствия назначений. Для теста пустого
списка используйте нового сотрудника без таких старых связей. IP архивных/заблокированных
записей не предлагаются, а сервер не позволяет назначать неактивные адреса.

Назначьте IP-B-вход «Тестовому Б» таким же способом.

## 5. Создание пользователей

1. В R откройте `/users`, нажмите «Добавить».
2. Заполните уникальное имя пользователя, email, пароль и повтор пароля.
3. Выберите «Тестового А», сохраните.
4. Проверьте появление записи и правильную привязку к сотруднику.
5. Создайте B с привязкой к «Тестовому Б».

**Ожидается:** после успеха диалог закрывается и таблица обновляется. Пользователь
создаётся без ролей. Сотрудник с уже существующей учётной записью больше не доступен
для выбора. Если список пуст, сначала добавьте сотрудника в «Персонале».

Негативные проверки с «Тестовым Новым»:

| Вариант | Ожидается |
| --- | --- |
| Разные пароль и повтор | Сообщение о несовпадении, записи нет |
| Пустое обязательное поле или неверный email | Сохранение не проходит |
| Слабый пароль, например `x` | Identity отклоняет создание |
| Логин существующего пользователя с другим свободным сотрудником | Дубликат отклоняется |
| Корректные данные и отмена вместо сохранения | Пользователь не создаётся |

После ошибок убедитесь, что новый пользователь не появился в таблице и сотрудник
остаётся свободным. Не назначайте IP и роли автоматически через создание: это
отдельные операции.

## 6. Подготовка ролей

В R создайте обычную роль `Тест редактор` с permissions:

- Сотрудники: Read, ReadDetails, ReadArchive, Write, Export.
- Подразделения: Read, ReadArchive, Write.
- Пользователи: Read, Manage.
- IP-адреса: Read, Manage.
- Классификаторы: Read, Manage.
- Типы органов: Read, Manage.

Создайте отдельную роль `Тест Б` с чтением и полным просмотром сотрудников,
а также изменением сотрудников для независимой проверки B.
В `/users` откройте «Роли и итоговые права» и назначьте роли A и B соответственно.
Не назначайте Root обычным тестовым пользователям.

**Ожидается:** зависимости чтения добавляются селектором. Роли и журналы доступны
только Root; обычная роль не должна давать управление ролями. Итоговые права
соответствуют назначениям. Индивидуальные старые permissions не дают дополнительных
прав; их наличие отображается в отчёте перехода на странице ролей.

Для последующего отзыва прав у A оставьте один источник проверяемого права.
Если право есть ещё в одной роли, снятие его в первой роли не лишит пользователя доступа.

## 7. Вход и правила IP

1. В профиле A войдите с созданными данными. В профиле B войдите под B.
2. Проверьте успешный вход при активном назначенном IP текущего соединения.
3. Для A в R очистите назначения IP-A, затем выйдите из A и попытайтесь войти снова.
4. Верните назначение и повторите вход.
5. Повторите с архивным или заблокированным IP: запретите все назначенные адреса,
   которые допускают текущее соединение, чтобы альтернативный адрес не маскировал результат.

**Ожидается:** пустой список и отсутствие подходящего активного назначения запрещают
новый вход; восстановление корректного назначения позволяет войти. IP подразделения
сам по себе не даёт вход — требуется назначение сотруднику. Root освобождён от этой
IP-проверки. Уже открытое соединение не обязано закрываться после изменения IP:
проверка выполняется при входе и новом соединении.

Для IPv4/IPv6/CIDR можно проверить вход с другого тестового устройства с известным
адресом, назначая точный адрес, включающую его подсеть и не включающую подсеть.
Не подменяйте IP заголовками браузера: это не проверяет реальный сетевой источник.

## 8. Область чтения данных

В A откройте сотрудников, подразделения и пользователей.

**Ожидается:** сотрудники Тест A и Тест A1 доступны, Тест B отсутствует. Root видит
все тестовые подразделения. Счётчик, поиск, фильтры и экспорт используют ту же область.
Права справочников проверяются отдельно; классификаторы и типы органов не ограничены
подразделением так же, как сотрудники.

Проверьте:

1. Поиск «Тестовый Б» под A не возвращает чужую запись.
2. Экспорт CSV под A не содержит сотрудников Тест B и полей полной карточки,
   отсутствующих в разрешённом списке, например личного номера.
3. После снятия Export кнопка экспорта исчезает; другие права списка сохраняются.
4. С одним Read список остаётся доступным, полный просмотр и изменение недоступны.
5. Возврат ReadDetails открывает полный просмотр, но не даёт запись без Write.
6. Без ReadArchive архив недоступен; после возврата архив доступен в разрешённой области.
7. Для обычного оператора создание пользователя предлагает только свободных активных
   сотрудников из доступных подразделений. Назначение IP при этом ограничено одним
   подразделением выбранного сотрудника, даже если оператор видит его потомков.

Для старой учётной записи без сотрудника или с некорректным подразделением область
данных должна быть пустой. Само создание через новую форму требует выбора сотрудника;
для проверки старых случаев используйте подготовленные тестовые данные.

## 9. Отзыв и возврат записи в открытой форме

1. В A откройте редактирование сотрудника, введите `EVENT-TEST`, не сохраняйте.
2. В R снимите у роли A только Personals.Write, оставив Read и ReadDetails, сохраните.
3. Не нажимая F5 в A, проверьте открытое окно и попробуйте отправить форму Enter.
4. В R верните Write, сохраните. Проверьте A и сохраните тестовое изменение.

**Ожидается:** при отзыве диалог остаётся открытым, ввод сохраняется, поля блокируются,
сохранение скрывается, Enter не записывает данные. После возврата право записи
восстанавливается без повторного открытия и потери ввода.

Повторите для новой формы пользователя со снятием Users.Manage и для назначения IP
со снятием IpAddresses.Manage. В последнем случае сохранение выбора блокируется.
Переходы прав не должны приводить к автоматическому созданию записи.

## 10. Отзыв чтения

1. В A откройте полную карточку или редактирование сотрудника.
2. В R снимите Write и ReadDetails, оставьте Read.
3. Проверьте A, затем снимите все права сотрудников.
4. Закройте диалог и вручную перейдите на `/personal`.

**Ожидается:** отзыв полного просмотра скрывает содержимое диалога с предупреждением,
но список остаётся. При полном отзыве меню и список недоступны, прямой адрес не
обходит защиту. Само окно не должно принудительно закрываться из-за события доступа.
Возврат чтения может показать уже загруженные данные; это не гарантирует их повторной
загрузки. Ранее показанные пользователю сведения невозможно фактически «забрать назад».

## 11. Несколько сеансов, роли и адресность событий

1. В A и A2 откройте разные формы, введите разные несохранённые значения.
2. В B также откройте форму и введите значение.
3. В R снимите Write только у роли A.

**Ожидается:** обе вкладки A блокируют запись и сохраняют свой ввод. B сохраняет
доступ и состояние формы. Если изменённая роль общая для A и B, уведомляются оба.

Дополнительно:

- Через «Роли и итоговые права» замените у A роль редактора на роль чтения:
  открытые формы отражают отзыв записи без нового входа.
- Верните редактора: доступ возвращается.
- Назначьте две роли с одинаковым Write, снимите его в одной: запись остаётся.
  Снимите во второй: запись блокируется.
- Удалите отдельную назначенную тестовую роль: её бывшие пользователи также
  получают обновление прав. Защищённую роль Root не используйте для этого теста.
- Root сохраняет полный прикладной доступ при изменении обычных ролей.

## 12. Таймер, навигация и восстановление соединения

**Ожидание без событий:** оставьте заполненный несохранённый диалог открытым минимум
130 секунд. Он не должен закрыться, потерять ввод или стать недоступным сам по себе.

**Навигация и открытие:** после изменения прав перейдите между страницами и откройте
новую форму. Интерфейс проверяет текущие права; «Добавить» должен открыть один диалог,
а не перезагрузить страницу. Навигация не обязана сохранять несохранённую форму.

**Восстановление:** в A откройте форму и введите маркер. В Network инструментов
разработчика отключите сеть только для вкладки A. Дождитесь потери соединения,
измените права в R и включите Online в A. После восстановления того же circuit
форма показывает актуальные права, маркер остаётся. Если circuit истёк или приложение
перезапущено и необходима полная перезагрузка, сохранение ввода не гарантируется.

Проверьте отправку формы сразу после отзыва права: перед сохранением выполняется
дополнительная проверка, а сервер отклоняет запрещённую операцию. Доставка события
не заменяет серверную авторизацию.

## 13. Конфликт версий и неуспешное сохранение

1. В двух вкладках Root откройте одну тестовую роль до изменения.
2. В первой измените permissions и сохраните.
3. Во второй попробуйте сохранить другой набор из устаревшей формы.

**Ожидается:** второй вариант отклоняется как конфликт; действуют права первого
успешного сохранения. Повторно откройте роль перед новой попыткой. Аналогично проверьте
две формы назначений одного пользователя. Ошибка не должна менять назначения,
закрывать несвязанные формы или стирать ввод в них.

Инициализацию «Администратор» проверяйте только в тестовой среде с существующей
пустой ролью: назначьте её тестовому пользователю, нажмите явную инициализацию
на `/roles`, проверьте появление несистемных прав. Повторная инициализация не должна
перезаписывать настроенную роль. Не очищайте реальные роли ради этого сценария.

## 14. Ограничения браузерной проверки

- Уведомления работают в одном процессе; несколько экземпляров требуют общего
  транспорта событий. Обновление интерфейса не имеет фиксированного срока доставки.
- Изменение БД напрямую не публикует событие. Актуальные права обнаруживаются при
  следующей предусмотренной проверке, а не обязательно немедленно.
- Событие доступа не перезагружает автоматически все таблицы и бизнес-данные.
- Старые IP вне подразделения сотрудника сохраняются отдельно, как описано выше.
- Обычная браузерная проверка не доказывает невозможность подделки ID, отсутствие
  внутренних лишних callback или атомарность транзакций. Эти случаи дополнительно
  проверяются сервисными и интеграционными тестами.

## 15. Протокол результатов и завершение

Для каждого раздела запишите:

| Проверка | Пользователь/вкладка | Исходные права и данные | Действие | Фактический результат | Статус |
| --- | --- | --- | --- | --- | --- |
| Создание сотрудника | R | | | | Не проверено |
| Создание пользователя | R | | | | Не проверено |
| Выбор IP по подразделению | R, A | | | | Не проверено |
| Вход и IP-допуск | A, B | | | | Не проверено |
| Область чтения и экспорт | A | | | | Не проверено |
| Отзыв/возврат записи | A, A2 | | | | Не проверено |
| Отзыв чтения | A | | | | Не проверено |
| Несколько сеансов | A, A2, B | | | | Не проверено |
| Ожидание 130 секунд | A | | | | Не проверено |
| Восстановление соединения | A | | | | Не проверено |
| Конфликт версий | R, R2 | | | | Не проверено |

При ошибке укажите шаг, время, URL, фактические роли, необходимость F5 и характер
восстановления соединения. Приложите скриншот и ошибку Console без паролей, cookies,
строк подключения и реальных персональных данных.

После проверки восстановите изменённые поля, роли, IP и статусы тестовых записей.
Не оставляйте тестовые учётные записи с лишними правами.
