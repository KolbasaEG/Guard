# Отчёт о нарушении целостности дерева подразделений в ответе кадрового API

Дата проверки: **10 октября 2026 года**. Время в отчёте указано по Минску, UTC+03:00.

## Суть проблемы

В полученном наборе `/subdivisions` подразделение с внешним `Id = 4448` содержит `ParentId = 2`, однако подразделение с `Id = 2` отсутствует среди всех полученных записей. Соответствующий родитель также отсутствует среди ранее импортированных подразделений в локальной БД Guard.

Это препятствует построению согласованного дерева подразделений и применению выгрузки в Guard. Причина исключения родителя из ответа пока не установлена: необходимо уточнение данных и контракта API.

## Параметры и способ проверки

| Параметр | Значение |
| --- | --- |
| Идентификатор диагностики | `01a125b0-2195-7ccf-8347-b63b6a24ab62` |
| Начало | 10.10.2026, 15:01:02 |
| Завершение | 10.10.2026, 15:04:41 |
| Продолжительность | Около 219,3 секунды |
| Метод запросов | POST |
| Ресурсы | `/classifiers`, `/subdivisions`, `/personnel` |
| Фильтр | `Data.UpdatedAt = "1962-10-01"` |
| Размер страницы | `Data.per_page = 500` |
| Обход страниц | Последовательный, `Data.page` от 1 до последней страницы каждого ресурса |
| Изменение данных Guard | Не выполнялось: отдельный диагностический режим |

Обязательный фильтр даты передавался на каждой странице всех трёх ресурсов. Дата выбрана существенно раньше предполагаемого начала внесения данных в источник. Это не доказывает полноту выдачи: фактическая семантика фильтра и возможные ограничения доступа требуют подтверждения разработчиков API.

Пример структуры запроса подразделений:

```json
{
  "Data": {
    "page": 1,
    "per_page": 500,
    "UpdatedAt": "1962-10-01"
  }
}
```

Запрос повторялся для страниц 2 и 3 с тем же фильтром и размером страницы. Учётные данные и заголовки авторизации в отчёт не включены.

## Подтверждённое нарушение

| Поле диагностики | Значение |
| --- | --- |
| Ресурс | `subdivisions` |
| Код нарушения | `MissingParentInResponse` |
| Внешний ID подразделения | `4448` |
| Поле связи | `ParentId` |
| ID отсутствующего родителя | `2` |
| Родитель найден в локальной БД | `false` |

Точная запись диагностического протокола:

```text
Диагностика 01a125b0-2195-7ccf-8347-b63b6a24ab62: нарушение "MissingParentInResponse", ресурс "subdivisions", запись "4448", поле "ParentId", ссылка "2", найдена локально False
```

Дополнительные результаты анализа:

- Записей подразделений с `ParentId = null` или `ParentId = 0` не обнаружено.
- Диагностика зарегистрировала одно нарушение во всём наборе.
- Других нарушений, предусмотренных текущим анализатором Guard, не обнаружено: дубликатов внешних ключей, циклов, некорректных проверяемых полей, отсутствующих подразделений сотрудников и отсутствующих справочных ссылок.

Последний пункт относится только к выполненным проверкам; он не подтверждает отсутствие скрытых записей, согласованность источника во времени или корректность всех бизнес-данных.

## Влияние на интеграцию

Предшествующий обычный запуск синхронизации 10.10.2026 в 14:50:04–14:53:40 с фильтром `UpdatedAt = "1987-10-01"` получил те же количества записей, но завершился на этапе применения ошибкой «Некорректное подразделение или отсутствующий родитель». Ошибка возникла при проверке дерева до изменения импортируемых данных.

Диагностический запуск установил конкретную отсутствующую связь. HTTP timeout, отмена страницы или остановка приложения не объясняют отказ предшествующего запуска. Guard не превращает неизвестного родителя в локальный корень автоматически: такое преобразование может изменить иерархию и область доступа пользователей.

## Вопросы разработчикам API

1. Что представляет собой запись с `Id = 2`: обычное подразделение, технический корень или объект другого типа? Существует ли она в источнике?
2. Почему запись `2` не возвращается в `/subdivisions` с фильтром `UpdatedAt = "1962-10-01"`, при том что на неё ссылается подразделение `4448`?
3. Исключают ли её права API-аккаунта, архивный/удалённый статус, отсутствие даты изменения или дополнительные серверные фильтры?
4. Какова точная семантика `UpdatedAt`: сравнение включительное или исключительное, какой часовой пояс используется, как обрабатываются отсутствующие даты и записи, которые никогда не изменялись?
5. Гарантирует ли выдача наличие всей цепочки родителей возвращённых подразделений? Если нет, как получить недостающих родителей: по ID, отдельным ресурсом или другим параметром?
6. Как API обозначает корневые узлы? Может ли положительный `ParentId` указывать на технический корень, который намеренно отсутствует в выдаче? Просим предоставить точное правило и идентификаторы либо иной устойчивый признак.
7. Обеспечивают ли страницы и три ресурса согласованное состояние во время обхода? Есть ли идентификатор снимка или другой механизм, предотвращающий изменение набора между запросами?

## Ожидаемый результат обращения

Просим проверить исходные записи `4448` и `2`, условия выборки и права используемого API-аккаунта и подтвердить один из вариантов:

- **`2` — обычное подразделение:** обеспечить получение этой записи и её необходимых родителей в рамках документированного сценария загрузки.
- **`2` — технический корень, исключённый намеренно:** документировать это правило и допустимое преобразование дочерних узлов в корни дерева потребителя. На основании согласованного контракта Guard сможет реализовать такое преобразование явно.
- **`ParentId = 2` — ошибочная связь:** исправить данные источника или формирование ответа.

Для повторной проверки необходимы документированное ожидаемое поведение и ответ API после исправления либо уточнения контракта. До получения такого подтверждения причина отсутствия родителя остаётся открытой; подтверждён сам факт отсутствующей связи.

## Основание отчёта

Отчёт составлен по событиям БД логов Guard, связанным указанным `DiagnosticRunId`, и реализации диагностического анализатора. Полные тела ответов не сохранялись; ID и связи приведены из структурированного протокола. Персональные данные сотрудников и секреты подключения в отчёт не включены.
