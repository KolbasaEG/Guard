**Команда Codex для Guard**  
Дополнение после диагностики среды: проектный лимит инструкций увеличен до 65536 байт; четыре проектных Skill, два .NET-плагина, три аналитических Skill и справочный каталог установлены. Точный состав, источник, ограничения и окружение валидатора — в [codex-skills.md. Ниже результаты первоначальной настройки сохранены как история; они не заменяют проверку обнаружения в новом чате.](codex-skills.md "codex-skills.md")  
Определены семь ролей для использования по необходимости после загрузки клиентом. Основной Codex остаётся разработчиком и координатором: оценивает риск, согласует контракты, назначает владельцев, объединяет результат и отвечает за итоговую проверку. Обычную задачу выполняет сам, включая тесты. Рабочие правила находятся в корневом [AGENTS.md, специализации — в](../AGENTS.md "../AGENTS.md") [.codex/agents. Этот документ не требуется читать целиком при каждом поручении.](../.codex/agents "../.codex/agents")  
**Ответственность**  
  
|  |  |  |  |  
| - | - | - | - |  
| **Роль** |  **Когда вызывать** |  **Что может менять по назначению** |  **Чего не делает** |  
| `guard_architect` |  Новая сквозная функция, границы, контракты, сложный рефакторинг |  Только явно порученную архитектурную документацию; обычно анализ |  Не меняет код, тесты, конфигурацию; не нужен для обычного DTO/CSS |  
| `guard_domain` |  Существенные инварианты, статусы, независимые правила дерева |  Назначенные файлы `Guard.Domain/` |  Не использует БД/HTTP/Identity и не придумывает полномочия |  
| `guard_application` |  Операции, DTO, поиск, серверный доступ, контракты |  Назначенные файлы `Guard.Application/` |  Не использует EF/PostgreSQL/HttpContext и не реализует хранилища |  
| `guard_infrastructure` |  Хранение, транзакции, конкурентность, миграции, интеграции |  Назначенные файлы `Guard.Infrastructure/`; миграции и snapshot у одного владельца |  Не придумывает бизнес-правила и не применяет миграции к рабочей БД |  
| `guard_web` |  Blazor/Radzen, страницы, middleware, endpoints |  Назначенные файлы `Guard/`; композиция только у назначенного владельца |  Не размещает бизнес-правила и доступ к DbContext в компонентах |  
| `guard_tester` |  Нетривиальные проверки и регрессии, PostgreSQL, браузер |  Назначенные тесты, фикстуры и тестовую конфигурацию двух тестовых проектов |  Не меняет production без передачи задачи и не ослабляет проверки |  
| `guard_security` |  Аутентификация, полномочия, область данных, чувствительные endpoints |  По умолчанию никаких файлов |  Не выполняет полный аудит и не исправляет находки самостоятельно |  
  
   
Специализация не обязывает делегировать каждую правку слоя. Общие файлы и контракты получают единственного владельца до начала изменений. Тесты принадлежат координатору либо назначенному tester; передача другому исполнителю должна быть явной. Субагент не создаёт свою ветку и не делегирует дальше.  
**Фактическая структура и целевые границы**  
На дату настройки, 19 октября 2026 года, `Guard.slnx` содержит шесть проектов непосредственно в корне, все на `net10.0`. `global.json` и общие `Directory.Build.*`/`Directory.Packages.props` в репозитории не обнаружены; SDK не закреплён таким файлом. Web — это `Guard/Guard.csproj`, а не отдельный `Guard.Web`.  
- Domain не имеет пакетов и ProjectReference; Application ссылается на Domain и использует BCL.  
- Infrastructure ссылается на Domain/Application, содержит EF/Identity 10.0.12, Npgsql EF 10.0.3, Scrutor, Serilog; сохраняется также зависимость Radzen 11.4.0. Это фактический состав, не рекомендация вводить UI-зависимости в Infrastructure.  
- Web ссылается на три библиотеки, использует Blazor InteractiveServer и Radzen 11.4.0; DI собирается в `Guard/GuardServiceRegistration.cs` и регистрациях слоёв. Наличие MediatR/FluentValidation не задаёт обязательный стиль операций.  
- UnitTests — исполняемый runner с собственным `Check`, ссылается только на Domain/Application. IntegrationTests — отдельный runner с зависимостями от четырёх production-проектов, включая быстрые инфраструктурные, HTTP, PostgreSQL и браузерные сценарии. xUnit/NUnit не используются. `scripts/Test-Guard.ps1` последовательно запускает оба уже собранных runner.  
Цель: независимые предметные инварианты — Domain; порядок операции, доступ и внешние контракты — Application; хранение и технические гарантии — Infrastructure; UI/HTTP и композиция — Web. Компоненты вызывают Application и не обращаются к БД напрямую.  
Перенос ещё не завершён: `EntityStatusTransitions` и `SubdivisionAccessPath` находятся в Application, `SubdivisionService` с EF-зависимыми операциями и проверками доступа — в Infrastructure. Существующие namespace сохранены. Координатор назначает владельца по фактическому файлу; перенос согласует отдельно. Настройка агентов не исправляет архитектуру и не закрепляет текущие отклонения как образец.  
**Параллелизм, модели и Skills**  
В [.codex/config.toml задано `agents.enabled = true` и `agents.max_concurrent_threads_per_session = 2`. Это технический предел одновременно открытых дочерних потоков после применения конфигурации поддерживающим клиентом, без основного потока. Семь определений ролей не означают семь запусков. Более строгие управляемые ограничения сохраняются.](../.codex/config.toml "../.codex/config.toml")  
Один пишущий исполнитель в общей папке, отсутствие вложенного делегирования, владение файлами и ориентиры до двух запусков на обычную задачу / четырёх на крупную — инструкции модели, а не технические блокировки. Обычно работает ноль или один субагент. Второй допускается для независимого анализа стабильной области. После завершения освобождают ненужные потоки штатным средством клиента; отсутствие такого средства сообщают, учитывая поток в лимите. Не создают изолированную параллельную разработку без отдельного поручения.  
Модель и уровень рассуждений задаются явно в TOML-файле каждой роли  
через параметры \`model\` и \`model_reasoning_effort\`. Эти файлы являются  
основным источником сведений о выбранной конфигурации; утверждение  
об общем наследовании модели всеми ролями больше не применяется.  
   
Принята следующая базовая политика:  
\- \`guard_architect\`, \`guard_infrastructure\` и \`guard_security\` —  
  уровень рассуждений \`high\` для архитектуры, конкурентности,  
  транзакций и проверки безопасности;  
\- \`guard_domain\`, \`guard_application\`, \`guard_web\` и \`guard_tester\` —  
  уровень \`medium\` для обычной реализации и тестирования  
  в пределах согласованных требований.  
   
Простые задачи, адресный поиск и небольшие изменения основной Codex  
обычно выполняет самостоятельно, без запуска субагентов,  
используя подходящий экономичный режим. Наличие специализированной  
роли не обязывает делегировать ей каждую правку соответствующего слоя.  
   
Конкретную модель и уровень рассуждений назначают только после  
подтверждения их доступности и совместимости с используемым клиентом.  
Отклонение от базовой политики должно быть обосновано задачей  
и отражено в соответствующей конфигурации. При недоступности  
назначенной модели исполнитель сообщает ограничение, а не заявляет,  
что требуемый режим использован.  
   
Максимальный уровень рассуждений и самая ресурсоёмкая модель  
не назначаются всем ролям автоматически. Эффективность выбранных  
режимов оценивается по качеству завершённых задач, фактическому  
расходу и числу повторных исправлений. Процент экономии  
без измерений не заявляется.  
Для этой настройки использован реально доступный `openai-docs`. Специальные Skills для .NET, EF или security не предполагаются установленными. Figma, документы и другие нерелевантные навыки не подключались. Навыки выбирают по конкретной задаче; их отсутствие не блокирует обычную роль. Новые Skills, плагины и MCP не устанавливались; глобальная конфигурация, sandbox, подтверждения и авторизация не редактировались.  
**Передача задачи**  
```  
Цель: одна конкретная подзадача.  
 Известные факты: краткий контекст, согласованные решения.  
 Область чтения: файлы, символы, необходимые зависимости.  
 Разрешённые изменения: точные файлы/каталоги либо «не изменять файлы».  
 Ограничения: контракты, безопасность, чужие изменения, проверки.  
 Готовность: проверяемые критерии завершения.  
 Результат: что вернуть координатору.  
   
```  
Ответ: итог; файлы или находки; реально выполненные проверки; блокеры и непроверенные предположения; действие координатора. Для существенной находки нужны место, условия, последствия и доказательства. Не пересылают всю переписку, исходники и логи. Область чтения расширяют по необходимости; ревьюер самостоятельно подтверждает существенные выводы.  
При выходе за полномочия, конфликте изменений, неизвестном критичном правиле или небезопасной проверке субагент останавливает зависимую работу и сообщает конкретный блокер. После двух неудачных попыток устранить одну причину меняют подход, а не повторяют его.  
**Самопроверка маршрутизации**  
Это мысленная проверка инструкций, без реальных запусков и без доказательства поведения модели.  
  
|  |  |  |  
| - | - | - |  
| **Задача** |  **Выбор и последовательность** |  **Владение изменениями** |  
| Поменять подпись кнопки Radzen |  Без субагентов; координатор меняет и проверяет экран |  Координатор: нужный файл `Guard/` |  
| Исправить локальное предметное правило |  Без субагентов при ясном правиле; при существенной сложности один `guard_domain` |  Координатор: фактический файл и тест; если правило ещё в Application, не переносить его попутно. Domain-агент получает только согласованную область |  
| Перемещение подразделения через все слои |  При новом решении `guard_architect` → координатор согласует контракты и реализует Domain/Application/Web → `guard_infrastructure` реализует атомарное хранение → `guard_tester` проверяет → `guard_security` проверяет стабильный доступ к дереву |  Исполнители последовательно получают свои области; координатор владеет контрактами, Infrastructure — хранением и миграциями, tester — тестами. Четыре запуска, ни одного параллельного изменения |  
| Изменить наследование полномочий |  Координатор уточняет ожидаемую политику и реализует → `guard_security` независимо проверяет; tester нужен только для сложной тестовой части |  Координатор: операции/контракты; тесты у него либо явно переданы tester; security только читает |  
| Добавить рискованную миграцию |  `guard_infrastructure` готовит миграцию, snapshot и план восстановления → `guard_tester` проверяет совместимость и восстановление на изолированной БД |  Infrastructure — единственный владелец миграций, tester — тесты; применение к рабочей БД требует отдельного поручения. Security подключается при риске изменения доступа, не автоматически |  
| Исправить падающий интеграционный тест |  При нетривиальном воспроизведении `guard_tester` исследует; исправляет ошибку теста либо возвращает production-причину координатору → владелец устраняет → повторная проверка |  Tester: тесты/фикстуры; координатор: production при необходимости. Проверку после исправления обычно выполняет координатор без нового запуска |  
  
   
Простой пример поручения: «Измени подпись кнопки в указанном компоненте, проверь сценарий; субагенты не нужны». Сложный: «Согласуй перемещение дерева с архитектором, передай атомарное хранение Infrastructure, затем проверь изолированные сценарии tester и область доступа security; изменения выполняй последовательно».  
**Проверка настройки и ограничения**  
Формат сверяется с официальными страницами [Subagents,](https://learn.chatgpt.com/docs/agent-configuration/subagents "https://learn.chatgpt.com/docs/agent-configuration/subagents") [Configuration Reference и](https://learn.chatgpt.com/docs/config-file/config-reference "https://learn.chatgpt.com/docs/config-file/config-reference") [AGENTS.md. Используются standalone-файлы с `name`, `description`, `developer_instructions`; идентификатор берётся из `name`, поэтому дефисы в именах файлов и подчёркивания в идентификаторах намеренны. Старые таблицы регистрации ролей и `max_threads` не добавляются.](https://learn.chatgpt.com/docs/agent-configuration/agents-md "https://learn.chatgpt.com/docs/agent-configuration/agents-md")  
Различайте четыре уровня проверки:  
1. **Синтаксис:** разобрать восемь TOML-файлов TOML-парсером; убедиться в семи уникальных именах и непустых обязательных строках, отсутствии лишних ключей, существовании назначенных каталогов.  
2. **Схема:** сверить поля с документацией и выполнить доступную штатную строгую проверку конфигурации установленного клиента. На этой машине обнаружен `codex-cli 0.162.0-alpha.2`; путь CLI совпадает с путём работающего процесса `codex.exe` в комплекте приложения. Это версия серверного бинарного файла, а не версия интерфейса desktop. `codex --strict-config doctor --summary --ascii --no-color` сообщил `config loaded` и успешную инициализацию desktop app-server. Его общий код выхода 1 связан с другими диагностическими ошибками, поэтому весь doctor не считается успешным. `--strict-config` для `features` этой версией не поддерживается. Сгенерированная локально схема app-server описывает протокол, а не полную схему файлов ролей.  
3. **Обнаружение:** загрузка семи custom-ролей приложением не подтверждена. Штатный `codex debug prompt-input` выполнен без модельного запуска: имена обнаружены только в тексте AGENTS.md, а не в отдельном каталоге ролей. Это подтверждает чтение инструкций, но не регистрацию custom-агентов. Проба `config/read` через отдельный stdio app-server не получила ответа в отведённое время; эффективный лимит сессии этим способом не подтверждён. Текущий чат начат до создания файлов; его доступные инструменты не доказывают загрузку новой конфигурации. Для применения откройте новый чат в этом репозитории; при необходимости перезапустите приложение. Не меняйте доверие к проекту и управляемые ограничения ради проверки. Если профильная роль недоступна, сообщите ограничение, не называя обычный субагент загруженной ролью.  
4. **Поведение:** реальные вызовы и соблюдение маршрутизации в этой настройке не проверялись; вся команда не запускалась. Проверку поведения при необходимости проводят отдельной маленькой задачей с одной явно выбранной ролью.  
Проверка состава изменений: `git status --short`, `git diff --check`, просмотр diff и новых файлов. Исходники, существующие тесты, пакеты и миграции должны оставаться неизменными. Для этой настройки сборка Guard и тесты приложения не требуются и не запускались. Вложенные AGENTS.md не создавались: специфические правила уже есть в корневых инструкциях и ролях.  
При создании выполнены разбор восьми TOML через Python 3.12 `tomllib`, проверки семи уникальных имён, точного набора обязательных полей, их типов и непустых значений, существования каталогов и файлов проекта. Ключи сверены с опубликованным форматом; отдельный локальный JSON Schema-валидатор файлов custom-ролей не найден. Инструкции ролей содержат 267–291 слово. Программно проверено сохранение прежнего текста AGENTS.md и ограничение изменений десятью назначенными файлами; `git diff --check` прошёл. Исходники и существующие тесты не изменены. Самопроверка маршрутизации приведена выше; запусков субагентов не было.
