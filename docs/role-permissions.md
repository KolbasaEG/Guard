# Роли и настраиваемые права доступа

## Принятые правила

Источником полномочий служат только назначения в AspNetUserRoles и claims типа
Permission в AspNetRoleClaims. Права нескольких ролей объединяются. Индивидуальные
AspNetUserClaims остаются в БД, но не дают доступа. Root получает все известные
разрешения и доступ ко всем подразделениям. Неизвестные коды не действуют даже для Root.

Обычный пользователь видит своё подразделение сотрудника и его потомков.
Если сотрудник, подразделение или корректный путь не назначены, область доступа пуста.
Фильтр пользователя может только сузить эту область. Общие классификаторы и типы
органов доступны по соответствующим permissions, без фильтра подразделения.

Права заново читаются из БД при каждом защищённом вызове. Заблокированная учётная запись не получает прикладных прав даже со старой cookie.
Claims старой cookie
не являются основанием для доступа. Меню и кнопки обновляются по событиям изменения
ролей и их permissions после успешного commit. Уведомляются все открытые сеансы
затронутых пользователей. Диалоги остаются открытыми: отзыв записи блокирует форму
с сохранением введённых значений, отзыв чтения скрывает содержимое. Права дополнительно
обновляются при навигации, открытии диалога, восстановлении соединения и перед/после
отправки формы. Таймер отсутствует. Уведомления действуют внутри одного процесса;
при нескольких экземплярах приложения потребуется общий транспорт событий.
Изменения напрямую в БД не создают событий и обнаруживаются при следующей проверке. Сервер отклоняет следующую операцию
сразу после отзыва права. Уже переданные пользователю сведения нельзя отозвать.

IP-допуск остаётся отдельной проверкой: IP сотрудника, пустой список запрещает вход,
Root освобождён; проверка при входе и новом соединении.

## Каталог

PermissionCatalog описывает стабильный код, группу, русское название, пояснение,
зависимость и системный признак каждого разрешения.

| Модуль | Права |
| --- | --- |
| Сотрудники | Read, ReadDetails, ReadArchive, Write, Export |
| Подразделения | Read, ReadArchive, Write |
| Пользователи | Read, Manage |
| IP-адреса | Read, Manage |
| Классификаторы | Read, Manage |
| Типы органов | Read, Manage |
| Логи | Read, Configure; только Root |
| Роли | Read, Manage; только Root |

Имена кодов определены в Guard/Core/Identity/Permissions.cs; существующие коды
сохранены. Write/Manage зависят от чтения, ReadDetails от Read.
Селектор автоматически добавляет зависимости; сервер проверяет их независимо.
Существующий некорректный набор claims не даёт зависимое право.

Список сотрудников содержит только идентификатор, ФИО, подразделение и статус.
Личный номер, год службы, внешние идентификаторы, классификаторы и аудит появляются
только в полной карточке с ReadDetails. CSV требует Export и использует те же
фильтры и область доступа, что список; выгружаются ФИО и подразделение.
Архив требует ReadArchive, удалённые сотрудники и подразделения доступны только Root.
Справочные значения в форме подразделения доступны как часть операции Write;
это не открывает самостоятельные страницы справочников.

## Компоненты и сервисы

- PermissionService, PermissionAuthorizationHandler: актуальные permissions и политики маршрутов.
- DataAccessScopeService: безопасная область подразделений.
- ReadRepository: обязательные permissions и область чтения до пользовательского LINQ.
- PersonalService.GetDetailsAsync: DTO полной карточки без связанных Identity-секретов.
- PersonalService.SearchAsync: SQL-проекция безопасного списка, сортировка по разрешённым полям, подсчёт и пагинация.
- RoleAccessService: роли и их permissions, назначения пользователей, отчёт перехода.
- Layout/Components/AccessStateProvider: каскадное состояние доступа и обновление интерфейса.
- Library/Authorization: PermissionView, AccessDenied и селектор с данными каталога через параметры.
- Roles/Add и Edit: поиск, группы разрешений, зависимости.
- Users/RoleAssignments: выбор ролей и отображение текущих итоговых permissions.
- Personals/Details: отдельная карточка просмотра; Edit редактирует сотрудника.
- Forms/EntityForm и EditEntity: совместимый режим ReadOnly без отправки формы.

Серверные проверки распространяются на запись, изменение статусов, синхронизацию
классификаторов, каталог IP, назначения IP, управление пользователями и логи.
Операции Identity с несколькими шагами выполняются в отдельном DI scope и транзакции.
Все IdentityResult проверяются; ошибка откатывает составную операцию.

Роли меняет только Root. Root нельзя переименовать, изменить или удалить.
Нельзя снять роль у последнего незаблокированного Root. Системную учётную запись
нельзя блокировать через административный сервис. Редактирование профиля не меняет
роли: используется отдельная форма назначений.

ConcurrencyStamp защищает сохранение роли; версия назначений включает stamp
пользователя и текущий набор role IDs. PostgreSQL advisory lock сериализует
операции управления доступом. При конфликте оператор должен открыть форму заново.
Инициализация также обновляет stamp. Изменения ролей и назначений, отказы в
permissions проходят через IAuditService; AccessDenied имеет outcome=failure.

## Переход существующей базы

Изменения схемы не требуются: используются штатные таблицы Identity.
При запуске приложения права существующих ролей автоматически не перезаписываются.

1. Войти как существующий Root и открыть «Роли».
2. Проверить отчёт: число сохранённых индивидуальных permission claims и роли
   без настроенных permissions. Пустая обычная роль не даёт доступа к модулям.
3. Настроить каждую роль. Для пустой роли «Администратор» есть явная кнопка,
   добавляющая все несистемные permissions. Она не перезаписывает настроенную роль.
4. В «Пользователи» открыть «Роли и итоговые права», проверить назначения.
5. Проверить сотрудника и его подразделение у обычных пользователей.
6. Проверить список, карточку, архив, экспорт и попытку доступа к чужой записи.

Индивидуальные permissions не удалять при переходе; они остаются для анализа
и отдельного решения о дальнейшей очистке. Новые индивидуальные права не назначаются.

## Проверки

Пошаговые сценарии ручной проверки интерфейса, диалогов и нескольких сеансов:
[Проверка через браузер](access-events-browser-testing.md).

Из корня репозитория:

```powershell
dotnet build Guard.slnx --no-restore
dotnet run --project Guard.IpRules.Tests/Guard.IpRules.Tests.csproj --no-build
dotnet run --project Guard.IpRules.Tests/Guard.IpRules.Tests.csproj --no-build -- --postgres Guard/appsettings.json
```

Интеграционный режим допускает только localhost. Создаёт отдельную временную
БД с UUID, применяет EnsureCreated и удаляет только её. Исходную БД не изменяет,
приложение и production seeding не запускает. Нужны права создавать тестовую БД.

Проверяются IP-регрессии, объединение и отзыв прав, игнорирование индивидуальных
claims, Root, зависимости, серверные запреты, область списка/подсчёта/экспорта,
пустая и некорректная область, конкуренция ролей и назначений, откат составной
Identity-операции и явная инициализация без перезаписи.
Браузерный сценарий с несколькими одновременно открытыми сессиями нужно проверить
в рабочей тестовой среде; сборка и сервисные тесты не заменяют визуальную проверку.
