# Исходная база архитектурного перехода

Актуализация 17 октября 2026 года: пользователь исправил размер каталога IP на примерно **500 000**. Остальные ориентиры прежние: 200 000 сотрудников, 1 000 подразделений, 100 000 строк экспорта. Упоминания 10 млн IP и результаты прежних замеров ниже являются историческими, не текущим целевым объёмом. Текущий стенд и [подготовка каталога](ip-catalog-canonical-keys.md) используют исправленный объём.

Дата: 16 октября 2026 года. Реализация приложения — `d71358e`; план — `95fa145`.
Этап 0 выполняется в `codex/architecture-stage-0`, созданной от ветки плана,
чтобы утверждённый документ был доступен вместе с реализацией. В main эта ветка
ещё не слита. Следующие этапы начинаются после проверки и принятия текущего.

## Объём и порядок переноса

Сейчас в solution два проекта: Web и исполняемый runner. Шесть списков строят
EF-запросы в code-behind: IpAddresses, Subdivisions, Classifiers, Users, Roles,
Logs. Сотрудники используют SearchAsync; это исходный пример разделения, но
IPersonalService ещё содержит legacy-чтение сущностей и query-делегат.
Identity endpoints также используют EF: их нельзя механически запретить вместе
с запросами списков, поскольку Identity UI и endpoints остаются в Web.

Это ориентир в 12 поставок, внутри этапов утверждённого плана. Календарный срок
не определён: поиск по 10 млн IP и перенос контрактов потребуют отдельной оценки
по первым двум поставкам. Переименование каталогов и обновление пакетов не входят.

Legacy API перечислен в инвентаре, включая интерфейсы репозиториев. Его нельзя
удалять только по отсутствию вызова из Index: формы, выборы, экспорт и фоновые
операции тоже являются потребителями. ApplicationUser/ApplicationRole проникают
прежде всего через ISecurityService/IApplicationRoleService и навигацию Personal.User;
UserDto уже содержит скалярные данные. Не нужно переписывать все DTO заново.

Дополнительные зависимости, мешающие механическому выделению сборок:
ICurrentUserService возвращает UserContext с ApplicationUser и графом сотрудника;
EntityStatusTransitions выбрасывает EntityRuleException из Services. При выделении
Domain перенести независимый тип ошибки вместе с правилом либо адаптировать
его на прикладной границе, сохранив сообщения и обработку формы. Не создавать
обратную ссылку Domain → Application ради прежнего namespace. ApplicationDbContext
также использует прикладную ошибку режима API: учесть её при парном переносе
Application/Infrastructure, а не копировать одноимённые типы между сборками.

## Доступ и состояния: база для сравнения

Источник permissions — назначенные роли и PermissionCatalog с зависимостями.
Название роли «Администратор» и индивидуальные claims не предоставляют доступ.
Root имеет полный серверный доступ; выбранное отображение «свои» продолжает
ограничивать его список. Для обычного пользователя пустой/некорректный Path
означает пустую область. Path использует числовой SubdivisionId, а FK — Guid Id.

| Область | Полномочия и область | Дополнительные ограничения |
| --- | --- | --- |
| Сотрудники | Personals.Read для списка, ReadDetails для полной карточки, Write для записи; подразделение и потомки | ReadArchive и Export проверяются отдельно; Deleted только Root; режим API запрещает ручную запись справочника |
| Подразделения | Subdivisions.Read/Write, ReadArchive/Export отдельно; серверная область | Перемещение проверяет и исходный узел, и нового родителя; перестроение дерева только Root; в API запись запрещена |
| IP | IpAddresses.Read/Manage/Export; Root либо доступные подразделения | Общие IP только Root; назначения — активные IP именно подразделения сотрудника, даже у Root; каталог IP остаётся локальным в API |
| Классификаторы | Classifiers.Read/Manage | Общий справочник; уникальность Type+Code; в API ручная запись запрещена |
| Учётные записи | Users.Read/Manage и серверная область | Защита Root, уникальная привязка сотрудника; локальные изменения/привязки разрешены в API; обязательны IdentityResult и stamp |
| Роли | Roles.Read/Manage из каталога; управление только Root | Версия роли/назначений, транзакция, защита последнего Root; индивидуальные permission claims не учитываются |
| Журналы | Logs.Read/Configure | Отдельная БД журналов; технические события отдельно от Identity-аудита |
| Экспорт | Permission соответствующей области плюс условия архива/удалённых записей | Exports.ReadArchive/Configure для архива согласно каталогу; повторный доступ автора, stamp и область при выдаче; AllSubdivisions только Root |
| Синхронизация/политики | Настройки и запуск по актуальному каталогу и Root-only ограничениям | Старый Synchronization.Run не выдавать как новое право; AccountPolicy.Save только Root; фоновые операции не требуют circuit |

Значения Status фиксированы: Inserted=1, Modified=2, Blocked=3, Archived=4,
ArchivedBlocked=5, Deleted=6. Активный список включает блокированные записи;
IP-допуск — только Inserted/Modified. Изменение полей справочника/IP допускается
в Inserted/Modified. Общие переходы задаёт EntityStatusTransitions, IP — отдельный
IpStatusTransitions. Восстановление Deleted в общем правиле требует Root, у IP
сейчас применяется отдельное правило без этого параметра: при переносе не
унифицировать их скрытым изменением поведения.

## Контексты, атомарность и DI

- Основная БД содержит справочник, Identity, экспорт и состояние синхронизации;
  LogsDbContext обслуживает отдельную БД. В обычном старте Program создаёт
  физические БД; Development также запускает seeding. Проверка сборки не требует старта.
- ReadRepository открывает контекст фабрики на вызов, накладывает защиту по
  typeof(T), материализует делегат до освобождения. При замене репозитория эти
  проверки должны перейти в конкретную операцию до удаления старой защиты.
- Personal/Subdivision/Classifier используют UnitOfWorkFactory на запись;
  PrepareAudit запоминает доверенного автора. Scoped-контекст с интерцептором
  также зарегистрирован; это отдельный путь, его нельзя считать изолированным
  на операцию в интерактивном circuit.
- UnitOfWork.CommitTransactionAsync сам вызывает SaveChangesAsync. Промежуточный
  SaveChanges внутри ExecuteInTransaction допустим лишь с проверенным откатом.
- SecurityService и RoleAccessService создают scopes, получают DbContext и
  Identity managers. Операция переноса должна сохранять общий контекст и
  транзакцию обязательных Identity-шагов.
- IServiceProvider используется также AccountPolicyService/PolicyUserManager,
  workers и Identity UI. Разделить service locator прикладных операций и
  допустимый scope host-обёрток; не заменять это единым запретом текста.
- Scrutor сканирует Program.Assembly; конфигурации EF — executing assembly.
  Typed DirectoryApiClient исключён из сканирования. При переносе обязательны
  явные регистрации, scopes, настройки HttpClient и отсутствие дубликатов.

| Блокировка | Где и для чего | Что сохранять |
| --- | --- | --- |
| 73460219 | ApplicationDbContext.ManagementLock; ручная запись справочника, назначения IP, смена режима, применение снимка | Транзакционная блокировка до завершения записи; повторная проверка режима под ней |

## Схема и эксплуатационная совместимость

Исходный список миграций: от 20260610123225_InitialCreate до
20261015174116_AddApiSnapshotConfirmation, всего 40. Файлы и SHA256 включены
в инвентарь. Полную историю не изменять; EnsureCreated не доказывает её применимость.

Ключевые границы модели:

- Personal → Subdivision, IP → Subdivision, Subdivision → Parent: Restrict.
- ApplicationUser.PersonalId: уникальная nullable-связь один к одному, SetNull.
  Удаление Personal.User при выделении Domain сохраняет FK/индекс/имена таблиц.
- PersonalIpAddresses: many-to-many, не заменять отдельными IP учётной записи.
- Classifier имеет альтернативный ключ Type+Code; составные FK сотрудников и
  подразделений используют его с Restrict.
- Уникальны IP.Address, внешние ID, Subdivision.SubdivisionId, Personal.PersonalId;
  имя индекса с UX само по себе не доказывает IsUnique.
- Path имеет varchar_pattern_ops; индекс Subdivision Status+InsertedDate имеет
  заданное направление сортировки. IP не имеет такого же составного индекса.
- Version является concurrency token сотрудников, подразделений, классификаторов,
  настроек синхронизации и политик; Identity использует собственные stamps.
  Каталог IP не получает Version автоматически при переносе.

Маршруты вместе с Account/Manage и параметром passkey записаны в инвентаре;
сохранить регистр `/Logs`, `/AdminPannel`, `/personal`, `/ip` и прочих путей.
В репозитории есть Development launch profiles http/https; готовой инструкции
production-службы, reverse proxy или publish profile не найдено. Перед этапом 5
нужно получить фактические команды запуска, content root, учётную запись службы,
места ключей/архива и резервирования; они сейчас не подтверждены.

DataProtection.KeyDirectory/ApplicationName/CertificateThumbprint опциональны;
не выводить значения или считать defaults рабочей конфигурацией. Сохранить
UserSecretsId, cookie-схемы и эффективный application discriminator.
ExportOptions.Directory по умолчанию App_Data/Exports относительно ContentRoot;
purposes: Guard.Exports.v1 и Guard.DirectoryApi.BasicPassword.v1. Файлы защищены,
архив имеет Windows ACL. Перемещение Web не должно менять эти условия.

## Проверки и измерения

Независимый режим runner включает рендеринг/HTTP/файловые ACL и не является
набором только unit-тестов. PostgreSQL-режим дополняет его проверками доступа,
версий, отката, синхронизации, экспорта и Identity.

Результаты этапа и измерений приведены ниже. Браузер,
полная цепочка миграций, конкурентные перемещения дерева, репрезентативное
распределение назначений 10 млн IP и production-развёртывание остаются отдельными
воротами плана. На этапе 0 приложение и рабочая БД не изменяются.

Команды проверки из корня:

```powershell
dotnet build Guard.slnx --no-restore -v quiet
dotnet run --project Guard.IpRules.Tests/Guard.IpRules.Tests.csproj --no-build -- --postgres Guard/appsettings.json
dotnet run --project Guard.IpRules.Tests/Guard.IpRules.Tests.csproj --no-build -- --benchmark Guard/appsettings.json
```

Режим `--benchmark` запускается отдельно от регрессии и только явно. Он использует
тот же PostgreSQL harness: допускает только loopback host, создаёт случайную БД
guard_ip_test_UUID, строит модель через EnsureCreated и удаляет только эту БД в
finally. На полном наборе нужна память/место PostgreSQL и несколько минут загрузки;
в этом запуске проверено свободное место локальных дисков до подготовки.
Прерывание процесса извне может не выполнить finally — оставшуюся БД нужно
идентифицировать по конкретному запуску, не очищать все БД по префиксу.

Синтетический набор фиксирован: 1000 корневых подразделений, 200000 сотрудников,
10 млн уникальных IPv6, равномерное распределение по подразделениям (10000 IP
и 200 сотрудников на одно). Все записи активны. Первые 100000 сотрудников
отбираются фильтром LastName=Export. Фамилии/имена синтетические, UUID детерминированы
через md5 для загрузки больших таблиц; это отличается от рабочих UUIDv7.
Существующие FK и индексы включены во время вставки; затем выполняется ANALYZE.

Для сотрудников используется реальный построитель ExportQueries.PersonalsAsync,
на котором основан SearchAsync, затем Count и DTO-проекция страницы в 20 строк.
Для IP замеряется явно описанный EF-запрос Count+страница с сортировкой Address+Id:
все записи и одно подразделение. Это не замер сортировки IP по умолчанию
InsertedDate+Id и не прохождение UI/circuit. Первая операция включает JIT/пулы/
кеши; последующие пять дают median/max прогретого режима. «Первая» не означает
холодный диск. Кеши PostgreSQL и ОС принудительно не сбрасываются.

Экспорт вызывает действующие ExportSnapshot и ExportDocumentWriter, включая
RepeatableRead, защищённый файл строк, Excel и упаковку частей по 50000 строк.
Здесь доверенный Root-контекст задан самим стендом; нет HTTP, очереди, реальных
checkpoint-запросов, финального защищённого архива и доставки. Проверки этих
границ выполняются регрессионным ExportIntegrationTests на малом наборе.
Временный файловый каталог создаётся вне рабочей директории архива и удаляется.
Это базовое время серверных частей, а не SLA полного экспорта.

Вывод для следующих поставок: сохранить серверную пагинацию и потоковый экспорт;
не материализовывать 10 млн IP в UI, DTO выбора или кэш. Большие legacy GetAll
удалять по потребителям, замещая ограниченным поиском. Поздняя страница сотрудников,
фильтры строк, сортировка IP по умолчанию, большие назначения одному сотруднику,
глубокие деревья, перекос распределения и параллельный экспорт требуют отдельных
замеров перед приёмкой соответствующей области. Индексы, keyset-пагинация или
новые ограничения не добавляются под видом механического переноса.
