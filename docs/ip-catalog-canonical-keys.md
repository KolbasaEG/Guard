# Индексируемая уникальность IP

Дата: 17 октября 2026 года. Ветка: `codex/architecture-ip-search`, база `58e7e9c`.

Текущий целевой объём после уточнения пользователя: около **500 тыс. IP**, 200 тыс. сотрудников, 1 тыс. подразделений, экспорт 100 тыс. строк. Прежние 10 млн IP были ошибочным ориентиром.

## Изменение

IpAddressService больше не материализует все Address для проверки одной записи. Под прежней транзакционной блокировкой каталога 74162001 выполняются два EXISTS: наличие неподготовленных строк и совпадение канонического ключа с исключением текущего ID при редактировании. Проверка остаётся глобальной, включая архив, блокировку и удалённые записи.

В Infrastructure добавлены два shadow-поля EF: CanonicalAddress и CanonicalSource. Domain, DTO и формат Address не меняются. Ключ вычисляет существующий IpAddressRule; отдельного SQL-парсера с другой семантикой нет. CanonicalSource сохраняет исходную строку, а CHECK запрещает использовать ключ вместе с другим Address. Все обычные синхронные и асинхронные сохранения ApplicationDbContext обновляют оба поля при добавлении или изменении адреса.

Индекс CanonicalAddress намеренно не уникальный: эквивалентные старые строки могут иметь разные ID и назначения сотрудникам. Подготовка не объединяет и не удаляет их; новые дубли запрещает операция под блокировкой. Прямые EF/SQL-записи не заменяют этот протокол и не являются разрешённым API управления каталогом. Существующий уникальный индекс исходного Address сохраняется.

| Значение ключа | Смысл |
| --- | --- |
| NULL | Строка ещё не подготовлена; создание и редактирование адресов запрещены |
| Пустая строка | Старое значение не разбирается IpAddressRule; сохранено, как раньше не участвует в эквивалентности |
| Канонический адрес | Точное равенство существующему правилу, включая mapped IPv6, полные префиксы и маскирование CIDR |

Дополнительный частичный индекс по Id при CanonicalAddress IS NULL поддерживает проверку готовности и пакетную подготовку. На пакет выполняется один параметризованный UPDATE FROM unnest массивов ID/ключей/источников, без обновления остальных столбцов. Число изменённых строк проверяется до commit. Старые значения не требуется нормализовать в самом Address. Изменение правил IpAddressRule в будущем требует отдельного пересчёта ключей.

## Подготовка существующей БД

Пользователь согласовал окно обслуживания с запретом записи. Здесь подготовлены код и миграция; к рабочей БД они не применялись.

1. Проверить результат и разрешить выпуск. Сохранить резервную копию штатным способом. Запретить запись в каталог всем старым экземплярам приложения и внешним загрузчикам. Новая версия требует новой схемы; смешанная запись старой и новой версией не поддерживается.
2. Применить миграцию 20261017120000_AddIpCanonicalKeys штатным инструментом развёртывания, после предыдущей 20261015174116_AddApiSnapshotConfirmation. Автоматический startup приложения её не применяет. Старые миграции не изменены. DDL и создание индексов могут блокировать чтение до окончания транзакции; их время на большой существующей БД нужно учитывать отдельно.
3. Из каталога опубликованного Web-приложения с проверенным подключением основной БД выполнить:

   ```powershell
   dotnet Guard.dll --prepare-ip-catalog --confirm-maintenance
   ```

   Режим использует обычную конфигурацию ASP.NET, включая переменные окружения. Сам HTTP-host, создание БД, миграции, seeding и логгер приложения не запускаются. Команда без одного из флагов или с лишними аргументами завершается до подключения. Не передавать строку подключения в командной строке.

4. Дождаться сообщения «Подготовка завершена». За один пакет обрабатывается до 2 000 строк; каждый пакет имеет собственный контекст и транзакцию. Блокировки каталога и таблицы защищают исходную строку внутри пакета; чтение во время пакетной подготовки доступно. Адрес, ID, назначения, статус и поля аудита не изменяются. При Ctrl+C или ошибке повторить ту же команду: подтверждённые пакеты повторно не обрабатываются, неподтверждённый пакет откатывается. Счётчики относятся к текущему запуску; адреса и настройки подключения не печатаются.
5. Убедиться, что незаполненных ключей нет. Выполнить штатное обслуживание статистики после массового обновления. Проверить размер частичного индекса: после подготовки он логически пуст, но физический размер может требовать REINDEX в том же окне обслуживания. VACUUM сам по себе не гарантирует уменьшение файла индекса.
6. Запустить проверенную версию, проверить чтение, создание нового адреса и отказ для эквивалентного дубля, затем разрешить запись. Гарантия готовности в сервисе сохраняется: появление NULL-ключа от внешней загрузки снова запрещает создание/редактирование до явной подготовки. Изменения статуса и назначения не заменяют операционный запрет записи на время выпуска.

Прямое SQL-изменение Address с прежним CanonicalSource отклоняется CHECK. Внешний административный импорт должен либо рассчитать оба корректных поля по тем же правилам и соблюдать блокировки, либо оставить оба NULL и повторить подготовку до возобновления записи. Нельзя подставлять непроверенный ключ ради обхода готовности.

Откат: остановить запись, откатить только новую миграцию до AddApiSnapshotConfirmation штатным инструментом, вернуть прежнюю версию и проверить каталог. Shadow-поля и новые индексы удаляются; исходные Address, ID, назначения и аудит сохраняются. Прежний алгоритм снова выполняет полное чтение адресов. Не запускать старую версию для записи поверх новой схемы с CHECK.

## Проверки

Сборка прошла без ошибок: итоговая инкрементальная — без предупреждений; пересборка Web показывала 25 существующих предупреждений. Полный функциональный прогон: **4 711 unit + 21 060 integration = 25 771**. Миграции, откат и повторное применение выполнялись только на временной изолированной PostgreSQL-БД, удалённой после прогона.

IpCanonicalKeyTests проверяет старые варианты IPv4/IPv6/CIDR, mapped IPv6, эквивалентные дубли и невалидные строки, пакеты и повторный запуск, сохранение исходных данных и аудита, отмену, откат после фактического SQL-save, обновление собственного ID, синхронное сохранение, отказ CHECK при устаревшем ключе и два конкурирующих эквивалентных создания. CLI-проверки подтверждают отказ некорректного запуска до инициализации host/БД. Проверки EF подтверждают соответствие snapshot и сохранение всей прежней цепочки плюс новую миграцию.

EXPLAIN с enable_seqscan=off подтверждает применимость индексов; это не доказательство естественного выбора плана. Синтетический замер на исправленном объёме 500 тыс. IP завершён отдельно; браузерная приёмка остаётся отдельной.

Первый синтетический прогон выявил медленное сохранение ключей отдельными EF UPDATE: 500 тыс. за 79,0 с, миллион за 158,9 с. Замер намеренно прерван отменой запроса только в его временной БД, runner выполнил штатное удаление БД. После этого сохранение заменено одним SQL UPDATE на пакет; результаты первого прогона не являются подтверждением завершённой нагрузки и не описывают итоговую реализацию.

Повторный прогон на прежнем ориентире 10 млн остановлен после уточнения пользователя; его временная БД также удалена штатным finally.

## Итоговый синтетический замер

Полный Benchmark завершился с кодом 0: 200 000 сотрудников, 1 000 подразделений, 500 000 IP, экспорт ровно 100 000 строк. Runtime .NET 10.0.12, 12 логических CPU, Debug, локальная PostgreSQL. БД и временный архив удалены. Заполнение сотрудников и IP после создания подразделений заняло 14,0 с; подготовка всех 500 000 ключей пакетами по 2 000 — **16,0 с**. После массового обновления выполнен VACUUM ANALYZE. Размер БД после подготовки — 268 940 991 байт; WAL и запас места не входят в это число.

Для обычных операций первый вызов измерен отдельно, затем пять прогретых вызовов:

| Сценарий | Первый, мс | Медиана прогретых, мс | Максимум прогретых, мс |
| --- | ---: | ---: | ---: |
| Создание IP, проверка сохранения и удаление тестовой записи | 60,7 | 1,6 | 3,3 |
| Отказ для эквивалентного старого IPv6 с полным префиксом | 5,2 | 0,7 | 1,1 |
| IP Count + страница, все подразделения, сортировка Address | 160,5 | 41,8 | 140,8 |
| IP Count + страница, своё подразделение | 9,1 | 2,5 | 3,5 |
| IP SearchAsync со стандартной сортировкой, все подразделения | 112,5 | 110,3 | 170,6 |
| Сотрудники, первая страница | 307,3 | 91,8 | 199,3 |
| Сотрудники, Skip 100 000 | 1 167,3 | 1 157,2 | 1 278,6 |

Снимок экспорта 100 тыс. строк — 1 513,3 мс; построение XLSX/ZIP — 2 642,3 мс, файл 254 447 байт. Данные синтетические и хорошо сжимаются. Измерения не включают HTTP, браузер, реальную стоимость permissions (в стенде фиксированный Root scope), параллельную нагрузку и сеть пользователя. Время миграции индексов на большой существующей БД отдельно не измерялось; 16 с подготовки не являются общей длительностью рабочего окна обслуживания.

Выявленная этими измерениями глубокая пагинация сотрудников проверена и ускорена [частичным индексом](architecture-personal-pagination-index.md): естественный план использует индекс, контракт Radzen сохранён. Выборочная [браузерная проверка ключевых сценариев](architecture-browser-acceptance.md) выполнена; полная пользовательская приёмка остаётся перед слиянием.
