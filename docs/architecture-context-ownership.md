# Владение контекстами и остаток legacy DI

Дата: 17 октября 2026 года. Ветка: `codex/architecture-ip-search`.

Этап 2 остаётся открытым. Контекст на операцию уже используется для основных записей. Scoped `ApplicationDbContext` нужен Identity; срок DI scope сам по себе не гарантирует безопасного параллельного использования. Эта поставка добавляет проверки и реестр, производственные регистрации не меняет.

## Владельцы

| Регистрация / потребитель | Владелец и завершение | Правило записи |
| --- | --- | --- |
| `IDbContextFactory<ApplicationDbContext>` | Фабрика общая; каждый вызывающий создаёт и освобождает собственный контекст | Фабричные options не содержат scoped-интерцептор. Создание контекста само по себе не устанавливает автора |
| `IUnitOfWorkFactory` → Personal, Subdivision, Classifier | Прикладной метод создаёт UoW через `await using`; UoW владеет контекстом, репозиториями и транзакцией | `PrepareAudit` фиксирует доверенного автора при создании UoW. Повтор операции требует нового UoW |
| IP и назначения IP | Метод сервиса; фабричный контекст и транзакция | Автор и UTC задаются явно; порядок существующих блокировок сохраняется |
| `ApplicationDbContext` scoped → Identity stores | HTTP request, отдельный scope административной операции или проверки сеанса; освобождает DI | Scoped-интерцептор получает текущую сессию при сохранении BaseEntity. Identity имеет собственные поля и concurrency stamps |
| `SecurityService`, `RoleAccessService` | Каждая операция открывает отдельный async scope, получает контекст и менеджер из него | Обязательные IdentityResult проверяются; составные записи в одной транзакции. После commit доставка событий не меняет подтверждённый результат |
| `LocalAccountService`, `OwnPasswordService`, `IpRestrictedSignInManager`, `PolicyUserManager`, middleware политики | Текущий HTTP request, последовательная работа через Identity store | Вход может сохранять счётчик ошибок/блокировку; смена пароля сохраняет hash/stamp. Нельзя перенести эти адаптеры в circuit или вызывать параллельно на одном store |
| `IdentityRevalidatingAuthenticationStateProvider` | Новый async scope при каждой проверке | Чтение через UserManager; контекст не хранится в circuit между проверками |
| `AccountPolicyService` | Фабричный контекст на вызов; worker создаёт scope на проход | Проверка политики может записывать блокировку, активность обновляется отдельным SQL. Это не только чтение |
| `ReadRepository<T>`, поиски, permissions, область, display, IP-допуск | Фабричный контекст на вызов, `await using` | Результат материализуется до освобождения. Несколько последовательных запросов не становятся одним снимком БД |
| Синхронизация и диагностика API | Контекст на запуск; отдельные контексты наблюдения. Worker владеет scope итерации | Автор задания сохраняется отдельно от HTTP; успешный снимок атомарен со статусом запуска; соединение session lock живёт до освобождения блокировки |
| Экспорт и HTTP-выдача | Контексты команды, снимка, обработки и результата выдачи принадлежат соответствующему вызову; worker владеет scope итерации | Файл и БД без общей транзакции; завершение выдачи использует отдельный контекст и ограниченный token очистки. Audit после commit не определяет успех записи |
| `IDbContextFactory<LogsDbContext>` → `LogService` | Сервис освобождает контекст чтения отдельной БД логов | Не участвует в транзакции основной БД; Serilog и security audit имеют собственный жизненный цикл |
| `DatabaseSeeder`, `DatabaseInitializer.ApplyMigrationsAsync` | Явный стартовый scope | Специальные административные записи. Рабочее приложение не запускалось; runtime-тесты используют временную БД runner |

Фабричные контексты не принадлежат DI scope, который разрешил фабрику. Их освобождает операция. Scoped контекст Identity, наоборот, принадлежит scope; внешний сервис не должен освобождать его отдельно от scope или смешивать с контекстом фабрики в одной транзакции.

## Legacy-регистрации и сканирование

В `Program.cs` явно зарегистрированы scoped `IUnitOfWork`, открытые `IGenericRepository<>` и `IBasicRepository<>`. Поиск потребителей в исходниках Guard не обнаружил их constructor injection: прикладные сервисы получают `IUnitOfWorkFactory`, а репозитории создаются самим UoW на его контексте. Это кандидаты на удаление, а не основание удалить scoped контекст Identity.

`SubdivisionRepository` и `IpAddressRepository` попадают под Scrutor по суффиксу `Repository`; наследуемые интерфейсы также участвуют в `AsImplementedInterfaces`. Потребителей этих специализированных интерфейсов в исходниках Guard не найдено. Само отсутствие явного `AddScoped` не означает отсутствия регистрации. Общий `ReadRepository<>` также соответствует предикату сканирования: перед очисткой нужна проверка конечных descriptors, включая открытые generic и дубликаты.

Сервисы по суффиксу `Service` регистрируются через Scrutor. Явные исключения сохраняют отдельные регистрации `DataAccessScopeService`, `CurrentUserService`, `AuditService`, `LogService`; `UnitOfWork` и базовые write repositories исключены. `DirectoryApiClient` зарегистрирован через `AddHttpClient` и явно исключён; его текущее имя не заканчивается на `Service`/`Repository`, но исключение защищает от будущей смены предиката. HTTP-адаптеры Account тоже попадают в scoped-сканирование; ограничение их использования HTTP-запросом остаётся частью контракта.

Эта поставка не утверждает, что весь production DI был разрешён через `ValidateOnBuild`: тестовый контейнер содержит только зависимости проверяемой операции. Следующий шаг очистки — сделать проверяемой общую регистрацию с тем же Scrutor-предикатом, подтвердить конечные descriptors и разрешение Identity/typed client без запуска и seeding приложения, затем удалить подтверждённо неиспользуемые регистрации.

## Выполненные проверки

`OperationLifetimeIntegrationTests`, вызванный из `RefactorIntegrationTests`, добавляет 11 проверок на временной PostgreSQL-БД:

- Один scoped `IUnitOfWorkFactory` создаёт разные контексты. Две операции доходят до барьера в открытых транзакциях, затем сохраняют независимо. Общая блокировка режима закономерно сериализует соответствующий участок SQL; тест не требует одновременного владения этой блокировкой.
- Успешная запись сохраняется, вторая откатывается после своего `SaveChangesAsync`. Изменение тестового исполнителя после создания UoW не меняет захваченных авторов. Проверяются UTC, освобождение обоих контекстов до завершения scope и новая запись тем же scoped factory после отката.
- Реальный `SubdivisionService.MoveAsync` меняет корень и потомка. Тестовый `SavedChangesAsync`-интерцептор бросает отмену после успешного SQL-сохранения двух строк до commit. Независимая выборка подтверждает откат Path, ParentId, Version и метаданных аудита обоих узлов. Производственный код интерцептор не использует.

Сборка успешна: 0 ошибок; при полной компиляции — 25 прежних предупреждений, последняя инкрементальная сборка — 0 предупреждений. Runner завершился с кодом 0: **20 050 проверок**, временная БД удалена. Рабочие данные, подключения, схема, UI и производственные регистрации не менялись; приложение и браузер не запускались.

## До завершения этапа 2

1. Проверить конечный production DI без побочных эффектов старта и убрать подтверждённый legacy регистрации.
2. Детерминированно проверить пересекающиеся перемещения дерева, включая одновременное изменение нового родителя и его предков. Текущие тесты stale version и отката не доказывают корректность всех таких гонок.
3. Проверить гонку переключения режима API с уже начатой ручной записью. Нынешние API-тесты проверяют запрет в установленном режиме; это отдельный критерий.
4. Сохранить существующие проверки отката составных Identity-операций и дополнить выбранные сценарии отказа обязательного шага после промежуточного сохранения. Не подменять такую проверку ошибкой доставки события после commit.

Неопределённый результат commit, отказ самого ILogger/освобождения ресурсов, гарантированная доставка событий и конкурентные HTTP-запросы смены пароля этой поставкой не моделируются. Перед выделением Domain по-прежнему нужны решения о `Personal.User` и независимых enum/контрактах с сохранением схемы и поведения FK.
