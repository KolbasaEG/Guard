# Владение контекстами и остаток legacy DI

Дата: 17 октября 2026 года. Ветка: `codex/architecture-ip-search`.

Этап 2 остаётся открытым. Контекст на операцию уже используется для основных записей. Scoped `ApplicationDbContext` нужен Identity; срок DI scope сам по себе не гарантирует безопасного параллельного использования. Регистрация контекстов, Identity и прикладных сервисов вынесена в `GuardServiceRegistration.AddGuardServices`, который вызывается из Program и тестов. Инициализация БД, seeding, настройка Serilog/SIEM и запуск приложения остаются в Program и этим методом не выполняются.

## Владельцы

| Регистрация / потребитель | Владелец и завершение | Правило записи |
| --- | --- | --- |
| `IDbContextFactory<ApplicationDbContext>` | Фабрика общая; каждый вызывающий создаёт и освобождает собственный контекст | Фабричные options не содержат scoped-интерцептор. Создание контекста само по себе не устанавливает автора |
| `IUnitOfWorkFactory` → Personal, Subdivision, Classifier | Прикладной метод создаёт UoW через `await using`; UoW владеет контекстом, репозиториями и транзакцией | `PrepareAudit` фиксирует доверенного автора при создании UoW. Повтор операции требует нового UoW |
| IP и назначения IP | Метод сервиса; фабричный контекст и транзакция | Автор и UTC задаются явно; порядок существующих блокировок сохраняется |
| `ApplicationDbContext` scoped → Identity stores | HTTP request, отдельный scope административной операции или проверки сеанса; освобождает DI | Scoped-интерцептор получает текущую сессию при сохранении BaseEntity. Identity имеет собственные поля и concurrency stamps |
| `SecurityService`, `RoleAccessService` | Каждая операция открывает отдельный async scope, получает контекст и менеджер из него | Обязательные IdentityResult проверяются; составные записи в одной транзакции. После commit доставка событий не меняет подтверждённый результат |
| `LocalAccountService`, `OwnPasswordService`, `IpRestrictedSignInManager`, `PolicyUserManager`, middleware политики | Текущий HTTP request, последовательная работа через Identity store | Вход может сохранять счётчик ошибок/блокировку; смена пароля сохраняет hash/stamp. Нельзя перенести эти адаптеры в circuit или вызывать параллельно на одном store |
| `IdentityRevalidatingAuthenticationStateProvider` | Новый async scope при каждой проверке | Чтение через UserManager; контекст не хранится в circuit между проверками |
| `AccountPolicyService` | Фабричный контекст на вызов; worker создаёт scope на проход | Проверка политики может записывать блокировку, активность обновляется отдельным SQL. Это не только чтение |
| `ReadRepository<T>`, поиски, permissions, область, display, IP-допуск | Фабричный контекст на вызов, `await using` | Результат материализуется до освобождения. Несколько последовательных запросов не становятся одним снимком БД |
| Синхронизация и диагностика API | Контекст на запуск; отдельные контексты наблюдения. Worker владеет scope итерации | Автор задания сохраняется отдельно от HTTP; успешный снимок атомарен со статусом запуска; соединение session lock живёт до освобождения блокировки |
| Экспорт и HTTP-выдача | Контексты команды, снимка, обработки и результата выдачи принадлежат соответствующему вызову; worker владеет scope итерации | Файл и БД без общей транзакции; завершение выдачи использует отдельный контекст и ограниченный token очистки. Audit после commit не определяет успех записи |
| `IDbContextFactory<LogsDbContext>` → `LogService` | Сервис освобождает контекст чтения отдельной БД логов | Не участвует в транзакции основной БД; Serilog и security audit имеют собственный жизненный цикл |
| `DatabaseSeeder`, `DatabaseInitializer.ApplyMigrationsAsync` | Явный стартовый scope | Специальные административные записи. Рабочее приложение не запускалось; runtime-тесты используют временную БД runner |

Фабричные контексты не принадлежат DI scope, который разрешил фабрику. Их освобождает операция. Scoped контекст Identity, наоборот, принадлежит scope; внешний сервис не должен освобождать его отдельно от scope или смешивать с контекстом фабрики в одной транзакции.

## Legacy-регистрации и сканирование

Удалены scoped-регистрации `IUnitOfWork`, открытых `IGenericRepository<>` и `IBasicRepository<>`. Поиск потребителей в исходниках Guard не обнаружил их constructor injection: прикладные сервисы получают `IUnitOfWorkFactory`, а репозитории создаются самим UoW на его контексте. Классы и интерфейсы репозиториев сохранены; scoped контекст Identity сохранён.

Scrutor теперь сканирует только суффикс `Service`. Неиспользуемые `SubdivisionRepository` и `IpAddressRepository` больше не регистрируются вместе с унаследованными write-интерфейсами. `IReadRepository<>` зарегистрирован явно один раз. Тесты проверяют конечные descriptors, включая отсутствие специализированных, открытых и закрытых legacy write-регистраций. Отдельная регистрация `RoleManager<ApplicationRole>` также удалена: менеджер уже предоставляется AddIdentity, что подтверждено конечным descriptor и разрешением сервиса.

Сервисы по суффиксу `Service` регистрируются через Scrutor. Исключения по точному типу сохраняют отдельные регистрации `DataAccessScopeService`, `CurrentUserService`, `AuditService`, `LogService`. `DirectoryApiClient` зарегистрирован через `AddHttpClient` и явно исключён; его текущее имя не заканчивается на `Service`, но исключение защищает от будущей смены предиката. HTTP-адаптеры Account тоже попадают в scoped-сканирование; ограничение их использования HTTP-запросом остаётся частью контракта.

`ServiceRegistrationTests` вызывает производственный метод регистрации в пустом WebApplicationBuilder без чтения appsettings и секретов. В обоих режимах Development/Production используются синтетические строки подключения, Serilog без sinks и ephemeral Data Protection. Контейнер проверяется с `ValidateOnBuild`/`ValidateScopes`; разрешаются все интерфейсы сервисов сборки Guard из конечного набора, а также закрытые read repositories, Identity managers/stores и workers. Host и workers не запускаются, операции БД/HTTP не выполняются. Регистрация Radzen, middleware и внешние sinks логирования этим тестом не проверяются.

## Конкурентное изменение дерева

Для ручного создания и перемещения дерева блокировка режима `73460219` теперь берётся внутри транзакции до чтения узлов, родителя и потомков; затем повторно проверяется локальный режим. Это закрывает сохранение устаревшего пути нового родителя, которого операция сама не обновляет. Блокировка удерживается до commit/rollback, дополнительных ключей и перестановки существующих блокировок нет. `TreeConcurrencyIntegrationTests` останавливает первую операцию после чтения дерева перед SQL-save, наблюдает ожидание второй в `pg_locks` и отсутствие чтения дерева до получения блокировки. Проверены перенос нового родителя, его предка, stale version потомка, цикл, создание под перемещаемым родителем и отмена ожидания. Проверяется согласованность всех ParentId/Path, обновление версий и автора, неизменность цели отменённой операции. Это проверки ручных операций сервиса; прямой SQL вне протокола блокировок ими не защищается.

## Переключение режима и начатая ручная запись

`ManagementModeConcurrencyTests` проверяет реальный `PersonalService.CreateAsync`, `UnitOfWorkFactory`, `ApplicationDbContext` и `SynchronizationService.SaveSettingsAsync`. Тестовый интерцептор останавливает ручную операцию после предварительной проверки Local перед запросом блокировки либо после SQL-вставки до commit. Вторая транзакция наблюдается ожидающей через `pg_locks`; порядок не зависит от задержки запуска задач.

- API-режим фиксируется первым: ручная операция, уже прошедшая предварительную проверку Local, после получения блокировки читает новый режим и получает `EntityRuleException`; сотрудник не создаётся.
- Ручная запись фиксируется первой: смена режима ждёт её commit, затем сохраняет API-режим; сотрудник и его автор/UTC сохраняются.
- Смена режима откатывается после SQL-save до commit: ожидающая ручная операция продолжается в Local; настройки, версия и аудит настроек остаются прежними, успешное событие не отправляется.
- Смена режима отменяется при ожидании блокировки ручной записи: отменённая операция не меняет настройки, ручная запись завершается успешно.

Независимый контекст до commit не видит промежуточных настроек или сотрудника. Проверяются версия и аудит настроек, число событий только после commit, отсутствие отклонённого сотрудника и новая успешная запись тем же scoped сервисом после завершения каждой гонки. HTTP запрещён тестовым handler; рабочие подключения и данные не меняются. Производственный код не изменён: существующая блокировка и повторная проверка режима уже обеспечивают требуемый порядок. Добавлена **31 проверка**; полный runner с PostgreSQL — **20 231**, временная БД удалена. Сборка: 0 ошибок, 25 прежних предупреждений.

Это проверка ручного создания сотрудника и сохранения режима через сервисы. Она не заменяет проверки применения API-снимка, всех видов ручных записей или записи прямым SQL в обход протокола блокировок.

## До завершения этапа 2

Сохранить существующие проверки отката составных Identity-операций и дополнить выбранные сценарии отказа обязательного шага после промежуточного сохранения. Не подменять такую проверку ошибкой доставки события после commit.

Неопределённый результат commit, отказ самого ILogger/освобождения ресурсов, гарантированная доставка событий и конкурентные HTTP-запросы смены пароля этой поставкой не моделируются. Перед выделением Domain по-прежнему нужны решения о `Personal.User` и независимых enum/контрактах с сохранением схемы и поведения FK.
