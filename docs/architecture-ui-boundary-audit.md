# Аудит оставшихся границ UI

Дата: 16 октября 2026 года. Проверено дерево после `b7b647b` в ветке `codex/architecture-ip-search`. Это дополнение к исходному [инвентарю](architecture-inventory.md), а не замена исторической базы. Проверка статическая: изучены потребители в Components, прикладные контракты и реализации затронутых операций. Сборка, браузер, PostgreSQL и нагрузочные замеры в рамках этого аудита не запускались.

## Вывод

В `Components/Pages` и `Components/Layout` не найдены прямые обращения к EF, DbContext, репозиториям или query-делегатам сервисов. Основные списки уже получают DTO. Однако критерий завершения этапа 1 ещё не выполнен: UI использует сущности для редактирования сотрудников и настроек, получает граф Identity через общий контекст, зависит от конкретных реализаций фильтров и Serilog. Отдельно Account содержит прямые обращения к Identity.

Выделять четыре проекта сейчас рано: перенос текущих типов закрепит зависимость Web от инфраструктурных моделей, а перенос сервисов целиком — зависимость Application от EF и Radzen. Микросервисы этих препятствий не устраняют; решение остаётся одним процессом.

## Аудит безопасности и Account

Отдельной страницы истории аудита не найдено. `IAuditService` имеет независимые параметры (AuditEventType и строки), реализация AuditService использует Serilog и должна остаться в Infrastructure. HTTP-вход, выход и восстановление пароля вызывают аудит из адаптеров Account; это допустимая ответственность Web при независимом контракте. Технический журнал и события безопасности сохраняют разные назначения.

`Components/Account` использует UserManager, SignInManager и ApplicationUser: Login, Register, подтверждения email, восстановление пароля, 2FA, passkeys, управление профилем, authentication state provider и endpoints. Это отдельная группа переноса, которую нельзя считать решённой формами администрирования пользователей. До переноса Web составить реестр маршрутов и фактической доступности этих сценариев; не удалять шаблонные страницы и не менять бизнес-поведение по результатам текстового поиска.

Нужны независимые операции Account и адаптеры Identity, сохраняющие cookie, security stamp, antiforgery, IP-допуск, аудит и результаты каждого обязательного Identity-шага. HTTP/circuit-обёртки остаются в Web. Проверка восстановления/смены пароля и logout уже есть в runner; остальные сценарии должны получить явный статус «проверен / не используется / требует проверки» до приёмки переноса. Данный аудит не доказывает работоспособность всех шаблонных маршрутов.

## Последовательность оставшихся поставок

Это уточнение объёма утверждённых этапов 1–2, а не новый архитектурный подход. Поставки делать последовательно, сохраняя собираемое приложение.

1. **Сотрудники.** Узкий контракт поиска/чтения/редактирования, DTO редактора и выбора, независимая проверка PersonalFilter. Перевести Add/Edit/PersonalFields и обновление после назначения IP. Проверить Read против ReadDetails, архив, область подразделений, запрет API-редактирования, конфликт версии и статус после сохранения IP; сохранить совпадение списка/экспорта. Это следующая реализация.
2. **Модель отображения пользователя и исполнитель операции.** Убрать Identity-граф из каскадного контекста, обновить Layout и потребителей. На сервере получить доверенного исполнителя и область, согласовать повторные проверки чтения и записи. Проверить Root без сотрудника, отсутствующее подразделение, смену permissions/области, отмену и устаревший ответ. Эта поставка пересекается с этапом 2 и не означает его полного завершения.
3. **Синхронизация.** Независимые команды и DTO, совместимые адаптеры внутренних runner/worker. Не менять хранение очереди, advisory locks, recovery, версию настроек и подтверждение полного снимка. Проверить, что DTO не содержит защищённого пароля, а новый пароль передаётся только командой сохранения и не журналируется.
4. **Экспорт и настройки.** Разделить Capture/Apply, убрать зависимость UI от DataExportService, ввести DTO retention/политики и независимые уровни журнала. Проверить старое JSON-задание, совпадение фильтров с выборкой, preview/выдачу/отзыв прав, конкуренцию настроек и публичные требования пароля. Из-за различий этих сценариев при необходимости разделить поставку на несколько коммитов.
5. **Account и очистка границ.** Выделить Identity-адаптеры, переключить UI на узкие контракты; проверить явную регистрацию и Scrutor. Убрать из будущего Application Radzen/EF/Identity/Serilog; закрыть или оставить внутри Infrastructure нужные legacy API. Подготовить автоматические проверки зависимостей при выделении проектов.

После этого отдельно завершить аудит времени жизни контекстов и атомарности этапа 2. Наличие фабрики не доказывает атомарность нескольких шагов; для каждой составной записи нужен один владелец контекста/транзакции и сохранённый аудит. Не считать завершённым весь этап по проверке только одной области.

## Условия перехода к отдельным проектам

- Потребители UI используют независимые контракты; никакой публичный контракт будущего Application не содержит EF, IQueryable, Radzen, Identity-модели или Serilog.
- Нет обратной связи Personal → ApplicationUser в будущем Domain. Оставшиеся сущности в фильтрах действительно независимы от Infrastructure.
- Web сохраняет HTTP/circuit/composition root; запросы и запись исполняются в Infrastructure, последовательность прикладных операций — в Application.
- Для затронутых областей пройдены сборка, подходящие тесты и браузерные сценарии; для транзакций и конкуренции — изолированная PostgreSQL. Перенос истории миграций и проверка publish остаются обязательными воротами следующих этапов.
- Схема и рабочие подключения не меняются ради переноса. Приёмка текущей ветки, merge и рабочее развёртывание остаются отдельными действиями.

Строки аудита о моделях Personal в этих формах описывают исходное состояние до этой поставки. Сравнение исходных полей и обновление Version после IP сохранены; чтение DTO ограничено серверными правами, областью и активным статусом. В пункте 1 последовательности ещё остаются узкие контракты списка/просмотра и независимая проверка PersonalFilter. Этап 1 целиком не завершён.

Уточнение после переноса списка и просмотра сотрудников: Index использует IPersonalSearchService/IPersonalStatusService, Details — IPersonalDetailsService. Проверка PersonalFilter вынесена в независимый PersonalFilterValidation; Web больше не вызывает PersonalQueryFilter.Apply/AsQueryable. Сервер поиска и экспорта повторно проверяет контракт перед построением выражения. Оставшиеся пункты аудита, включая UserContext и Account, сохраняют силу.
