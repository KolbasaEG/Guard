# Выделение Guard.Application

Дата: 17 октября 2026 года. База: `2c32bfb`, ветка `codex/architecture-ip-search`.

Создана библиотека .NET 10 Guard.Application. Единственная ссылка проекта — Guard.Domain; пакетов и FrameworkReference нет. Решение содержит три производственных проекта и существующий runner. Процесс приложения, подключения и схема БД сохраняются.

## Перенесённый состав

Физически перенесены 72 исходных файла. Все они совпадают с исходными Git blobs: содержимое, кодировки, namespace и поведение сохранены.

- 35 независимых интерфейсов, включая три порта чтения доступа; некоторые файлы содержат несколько интерфейсов и сопутствующие записи.
- Все DTO из Core/6-Services/DTOs, контракты и параметры экспорта из ExportContracts.cs.
- IpAccessService, PermissionService и DataAccessScopeService: решения принимаются через существующие порты, без EF, HTTP и ASP.NET Identity.
- SubdivisionAccessPath, IpAddressRule, Permissions, PermissionDefinition/PermissionCatalog и прикладные исключения.

Каталог permissions перенесён вместе с UserAccessSnapshot: его метод Has использует каталог в теле, хотя это не видно из публичной сигнатуры. Исторический namespace Guard.Core.Identity сохранён для независимых правил; библиотека не ссылается на ASP.NET Identity. EntityWriteMapping, EF-запросы и фильтры, readers, контексты, миграции, workers и реализации атомарных операций остаются в Guard. Семь legacy-интерфейсов также остаются там; перенос Core целиком не выполнялся.

## Зависимости и регистрация

Направление ссылок: Guard → Guard.Application → Guard.Domain; прямая ссылка Guard → Domain остаётся. Оба проекта явно подключены к runner. Domain не зависит от Application.

Scrutor продолжает сканировать только Guard. Три перенесённых сервиса доступа зарегистрированы явно как scoped; тест проверяет единственность, тип и lifetime каждой регистрации в Development и Production. Typed HTTP client сохраняет прежнюю регистрацию и таймаут. Проверка разрешения производственного графа DI теперь охватывает интерфейсы обеих сборок; host, фоновые задачи и внешние интеграции при этом не запускаются.

ApplicationContractBoundaryTests проверяет зависимости скомпилированной сборки только на Domain/BCL, сохранение 35 интерфейсов, размещение трёх реализаций, отсутствие дубликатов типов в Guard и ровно семь оставшихся legacy-контрактов. Проверка публичных сигнатур дополнена всеми DTO, включая экспорт: предметные сущности, IQueryable, EF, Identity, HTTP и Radzen на этой границе запрещены. DomainAssemblyBoundaryTests теперь определяет host через GuardServiceRegistration, поскольку ICurrentSession принадлежит Application.

## Проверки и ограничения

- Restore и сборка решения выполнены: 0 ошибок, 25 прежних предупреждений; последующая инкрементальная сборка тестов — 0 ошибок и предупреждений.
- Отдельная сборка Guard.Application: 0 ошибок и предупреждений.
- Полный runner с PostgreSQL: **20 797 проверок**, код завершения 0; изолированная временная БД удалена по завершении.
- Проверены неизменность содержимого 72 перенесённых файлов, diff и включение новых путей в статический инвентарь.
- Интеграционные проверки сохранили контроль реляционной модели относительно снимка миграций, IP/permissions/области подразделений, Identity, конкурентных записей, дерева, синхронизации и экспорта.

Рабочая БД и настройки подключения не изменялись. Приложение, браузер, публикация и развёртывание не запускались; нагрузка в 10 млн IP и экспорт 100 тыс. строк повторно не измерялись. Полные имена типов сохранены, assembly-qualified names изменились: нужен полный согласованный вывод сборки/публикации, включая Guard.Application.dll и Guard.Domain.dll. Совместимость сторонних бинарных потребителей не проверена.

## Следующий участок

Цель остаётся прежней: четыре производственных проекта и два тестовых. Этапы 1–2 ещё открыты по реализации прикладных операций. Следующий участок — определить состав Guard.Infrastructure и его обратные зависимости от Web: текущая регистрация объединяет UI/Identity, контексты, typed clients и workers. Перед физическим переносом нужно разделить регистрацию и адаптеры, сохранить аудит и общий контекст Identity внутри операции, расположение EF-конфигураций и миграций, а также разрешение графа DI. Транзакции и блокировки нельзя дробить ради ссылок сборок. Неопределённый результат commit при потере соединения остаётся ранее описанным ограничением.
