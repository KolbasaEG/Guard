# Сверка критериев этапов 1–2

Дата: 17 октября 2026 года. Проверяемая база: `c7d77fc` и [индекс пагинации сотрудников](architecture-personal-pagination-index.md), ветка `codex/architecture-ip-search`.

## Вывод

Технический критерий этапа 1 выполнен. Публичные прикладные интерфейсы UI находятся в Application и не требуют EF, IQueryable, Radzen или моделей Identity; страницы не выполняют EF-запросы. Это результат проверки кода и существующих автоматических проверок, а не пользовательская приёмка всех экранов.

Технический критерий этапа 2 выполнен в пределах приведённой матрицы. Исполнитель, актуальные permissions, область и владельцы контекстов определены; атомарные инфраструктурные операции допустимы по самому плану. Наличие EF внутри такой операции не является основанием для нового слоя прокси. Последняя выявленная транспортная зависимость создания экспорта отделена через IClientIpAccessor и доверенный Web-адаптер; см. [проверки метаданных](architecture-export-request-metadata.md). Это не пользовательская приёмка и не разрешение merge.

Физическая структура четырёх производственных проектов и двух runners уже реализована. Микросервисы и дополнительные процессы для одного разработчика и одного сервера не требуются.

## Этап 1

| Пункт плана | Статус и доказательство |
| --- | --- |
| 1. Явные запросы, Items + Count и DTO | Выполнен для перенесённых списков и форм. Контракты перечислены и рекурсивно проверяются в ApplicationContractBoundaryTests; сейчас 37 интерфейсов: 34 сервисных и 3 порта доступа |
| 2. Независимые фильтры и повторная серверная проверка | Выполнен: SearchFilterContractTests, IpSearchFilterTests и проверки фильтров областей; UI передаёт параметры, а не произвольное выражение запроса |
| 3. Модели полей фильтра в Web | Для Identity и технических списков используются отдельные модели; независимые Domain-типы в остальных фильтрах допускаются планом |
| 4. Доступ, статус, иерархия, фильтр, Count и пагинация | Проверяется специализированными тестами поисков и PostgreSQL-сценариями. Отдельно сохраняется ограничение отображения Root выбранной иерархией |
| 5. Удаление query API из UI | Выполнен: поиск по Components не обнаружил EntityFrameworkCore, IQueryable, SearchQuery, IReadRepository или DbContext. Семь legacy-интерфейсов удалены; Infrastructure больше не владеет сервисными интерфейсами |
| 6. Разделение Capture и исполнения экспорта | Выполнен; см. [границу экспорта](architecture-export-boundary.md). Web преобразует Radzen, сервер проверяет независимый фильтр. HTTP-выдача отдельно перенесена в Web |
| 7. DTO редакторов и ограниченные результаты Identity | Выполнен: узкие контракты управления и Account не возвращают ApplicationUser, ApplicationRole или IdentityResult. Согласованный Account: вход, выход, свой пароль; существующая 2FA блокирует новый вход, данные 2FA сохраняются |

Основание для статуса: ApplicationContractBoundaryTests, ManagementBoundaryTests, функциональные проверки границ областей и поиск по исходникам. Последний полный функциональный прогон — 4 711 unit + 21 073 integration = 25 784 проверки, включая временную PostgreSQL-БД. Синтетический замер выполнен на 200 тыс. сотрудников и 500 тыс. IP; результаты и ограничения приведены в отчёте индекса. Браузерная приёмка всех экранов после всей серии переносов остаётся отдельной.

## Этап 2

| Пункт плана | Статус и доказательство |
| --- | --- |
| 1. Доверенный исполнитель | Выполнен: ICurrentSession и CurrentSession; CurrentSessionAdapter в Web получает principal из Blazor/HTTP. Автор операции не берётся из DTO формы |
| 2. Актуальные permissions и область | Выполнен: независимые решения Application и три порта чтения; stamp, блокировка, срок пароля и Root сохраняются. Claim cookie не заменяет актуальные полномочия |
| 3. Исполнитель фоновых заданий | Выполнен в рассмотренных очередях: сохранённый автор или system:api-sync, повторные проверки в runner/экспорте. Workers с EF создают свои scope без AuthenticationStateProvider; см. [размещение workers](architecture-worker-boundaries.md) |
| 4. Контекст на операцию | Владельцы перечислены в [реестре контекстов](architecture-context-ownership.md). UoWFactory для сущностей, фабричные контексты IP/экспорта/синхронизации, отдельные async scope административных операций Identity. Request-scoped Identity для входа и своего пароля является явным исключением, а не контекстом circuit |
| 5. Обязательные IdentityResult и атомарность | Выполнен для охваченных административных операций. IdentityRollbackIntegrationTests и UserAdministrationIntegrationTests проверяют отказ после промежуточного SQL-save, откат, отсутствие событий успеха и повторное использование сервиса. Это не исчерпывающая инъекция отказа в каждый метод Identity |
| 6. Аудит, отмена, версии, блокировки, события после commit | Основные гарантии подтверждены сценариями дерева, режима управления, версий и завершения операций. UoWFactory фиксирует автора через PrepareAudit; подтверждённый результат сохраняется при охваченных сбоях последующего аудита. Неопределённый commit и гарантированная доставка событий не реализованы |
| 7. Узкие возможности хранения | Три порта чтения доступа и специализированные контракты операций существуют. Атомарные дерево, Identity и синхронизация остаются в Infrastructure по разрешению плана; разбивать их на отдельные репозиторные вызовы не требуется |
| 8. Защита generic ReadRepository | Сохранена. UI от него не зависит; удаление серверной защиты не нужно для закрытия этапа и допустимо только при эквивалентной защите всех путей |

DataExportService.CreateAsync получает снимок ClientIp через независимый IClientIpAccessor; Web-адаптер читает текущий доверенный RemoteIpAddress. Сохранены null вне HTTP, нормализация mapped IPv4, автор из IPermissionService и аудит после commit. Поиск по Application и Infrastructure/Core/6-Services не обнаружил HttpContext, IHttpContextAccessor или AuthenticationStateProvider. ClientIp не даёт полномочий.

LocalAccountService и OwnPasswordService — явные HTTP/Identity-адаптеры: они выпускают или обновляют cookie и используют request scope. IpRestrictedSignInManager и PolicyUserManager также остаются интеграцией Identity. Их физическое расположение само по себе не нарушает публичные контракты Application; будущий перенос должен сохранить регистрацию, политики, 2FA, аудит и семантику сохранённого пароля при ошибке обновления cookie. Не следует описывать Infrastructure как полностью свободную от HTTP.

## Порядок оставшейся работы

1. [Индексируемая уникальность IP](ip-catalog-canonical-keys.md) реализована: два EXISTS вместо материализации Address; ключи сохраняют прежнюю эквивалентность, старая БД требует миграции и явной возобновляемой подготовки. Рабочая БД не изменялась; переход выполняется в согласованное окно обслуживания.
2. Актуальные синтетические замеры и проверка ключевых экранов — отдельные свидетельства. Пользователь исправил объём каталога с 10 млн на примерно 500 тыс. IP; текущий Benchmark использует 200 тыс. сотрудников, 1 тыс. подразделений, 500 тыс. IP и экспорт 100 тыс. строк. Пользовательская приёмка и подтверждение merge остаются отдельными шагами.

Неопределённый результат commit, гарантированная доставка аудита, отказ ILogger и конкурентные HTTP-запросы смены пароля остаются отдельными вопросами надёжности. Их нельзя считать решёнными по результатам имеющихся тестов; они также не требуют введения микросервисов. Требуемые гарантии и цена реализации должны рассматриваться явно в соответствующем участке.
