# HTTP-граница передачи экспорта

Дата: 17 октября 2026 года. Ветка: `codex/architecture-ip-search`. База: `d2a2375`.

## Изменение

`ExportEndpoints` перенесён из Infrastructure в `Guard/Web/Exports`, namespace — `Guard.Web.Exports`. Маршрут `POST /exports/{id:guid}/download` сохранён. Web отвечает за авторизацию маршрута, CSRF, запрет Range, заголовки, копирование в HTTP body, Flush и преобразование ошибок в HTTP-ответ. Его параметры больше не содержат EF, ExportStorage или ExportAccess.

В Application добавлены `IExportDeliveryService` и `ExportDeliveryFile`: имя, content type, размер. Контракт использует только BCL, включая Stream и CancellationToken. Всего независимых интерфейсов теперь 36: 33 сервисных и три порта чтения доступа. Callback получает заимствованный поток только на время вызова; он обязан завершить копирование и Flush до возврата. Возврат означает успешную передачу со стороны сервера, исключение — неуспешную. Подтверждение получения файла клиентом этот контракт не обеспечивает.

`ExportDeliveryService` в Infrastructure сохраняет связанную оркестрацию без HTTP-зависимостей: доверенный пользователь, владелец задания (включая Root), проверка состояния и срока, SHA/размер, повторная проверка полномочий и области, ArchiveGate, атомарный Ready → Delivering и создание попытки. Файловый поток закрывает сервис. После callback сервис сохраняет Delivered/Failed и завершает попытку в одной транзакции, используя отдельный 15-секундный token при отмене исходного запроса. Затем освобождает ArchiveGate.

Регистрация scoped-сервиса выполняется существующим Scrutor-сканированием; новый явный дубликат не добавлен. Проверяется единственность регистрации в четырёх конфигурациях композиции.

## Ошибки и аудит

CSRF и Range отклоняются до вызова сервиса, проверок БД и занятия попытки; их аудит остаётся в Web с прежним отсутствующим автором. Сервис ведёт аудит последующих ошибок и переходов. Web не дублирует его. Сбои доставки событий по-прежнему логируются и не меняют подтверждённый исход операции. Сохранены прежние два ExportFailed при ошибке уже начавшейся передачи: ошибка и фиксация неуспешного завершения.

При ошибке callback сервис сначала выполняет завершение попытки, затем исключение попадает в Web для формирования ответа/Abort. Раньше HTTP-ошибка обрабатывалась до блока finally в общем endpoint; теперь HTTP-адаптер получает ошибку после финализации. Коды 403/404/409, безопасные сообщения, заголовки и одноразовость сохранены. Ошибка записи результата по-прежнему логируется без повторной выдачи; восстановление таких заданий остаётся обязанностью существующей обработки экспорта. Неопределённый исход commit и гарантированная доставка аудита этой поставкой не решаются.

Полное имя публичного CLR-типа endpoint изменилось; внутренние host и тестовые потребители обновлены. Внешние потребители старого extension namespace, если существуют вне репозитория, потребуют обновления. Схема БД, миграции, настройки и данные не изменены.

## Проверки

Добавлены проверки принадлежности HTTP-адаптера Web, независимости его аргументов от Infrastructure, отсутствия HTTP-зависимостей в конструкторе сервиса, новой границы контрактов и производственной DI. Новый тест напрямую вызывает независимый контракт: успешная передача, IOException и отмена внутри callback. Независимый DbContext видит подтверждённую попытку до копирования; проверяются точные байты/SHA, окончательное состояние и запрет повторного вызова callback.

Сохранены существующие HTTP-проверки CSRF, Range, владельца/Root, повреждения архива, точных байтов и заголовков, повторного скачивания, реального сбоя body и сбоев аудита. Первый прогон выявил некорректную новую проверку закрытия потока через CanRead: существующий ProtectedInput всегда возвращает true. Эта проверка удалена; production-обёртка не менялась.

Сборка решения прошла без ошибок. Полный повторный прогон: **4 711 unit + 20 963 integration = 25 674**; временная PostgreSQL-БД удалена. Итоговая инкрементальная сборка — без предупреждений; предшествующие сборки показывали существующие предупреждения Web/Infrastructure. Браузерные и нагрузочные сценарии в эту поставку не входят; приложение с рабочим Program не запускалось.

## Следующий участок

Проверить транспортные зависимости IpMiddleware, AccountPolicyMiddleware и PermissionAuthorizationHandler и перенести подходящие адаптеры в Web с проверками порядка и отказов. Workers и остальные EF-зависимые операции требуют отдельной сверки. Этапы 1–2 остаются открытыми.
